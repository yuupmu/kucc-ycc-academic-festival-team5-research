과거 Codex 작업부터 현재 파이프라인까지의 구조, 목적, 변경 이유, 실험 결과와 한계

작성일 2026년 11월 26일 · 한국 시간 기준

이 보고서는 2026년 10월 28일의 최초 설계 대화부터 2026년 11월 26일의 작업을 정리한다. 본문 상태표는 오전 10시 43분에 고정했다. 이후 오전 11시 02분까지 새로 확인한 학술제용 실험은 27절에 별도로 추가했다. 그 뒤 진행되는 작업은 다음 개정 대상이다. Markdown과 PDF는 같은 본문으로 제작했다.

## 1. 이 문서의 범위와 읽는 방법

이 프로젝트의 목적은 불충분한 요구사항을 받은 AI가 임의의 정책으로 코드를 완성하는 상황을 줄이는 것이다. 메인이 계획이나 코드 한 버전을 내면 감시자들이 빠진 정보와 근거 없는 판단을 발견하고, 완성 전에 사람에게 필요한 사항을 묻는다. 사람의 자연어 답변을 받은 메인은 코드를 수정하고 다시 검토받는다. 최종 정확도뿐 아니라 필요한 질문을 했는지, 답을 실제로 반영했는지, 비용이 얼마나 들었는지도 연구 대상이다.

그동안의 작업에는 웹 실행 환경 개발, 벤치마크 제작, 실제 API 파일럿, 작은 로컬 모델 선정, 감시와 자체 검토의 비교, A·B·C·D의 전달 구조 분석, 중간 채점 노출 문제의 정정, 인간 개입 복원, 시간 조건 보존 실험, 범용화 시도가 포함된다. 같은 이름을 썼어도 시기별로 역할과 정보가 달랐다. 따라서 각 실험은 당시의 모델·입력·질문 기회·수정 예산·채점 시점을 기준으로 설명한다.

자료는 과거 Codex 대화의 사용자 요청과 최종 보고, 현재 소스, 저장된 모델 요청·응답, 결과 JSON, 10월의 실행 DB, 기존 실험 보고서, 2차 미팅 PDF와 멘토 피드백을 대조했다. 실제 실행 10건의 상태와 채점 파일을 다시 읽었고, 주요 순차 실험의 합계는 결과 JSON에서 다시 계산했다. 이 문서를 만들기 위한 새로운 모델 성능 실험은 실행하지 않았다. [S01-S04, S20-S25]

문서에서 ‘실험 결과’는 저장된 결과로 확인한 값이다. ‘재생’은 저장된 응답이나 규칙을 다시 적용한 진단이며 새 모델 실행과 구분한다. ‘현재 구현’은 기준 시각에 존재하는 코드다. ‘다음 비교’는 아직 완료된 결과가 없는 제안이다. 미제출 코드의 연구자 측정값은 공식 제출 성적과 함께 표기하지 않고 상태를 명시한다.

현재까지 가장 직접적으로 확인한 두 사례가 있다. 자유 질문 시드 157에서 독립 감시자가 메인이 묻지 않은 정정 기간을 확인해 단일의 15개 정답을 멀티의 20개 정답으로 늘렸다. 시간 조건을 담당자 원문에 연결한 시드 263에서는 기존 멀티의 25개 정답이 29개로 늘고 2차부터 6차까지 유지됐다. 두 결과는 모두 같은 예약 취소 40문항의 제한된 비교이며, 해당 실행들은 버전 상한에서 미제출로 끝났다. [S20, S21]

## 2. 처음 의도와 지금의 연구 질문

### 2.1 10월 28일의 출발점

최초 대화에서는 Oxy, OxyGent, OxyBank와 같은 구성 개념을 참고하면서 ‘언제 인간의 판단을 요청할 것인가’를 논의했다. 사용자는 감시 페르소나를 3개 컨셉별로 3개씩 구상하고, 모델이 적절한 순간에 질문하는지와 인간 피드백이 작업물에 제대로 반영되는지를 보려 했다. 현장 맥락, 문제 정의, 가치 우선순위, 말로 설명하기 어려운 의도, 탐색 방향의 고착, 실제 사용 경험이 인간 개입의 후보였다.

처음에는 여러 작업 에이전트가 병렬로 일하는 구조도 검토했다. 이후 사용자는 ‘메인 프로그램이 프로젝트를 진행하고 감시자 1·2·3이 필요한 조언을 사람에게 요청한다’는 형태를 확정했다. 작업 에이전트 3명과 감시자 1명으로 설명한 초기 제안은 이 과정에서 수정됐다. 현재 연구의 중심 역할 수는 메인 1명과 감시자 3명이다. 9개 페르소나 아이디어는 탐색 후보이며 9명 동시 실행의 실험 기록을 뜻하지 않는다. [S01, S02]

### 2.2 무엇을 관찰하려 했는가

사람만 결정할 수 있는 운영 방침과 코드 안에서 검증 가능한 사실을 구분하는 것이 출발점이었다. 예를 들어 ‘현재 시간이 예약 생성보다 빠르면 어떻게 처리하는가’는 과제 계약에서 정할 수 있고, ‘정정 유예를 정확히 몇 분으로 운영하는가’는 담당자에게 물어야 한다. 감시자가 질문을 많이 만들었다는 사실만으로 연구 목표를 달성한 것은 아니다. 필요한 질문을 충분히 일찍 했고, 받은 답이 동작에 반영돼야 한다.

초기 설계에는 질문의 영향 범위, 관련 작업만 보류하는 방식, 질문 화면, 여러 사용자의 답을 절충하는 방식, 과거 인간 판단의 메모리 활용도 포함됐다. 실제 구현은 단일 함수나 텍스트 프로젝트의 공유 상태·질문·수정에 집중했다. 일반적인 여러 작업의 병렬 배분, 다중 사용자 의사결정 조정, 과거 결정으로 모델을 재학습하는 실험은 완료된 성과로 기록할 근거가 없다.

### 2.3 11월 26일에 다시 명시한 세 비교 조건

최신 관련 대화에서 사용자는 범용적인 구조와 아래 세 조건을 분명히 했다. 성능과 사용 토큰을 학술제에서 공개할 계획이며, 출력 양식 문제로 실험이 반복해서 막히면 로컬 모델을 한 단계 높이는 방안도 요청했다. 이 요청은 현재 보고서의 연구 방향을 해석하는 가장 최신 기준이다. [S24]

| 조건 | 정보와 질문 권한 | 비교하려는 효과 |
|---|---|---|
| ① 불충분한 정보의 메인 단독 | 공개 요구로 작업을 제출한다. 외부 정책 답을 받는 추가 검토가 없다. | 추가 개입 전의 기준 성능 |
| ② 메인 자체 점검과 인간 개입 | 메인이 부족한 정보를 점검하고 사람에게 질문한 뒤 수정한다. | 질문·추가 정보·자체 점검의 효과 |
| ③ 감시자 점검과 인간 개입 | 감시자 A·B·C가 누락을 찾아 질문하고, 받은 자연어 답으로 메인이 수정한다. | 감시 구조가 자체 점검에 더하는 효과 |

이전 인간 개입 실험에서는 멀티 조건의 메인도 질문을 낼 수 있었다. 최신 ③ 조건과 질문 주체가 완전히 같지 않다. 또 기존 단일 조건은 같은 세 관점의 자기검토를 세 차례 수행했다. 이 차이를 기록해야 이전 예비 결과와 앞으로의 세 조건 비교를 혼동하지 않는다. 기준 시각에 최신 세 조건의 완결된 결과표와 모델 교체 성적은 확인되지 않았다.

## 4. 이름과 용어를 구분해야 하는 이유

| 기록에 나온 이름 | 실제 의미 | 읽을 때 확인할 사항 |
|---|---|---|
| A·B·C 비교 | A 단독, B 자체 검토, C 독립 감시라는 실험 조건 | 에이전트 세 명의 이름과 다름 |
| A·B·C 감시자 | 같은 코드의 누락·근거·인간 판단을 각자 검토하는 역할 | 해당 회차에서 동료 의견을 받는지 확인 |
| D | 시기에 따라 의견 통합자, 코드 추적자, 후보 선택자, 최종 수정자 | 모든 실험에서 같은 일을 한 역할이 아님 |
| 단일 모델 | 동일한 모델 계열을 사용한다는 의미일 수도 있음 | 같은 모델로 여러 역할을 호출하는 멀티 구조가 가능 |
| 단일 에이전트 | 같은 개발자 역할이 혼자 작성하거나 여러 번 자체 검토 | 호출 1회와 여러 회를 구분 |
| 독립 검토 | 같은 회차의 다른 감시 응답을 보지 않고 검토 | 물리적인 동시 실행 여부와 별개 |
| 사이클 | 작성한 버전을 검토하고 다음 버전을 만드는 반복 | 새 시드 실행 횟수와 별개 |
| 시드 | 생성 난수의 초기값 | 다른 업무 과제나 새로운 평가 데이터와 별개 |
| 점수 | 해당 조건의 코드가 맞힌 문항 수 | 완료 여부, 미판정, 잘못된 반환을 함께 봐야 함 |

로컬 실험은 대체로 모델 슬롯 하나에서 역할들을 순서대로 호출했다. 독립 감시라는 말은 동료 응답을 입력에 넣지 않는 정보 조건을 뜻한다. 초기 웹 구현에서는 실제 비동기 감시와 먼저 도착한 질문 처리가 있었다. 두 실행기의 병렬성을 같은 것으로 설명하면 안 된다.

## 5. 초기 웹 실행 환경의 구조

### 5.1 화면 데모에서 실제 실행기로

초기 데모는 작업 A·B·C와 감시 분기를 표시했다. 각 분기에 답하면 그 분기만 진행하고 나머지는 기다렸으며, 마지막에 기록을 내려받았다. 당시 질문과 지연은 고정 예시와 타이머였고 실제 모델 생성이나 의미적 통합은 연결되지 않았다. 이후 메인 프롬프트 입력, 감시자 3명의 컨셉·지침, 진행 상태, 개입 요청, 답변·반영 기록 중심으로 화면을 단순화했다. [S01, S02]

모의 백엔드를 연결한 뒤 실제 API 연결·해제, 메인·감시자별 모델 선택, 공유 상태 저장, 코드 작성·검증, 사람 답변, 완료 후 수동 채점을 순서대로 구현했다. API 키는 메모리에 보관하고 실행 기록에는 넣지 않는 방식이었다. 과제별 정책을 열람하는 ‘규칙’ 버튼을 추가했으며, 사용자가 그 화면을 열었다는 사실만으로 모델에 정책을 전달하지 않는다.

### 5.2 웹 구현의 반복 흐름

```text
공개 과제와 사용자 프롬프트
  ↓
메인 → 계획·미확정 가정 제출
  ↓
공유 상태 저장 → 감시자 1 / 감시자 2 / 감시자 3
  ↓                          ↓
메인 → 코드 vN 작성          계속 / 검증 / 사람에게 질문
  ↓                          ↓
문법·자체 검사 → 상태 갱신    질문 화면 → 자연어 답변 저장
  ↓                          ↓
최신 상태와 답변을 다음 메인 호출에 전달
  ↓
새 코드 → 다시 감시 → 완료 조건 확인 → 수동 최종 채점
```

계획 제출 직후와 각 코드 버전 작성·검증 후에 감시자를 호출한다. 모델이 글자 단위로 코드를 생성하는 도중의 내부 사고를 읽는 구조는 아니다. 감시자가 보는 것은 공개된 계획·가정·소스·기록이다. 실행 관리자가 동일 시점의 상태를 복사해 각 감시자에게 넣는다.

같은 회차의 감시자들은 서로의 이번 응답을 보지 않는다. 웹 구현의 다음 회차에는 이전 감시 결과가 공유 상태에 포함될 수 있다. 한 감시자의 응답이 먼저 오면 질문을 등록하고, 같은 질문 key가 오면 합친다. 사람의 답이 왔을 때 이미 진행 중인 모델 호출을 소급해서 바꾸지는 못하므로 다음 메인 호출에 반영한다.

### 5.3 실제로 주고받은 정보

| 방향 | 데이터 | 용도 |
|---|---|---|
| 메인 계획 → 관리자 | plan, assumptions | 현재 작업 방향과 미확정 가정 기록 |
| 메인 구현 → 관리자 | 전체 code, summary, complete, 자체 검사 | 코드 버전 저장과 검증 |
| 메인 → 결정 처리 | applied_decision_ids, context_decision_ids | 코드 반영 보고와 맥락 확인을 구분 |
| 관리자 → 감시자 | 계약, 계획, 소스·버전, 질문·답, 이전 검토, 검사 결과 | 같은 상태를 서로 다른 관점에서 검토 |
| 감시자 → 관리자 | continue / verify / human, reason, requests, checks | 계속 진행·검증·질문 요청 |
| 담당자 → 공유 상태 | 질문에 대한 자연어 답·추가 조언 | 다음 작성과 검토의 운영 근거 |

완료 시에는 최신 코드에 대한 세 검토, 미응답 질문 유무, 메인의 완료 보고, 당시 구현된 검사 조건을 확인했다. 초창기 완료 처리에는 빈 검사 목록을 0/0 통과로 취급하는 결함이 있었고 이후 수정됐다. 결정 ID가 처리됐다는 모델의 보고는 자연어의 의미가 실제 코드와 같다는 증거까지 제공하지 못한다.

### 5.4 실제 사용한 감시 관점

기본 관점은 ‘개입 판단의 태도’, ‘집중하는 근거’, ‘인간에게 필요한 기여’였다. 첫 관점은 위험과 되돌릴 수 있는 범위, 사용자 의도를 보고, 둘째는 문서·검사·목표·의존성의 근거를 보며, 셋째는 현장 맥락·가치 우선순위·사용 경험처럼 사람이 보충할 내용을 봤다. 초기 로컬 자체 검토 대조군도 이 세 관점을 사용했다.

다른 실제 입력 묶음은 ‘주장 감사관’, ‘궤적 분석가’, ‘새벽 3시 온콜’이었다. 각각 작업자의 주장과 기록의 일치·누락, 현재 진행 방식이 좋은 결과로 이어지는지, 운영 중 문제가 생기면 빠르게 진단·중단할 수 있는지를 살폈다. 10월 30일 마지막 100점 실행은 이 묶음을 사용했다. 두 묶음을 같은 조건에서 반복 비교한 성능표는 없어 페르소나의 우열을 말할 수 없다. [S02]

### 5.5 저장·복구와 실행 상태

SQLite에 실행 설정과 상태를 저장하고, 코드 버전·모델 호출·원문 응답·사용량·질문·답변·채점 파일을 보존했다. 새 인간 답변 없이 자동 수정 6회가 이어지면 일시 정지했으며 사람 답변 반영을 이 제한과 구분했다.  중단·실패·재시작 뒤 기존 답변과 코드를 이어 쓰도록 했다. 진행 중, 모델 응답 대기, 사람 답변 대기, 일시 정지, 완료, 오류를 화면에서 구분했다.

`affected_tasks`는 영향 범위와 화면 상태를 나타내는 필드였다. 모든 하위 작업이 별도 에이전트로 병렬 실행되고 의존성에 따라 선택적으로 멈추는 범용 스케줄러가 완성됐다는 뜻은 아니다. 현재 사용자가 강조한 연구 대상도 질문·답변·반영 구조다. [S02, S24]

## 6. 만든 평가 과제와 점수의 뜻

### 6.1 원래 예약 취소 100문항

함수 계약은 `can_cancel(now, booked_at, starts_at) -> bool`이다. 입력은 현재 시각, 예약 생성 시각, 이용 시작 시각이다. 시각을 한국 시간으로 해석하고 잘못된 입력과 시간 순서를 처리하며, 휴무일에 따른 마감 조정까지 구현한다.

| 적용 순서 | 고정된 평가 정책 |
|---|---|
| 1 | 날짜 오류나 시간대가 없는 입력을 거부 |
| 2 | 예약 생성이 현재보다 미래이거나 이용 시작 이상이면 거부 |
| 3 | 현재가 이용 시작과 같거나 뒤면 거부 |
| 4 | 예약 생성 후 10분 이내 정정 허용, 정확히 10분 포함 |
| 5 | 일반 취소는 이용 시작 24시간 전까지 허용, 마감 순간 포함 |
| 6 | 일반 마감 날짜가 휴무일이면 직전 영업일 18시로 조정 |

정기 휴무는 금·토·일, 추가 실험용 휴일은 2026년 11월 10일과 12월 24일이다. 휴무는 일반 마감 계산에 적용한다. 이미 시작한 예약의 거부가 10분 정정보다 우선한다. 10유형 각 10문항이며 허용 45개, 거부 55개다. 무조건 거부하는 함수도 55점을 얻으므로 점수의 기준을 함께 읽어야 한다. 정답 구현의 100/100은 평가기 확인용 결과다. [S02, S05]

### 6.2 예약·대기열·자원 배정 150세트

함수 계약은 `simulate(initial_state, events)`다. 좌석·노트북·프로젝터 등 한정된 자원에 대해 예약, 대기, 취소, 변경, 수량 변경을 순서대로 처리한다. 상태 하나의 참·거짓을 넘어서 앞선 결정이 뒤의 사건과 알림에 영향을 주는 과제다.

15개 시나리오 계열에 변형 10개씩, 총 150세트와 1,690개 사건이 있다. 세트당 사건 수는 8~18개다. 정원 경계, 큰 그룹 건너뛰기, 우선순위와 선착순, 복수 자원 확보, 대기 취소, 반복 취소, 비선점, 예약 변경, 증설·축소, 중복 사용자·ID 재사용, 재전송·event_id 충돌, 잘못된 입력, 복합 연쇄를 평가한다.

사건별 결과, 최종 상태, 알림이 모두 맞아야 세트당 1점을 준다. 객체 키 순서는 무시하지만 배열의 순서·값·타입은 비교한다. 내부 모든 중간 상태의 불변조건을 직접 측정한 점수는 아니다. 150개는 서로 다른 문제 유형 150개가 아니라 15개 계열의 변형이다. [S02, S06]

### 6.3 로컬 비교용 기본 예약 취소 40문항

로컬 모델에서는 날짜 파싱 부담을 줄이기 위해 `allow_cancel(age_seconds, until_start_seconds)`를 사용했다. 첫 값은 예약 후 경과 시간, 두 번째 값은 이용 시작까지 남은 시간이며 단위는 초다. 두 번째가 0이면 시작 순간, 음수이면 시작 후다. 공통 어댑터가 원래 날짜 입력을 정수 초로 바꾼다.

평일 마감, 마감 경계, 예약 직후 유예, 시작과 유예 우선순위에 각 10개씩 있다. 휴무 달력은 이 기본 비교에서 제외됐다. 허용과 거부가 20개씩이므로 일괄 허용이나 거부도 20점을 얻는다. 40점과 100점, 자원 배정 150점을 직접 같은 난도로 비교할 수 없다.

부분정보 안내에는 24시간 일반 마감과 별도 정정 시간이 있다는 사실이 나오지만, 정정 길이·끝점·충돌 우선순위가 충분히 주어지지 않는다. 완전정보 조건은 전체 운영 명세를 주고, 인간 개입 조건은 실제 질문한 정책의 자연어 답을 준다. 이 차이가 질문 효과를 측정하는 핵심이다. [S07, S08]

### 6.4 같은 정책의 추가 56개 입력

일부 A·B·C·D 실험은 예약 경과 시간 8개와 시작까지 남은 시간 7개의 조합, 총 56쌍도 평가했다. 기존 40문항과 공개 검사에 없는 입력 쌍을 사용했다. 이는 같은 정책에서 입력 범위가 달라질 때의 성능이다. 새 도메인이나 새로운 서비스 정책에서의 일반화 검증으로 해석할 수 없다. [S15-S19]

### 6.5 범용화 시도의 추가 과제

현재 추가한 문의 배정은 소문자 태그 목록을 담당 팀 이름 하나로 바꾸는 `triage(tags)`이며 16문항이다. 태그가 겹칠 때 우선순위, 미지의 태그, 기본 동작의 정책을 물어야 한다. 표시 태그 병합은 `merge_labels(base, incoming)`이며 16문항이다. 공백 제거, 대소문자 등 같은 태그의 판별, 중복 표기와 표시 순서가 쟁점이다.

자바스크립트의 두 파일로 된 문자열 표식 예제도 공개 작업 파일로 확인된다. 그러나 기준 시각의 완료된 성능 비교는 확인되지 않았다. 파일이 존재하는 과제와 실제 비교가 끝난 과제를 구분한다. [S23]

### 7.1 90점의 원인

감시자가 추가 휴일을 물었지만 사람은 ‘없다’고 답했다. 고정 채점 정책에는 추가 휴일 두 날짜가 있었다. 추가 휴일 유형과 연속 휴무 유형에서 각각 5개를 틀렸고 다른 8유형은 모두 맞혔다. 실행 오류는 0개였다. 2차 미팅 자료는 이 실행을 의도적인 거짓 답변 조건으로 표시한다. 이 손실은 질문하지 않은 문제와 구분해야 한다. 사람의 답과 채점 정책이 달랐기 때문이다.

다음 100점 실행은 별도 세션이며 정책 전체와 휴일 목록을 두 답변으로 받았다. 90점에서 100점으로 오른 하나의 통제된 반복 실험처럼 기록하면 안 된다. 자원 배정의 150점 실행은 인간 결정 9개를 받고 코드 v10에서 완료했으며, 복잡한 상태 전이까지 전체 실행 경로가 작동한다는 파일럿 근거다.

### 7.2 발견한 운영 결함과 수정

## 8. 발표와 멘토 피드백이 바꾼 비교 방향

11월 10일에는 구현과 10건의 파일럿을 MD와 14장 발표자료로 정리했다. 실제 웹 화면, 파이프라인, 질문·답변·오류 상태를 추가했고 슬라이드별 해설과 통합 대본을 만들었다. 2차 미팅 자료는 실행 환경이 마련됐다는 점과 단일 AI보다 정확하거나 효율적인지는 아직 검증해야 한다는 점을 함께 제시했다. [S02-S04]

멘토 피드백의 첫 문제는 천장효과였다. 90~100%에 몰린 점수에서는 페르소나 차이와 감시자 효과를 보기가 어렵다. 메인 혼자 때때로 실패하는 조건을 확보해야 한다. 사용자는 목표를 60%에 맞추기 위해 사후적으로 과제를 조정하는 데 매몰되지 말라고 명시했다. 실제 얻은 성능과 오류 구조를 기준으로 비교하기로 했다.

또한 같은 호출 수로 간단한 자체 검토가 같은 누락을 찾을 수 있는지를 먼저 비교하라는 지적이 있었다. 모델 수, 관점 다양성, 추가 호출을 한 번에 바꾸면 원인을 분리하기 어렵다. 사람의 답변이 매번 달라지면 사람도 추가 변인이 된다. 질문 포착·반영·부담·시간·토큰을 함께 기록하고, 반복 실행의 변동보다 작은 차이를 어떻게 해석할지 검토해야 한다. 이 원칙들이 이후 로컬 기준선과 자체 검토 대조군의 배경이다. [S03]

## 9. 로컬 모델 파일럿: 먼저 실패의 종류를 분리하다

### 9.1 실행 환경과 입력 단순화

11월 25일에는 로컬의 작은 모델로 기준선을 만들었다. 기록상 환경은 Apple M5 Pro, 메모리 24GB, macOS 26.5.1이며 llama.cpp b12706과 Q4_K_M 양자화를 사용했다. 기본 설정은 문맥 8,192, 슬롯 1개, temperature 0.3, top_p 0.9, top_k 40이다. 최초 비교 시드는 17·29·43이었다. 질문 출력 예산은 450토큰, 코드 출력 예산은 1,500토큰이었으며 생각 토큰도 출력 한도를 소비했다. 이는 당시 실행 설정이며 장비나 모델을 지금 다시 측정한 값은 아니다. [S07]

처음에는 ISO 날짜·시각을 입력했다. 1.5B 모델은 함수 형식, 날짜 파싱, 시간대 처리에서 대부분 실패했다. 정책을 추론하기 전에 기본 실행이 막혀 감시 효과를 보기 어려웠다. 그래서 핵심 정책을 유지한 채 `age_seconds`와 `until_start_seconds`로 입력을 단순화했다. 전자는 예약 생성 뒤 경과 시간, 후자는 이용 시작까지 남은 시간이다. 음수·0·양수의 의미와 단위를 명시해 날짜 변환 부담을 분리했다.

이 전환은 성능을 올린 중요한 변경이다. 그러나 입력 표현도 바뀌었으므로 날짜형 100문항 실험과 초 단위 40문항의 점수를 직접 비교할 수 없다. 작은 모델의 정책 오류를 관찰하기 위한 실험 환경의 변경으로 읽어야 한다.

자원 배정 150세트에서는 완전한 정보를 줘도 Qwen3 단독이 세 시드 합계 0/450이었다. 참조 구현은 150/150이었다. 긴 상태 전이와 엄격한 출력 일치가 필요한 과제에서는 기본 구현 능력이 부족했다. 예약 취소에서 높은 점수를 낸 모델이라고 모든 업무에 적당한 기준선 모델이라고 단정할 수 없었다.

## 10. 첫 A·B·C 비교: 자체 검토와 독립 감시

### 10.1 이때의 A·B·C는 실험 조건 이름이다

이 실험의 A는 단독 초안, B는 자체 검토, C는 독립 감시 조건이다. 이후 A·B·C라는 감시자 이름과 구분해야 한다. 3모델 × 3시드로 만든 9개 초안을 공유하고 추가 검토의 효과를 비교했다. 초안은 질문과 코드의 2회 호출로 만들었다. B와 C는 검토 3회와 최종 수정 1회를 더해 총 6회 호출이었다. [S09]

```text
공통: 공개 요구 → 질문 → 담당자 답 → 메인 초안
  A 조건: 초안을 그대로 평가
  B 조건: 같은 메인의 관점 1 → 관점 2 → 관점 3 → 메인 수정
          뒤 관점은 앞 관점의 내용을 볼 수 있음
  C 조건: 감시 1 / 감시 2 / 감시 3 → 의견 수집 → 메인 수정
          같은 회차의 감시자들은 동료 응답을 보지 않음
연구자: 각 산출물을 공통 문항으로 비교
```

### 10.2 결과와 실제 질문의 정보량

| 모델 | A 단독 / 120 | B 자체 검토 / 120 | C 독립 감시 / 120 |
|---|---:|---:|---:|
| 7B | 79 | 79 | 79 |
| 14B | 69 | 69 | 74 |
| Qwen3 | 98 | 98 | 98 |
| 합계 / 360 | 246 | 246 | 251 |

C의 총 개선은 5문항이었다. 14B 시드 43에서 틀리던 10문항을 고쳤지만 맞던 5문항을 잃어 순증가가 5였다. 7B는 오래된 예약이 48시간 전에 취소 가능한 경우까지 막는 문제를 검토 뒤에도 유지했다. 감시가 코드 수정을 유발해도 전체 정책을 보존하는 것은 별개였다.

B에서는 형식상 질문이 18개, C에서는 6개였지만, 각 조건에서 초안 이후 남아 있던 미확인 정책 항목의 합계 17건 가운데 새로 확보한 것은 1건이었다. 이 17건은 서로 다른 정책 17종이 아니라 여러 초안에서 남은 미확인 항목을 합한 수다. 질문 수와 정보 획득량은 같은 지표가 아니다. 앞선 감시자 사례 생성 보조 실험의 제안 52개 중 유효한 것은 43개였고, 기대값이 잘못된 제안 16개가 있었다. 실제 결함을 정확히 겨냥한 제안은 3개였다. 검토자가 만든 사례라고 곧바로 정답 기준으로 쓰면 안 된다는 근거가 됐다.

| 모델 | B 평균 토큰 | C 평균 토큰 | B 기록 시간 | C 기록 시간 |
|---|---:|---:|---:|---:|
| 7B | 5,223.7 | 4,278.7 | 19.06초 | 14.90초 |
| 14B | 6,012.7 | 4,938.0 | 61.40초 | 50.57초 |
| Qwen3 | 6,745.7 | 6,115.7 | 39.12초 | 41.75초 |

전체 고유 모델 호출은 90회, 토큰은 90,199개, 실험 경과 시간은 약 607초로 기록됐다. 이 결과는 감시자의 보편적 우위를 입증하기보다, 추가 검토가 대부분 같은 판단을 반복하고 일부 수정에서 회귀가 발생한다는 초기 진단이다.

## 11. 완료 판정과 전달 경로를 고치다

### 11.1 내용이 전달됐는가와 정말 끝났는가는 다른 문제

검토자가 지적한 내용이 메인에게 전달되지 않거나, 검사 목록이 비어 있는데 0/0을 성공으로 취급하는 문제가 발견됐다. 완료 게이트의 재생에서는 검사 0개를 ‘전부 통과’로 처리하던 경로를 확인하고 미검증 상태로 멈추도록 바꿨다. 이것은 특정 상태 전이의 결함을 재현한 검사이지, 실서비스 전체에서 그 오류가 얼마나 자주 발생했는지 측정한 값은 아니다. [S10, S11]

전달 실험에서는 Qwen3의 39/40 코드에 실패 결과를 일반적인 목록으로 제시하며 5번 수정해도 39가 유지됐다. 담당자의 원문, 해당 입력의 실제 결과, 기대 결과를 연결해 주자 다음 수정에서 40이 됐다. 전달을 구체화하면 고칠 수 있는 오류가 존재했다. 다만 실제·기대 결과를 중간에 모델에게 보인 이 방식은 이후 확정된 ‘중간 채점 정보 금지’ 조건과 다르다. 현재 연구의 유효 성능 증거로 재사용할 수 없다.

앞선 확정 규칙의 사례 실행 보조 실험은 일반 감시에서 나온 초안·의견·답을 고정하고 마지막 수정에 사람의 기대값과 실제 결과를 더했다. 7B는 일반 감시 79에서 70/120으로 내려갔고, 14B는 74에서 79/120으로 올랐으며, Qwen3는 98/120을 유지했다. 공개 검사를 모두 통과한 두 코드도 전체 평가에서는 29/40과 39/40이었다. 공개 사례와 평가 입력이 겹친 네 문항을 제외해도 변화 방향은 같았다. [S10]

완료 게이트를 적용한 별도 비교는 이 보조 실험의 최종 코드인 70·79·98/120에서 시작했다. 일반 재검토 대조군과 실패 사례 피드백 조건의 최종 합계는 각각 7B 70 대 74, 14B 74 대 74, Qwen3 98 대 99였다. Qwen3 시드 43은 네 번째 추가 수정에서 시작 정각을 고쳤다. 이 결과와 앞 문단의 ‘답 옆에 실행 근거를 붙여 1회 만에 고친’ 전달 실험은 다른 실행이다.

완료 게이트 비교의 추가 호출·토큰은 대조군/피드백 순으로 7B 15회·23,145개 / 15회·29,580개, 14B 10회·20,866개 / 10회·25,185개, Qwen3 10회·25,850개 / 9회·28,732개였다. 공개 사례와 겹친 세 평가 문항을 빼면 Qwen3 두 조건은 모두 92/111이었다. 별도 미노출 입력 9개에서는 대조군 6/9, 수정 코드 9/9여서 정각 규칙의 수정은 다른 입력에도 적용됐다. 다른 정책까지 개선됐다는 근거는 아니다. 이 일련의 실행 피드백 방식은 현재의 중간 채점 비노출 조건과 구분한다. [S11]

### 11.2 실패를 보고 최대 5번 더 고친 재벤치마킹

확인된 사례 실패가 있으면 최대 5번 추가 수정하고 원문 피드백을 모두 보존하는 재벤치마킹을 진행했다. 54쌍의 전달 내용이 기록됐다. 이 실험 역시 중간 실행 결과를 사용한 역사적 디버깅 실험으로 분류한다. [S12]

| 조건 | 최초 / 360 | 추가 수정 후 / 360 | 추가 수정 호출 |
|---|---:|---:|---:|
| A 단독 | 246 | 246 | 0 |
| B 자체 검토 | 246 | 247 | 11 |
| C 독립 감시 | 251 | 246 | 20 |

B는 한 문항을 고쳤고 기존 정답 손실은 없었다. C는 틀린 15개를 고치면서 맞던 15개를 잃었다. C의 최초 결과보다 최종 합계가 낮아진 것은 비교 기준이 A인지 C의 최초 수정본인지에 따라 증감이 달라짐도 보여 준다. Qwen3 시드 43에서는 이용 시작 순간을 고치다가 일반 마감 뒤 분기에 항상 참인 `until_start_seconds < 0 or until_start_seconds >= 0`을 넣었다. 이 분기가 정당한 정정도 거부해 39에서 30으로 내려갔다.

전체 121회 호출, 160,866토큰, 경과 1,143.1초였다. 조건별 평균은 A 약 1,083토큰·10.8초, B 8,689토큰·59.7초, C 10,267토큰·72.4초였다. 더 많은 수정 기회와 더 자세한 피드백이 성능을 단조 증가시키지 않았다. 이후에는 잘못된 부분을 고칠 때 이미 맞던 부분을 얼마나 잃는지 따로 기록하게 됐다.

## 12. 3사이클 실험: 반복 자체가 도움이 되는가

이번에는 중간 실행 결과를 주지 않고, 초안에 대해 A·B·C가 독립 검토하고 D가 통합한 뒤 메인이 수정하는 사이클을 세 번 돌렸다. 사람에게 정책을 새로 묻는 과정은 없었다. 매 사이클 5회 호출이 추가되므로 누적 호출은 초안 1회, 1사이클 후 6회, 2사이클 후 11회, 3사이클 후 16회다. [S13]

```text
공개 정보 → 초안
  → A·B·C 독립 검토 → D 통합 → 메인 수정 1
  → A·B·C 독립 검토 → D 통합 → 메인 수정 2
  → A·B·C 독립 검토 → D 통합 → 메인 수정 3
연구자 평가: 저장된 각 버전의 변화 확인
```

| 시드 | 초안 | 1사이클 | 2사이클 | 3사이클 |
|---|---:|---:|---:|---:|
| 17 | 25 | 35 | 35 | 35 |
| 29 | 30 | 30 | 30 | 30 |
| 43 | 30 | 30 | 30 | 30 |
| 합계 / 120 | 85 | 95 | 95 | 95 |

평균 누적 토큰은 559 → 5,470 → 10,980 → 16,374, 기록 시간은 10.5 → 50.5 → 91.2 → 129.6초였다. 고유 호출 48회, 49,122토큰, 약 388.68초가 들었다. 뒤의 두 사이클은 32,712토큰을 쓰고도 평가 입력의 반환을 바꾸지 않았다.

시드 17은 15개를 고치고 5개를 잃었다. 그런데 담당자에게 묻지 않고 정정 기간을 10분으로 정했으며, 끝점도 `<`로 구현했다. 점수의 상승과 정보의 정당한 획득을 분리해야 한다. 같은 예산의 자체 검토 대조군도 없어 이 +10을 독립 감시만의 효과로 단정할 수 없다. 사용자가 원한 인간 개입 연구에서 벗어난 부분이 이때 이미 있었다.

## 13. D 통합자 진단: 요약이 문제인지 코드 추적이 문제인지

### 13.1 같은 의견을 다른 형태로 전달한 재생

D가 감시자 의견을 요약하면서 근거를 잃는지 확인하기 위해 시드 29의 2사이클 코드와 시드 43의 3사이클 코드를 골랐다. 같은 원본 코드와 A·B·C 원문을 주되, 한쪽은 일반 요약, 다른 쪽은 코드 추적을 강조했다. 두 방식 모두 합계 60/80에서 64/80이 됐다. [S14]

시드 29는 30에서 34로 올랐지만 이용 시작까지 1시간 미만이면 허용하는 새로운 정책을 만들었다. 5개를 고치고 1개를 잃었으며, 정정 조건의 예약 경과 시간을 빠뜨렸다. 시드 43은 30을 유지했다. 요약 방식은 5,753토큰·22.52초, 추적 방식은 6,950토큰·34.60초였다. 추적 지시를 늘린 비용이 두 사례의 점수 차이로 이어지지 않았다.

### 13.2 말로 지적한 위치와 실제 동작의 차이

별도 의견 진단은 두 코드, 세 시드, 두 표현 방식으로 12회 호출했다. 입력 세 개씩에 대한 반환값 추정은 양쪽 모두 9/18개가 맞았다. 실행 줄과 값을 함께 맞힌 것은 0/18 대 2/18이었다. 특정 줄을 삭제해도 결과가 바뀌지 않는다는 답은 6/6 맞혔으나 그 이유를 올바르게 설명한 것은 양쪽 모두 0/6이었다. 실제 첫 반환문은 21행인데 마지막 34행을 원인으로 지목한 사례가 있었다.

토큰은 6,452 대 8,854, 시간은 20.09 대 24.03초였다. 18쌍의 최종 예측은 동일했다. 이 실험은 작은 표본에서 D가 제어 흐름과 정책 근거를 정확하게 연결하지 못했음을 보여 준다. 모든 모델이나 모든 코드에 대한 한계로 일반화할 근거는 아니다.

## 14. 실행 근거와 후보 선택: 개선됐지만 철회해야 한 결과

### 14.1 실행 표를 주고 수정한 verified A·B·C·D

실제 실행 근거를 붙이면 추적 오류가 줄어드는지 보기 위해 공개 사례의 기대값·실제값 표를 모델에게 전달했다. 수정본이 기존 확인 사례를 보존하고 적어도 하나 개선하면 채택하는 선택 규칙도 사용했다. 시드는 17·29·43·71·89·113이었다. [S15]

다음에는 A·B·C가 같은 초안에서 독립적으로 전체 함수를 만들고, 통과 수가 가장 높은 후보들 중 D가 선택하게 했다. 원본을 보존하고 필요하면 새 후보를 최대 한 번 더 만들었다. 새 시드는 131·157·191·223·257·293이었다. [S16]

### 14.3 왜 이 개선 주장을 철회했는가

설정에 `score_feedback: false`라고 적혀 있어도 실제 모델 입력에 공개 검사 기대값, 실제값, 통과 여부가 들어갔다. ‘숨은 최종 점수는 안 보였다’는 의미와 ‘파이프라인 중 모델이 가채점 결과를 모른다’는 사용자의 규정은 달랐다. 후보 선택과 종료 판단에도 검사 결과가 쓰였다. 따라서 앞의 상승폭은 현재 연구 조건을 만족하는 결과에서 제외해야 한다.

사용자는 이 부분을 직접 지적했고, 이후 연구자와 모델의 정보 경계를 다시 설정했다. 연구자는 버전별 과정을 관찰하고 다음 실험의 구조를 개선할 수 있다. 실행 중인 메인·감시자·D는 중간 점수나 실패 문항, 점수 기반 선택 신호를 받지 않는다. 사람 역할이 제공하는 내용도 질문에 대한 정책 자연어로 한정한다. 이 구분이 이후 모든 결과의 유효성을 판단하는 기준이다.

## 15. 중간 결과를 제거한 blind 재실험

앞 실험의 새 6시드 초안을 그대로 쓰고 실행 결과를 입력에서 제거했다. 후보는 원본 소스만 검토하며 D는 전체 코드 중 하나를 선택한다. 예산은 고정하고, 연구자가 점수가 높은 중간 버전을 골라 제출하지 않도록 했다. [S17]

| 구조 | 기본 / 240 | 추가 / 336 | 호출 수 | 토큰 |
|---|---:|---:|---:|---:|
| 직접 작성 | 169 | 256 | 6 | 3,550 |
| 짧은 검토 | 169 | 256 | 12 | 8,894 |
| 순차 자체 수정 | 169 | 256 | 30 | 34,216 |
| A·B·C·D | 169 | 256 | 30 | 30,278 |

모든 조건이 6 × (40+56) = 576개 입력에서 같은 반환을 냈다. 원본과 A를 공유했으므로 실제 고유 호출은 48회, 제출 산출물은 24개였다. C 후보 하나가 출력 한도에 걸렸고 D는 A를 선택했다. 실행 근거를 제거하자 앞서 보인 상승은 재현되지 않았다.

이 결과는 ‘멀티 구조는 항상 무의미하다’는 결론이 아니다. 선택된 모델·프롬프트·예산 아래에서 실행 피드백 없이 후보를 늘리는 것만으로는 잘못된 정책을 수정하지 못했다는 결과다. 아직 사람에게 누락된 정책을 묻는 핵심 장치는 복원되지 않았다.

## 16. 수정 반영을 강화한 순차 구조

### 16.1 전체 규칙표를 다시 만드는 방식

병렬 처리보다 수정 반영을 우선해 역할들을 순차로 연결했다. A는 코드 초안 없이 요구사항을 정리하고, B는 전체 규칙표를 다시 쓰며, C와 D는 유지 또는 교체했다. 자체 검토와 A·B·C·D 모두 5회 호출이었다. 기존 6시드에 307·331·353·379·401·419를 더해 12시드로 비교했다. [S18]

| 구조 | 기본 / 480 | 추가 / 672 |
|---|---:|---:|
| 직접 작성 | 343 | 512 |
| 전체 규칙표, 자체 검토 | 245 | 442 |
| 전체 규칙표, A·B·C·D | 273 | 480 |

A·B·C·D의 B 단계는 260/480·464/672, C 단계는 273/480·480/672, D 단계는 그대로였다. C는 기본 25개를 고치고 12개를 잃었다. 전체를 재작성하면서 24시간을 24초로 바꾸는 단위 오류가 생겼다. 충분한 지적이 전달되는 것과 기존 정책을 보존하면서 구현하는 것은 다른 문제였다.

### 16.2 원본의 반환 지점을 보존하는 방식

다음에는 원래 함수의 반환 위치를 보존하고 조건을 삽입하도록 바꿨다. 단위도 공개 원문에서 가져오게 했다. 같은 초안과 A 분석을 사용해 전체 재작성의 부작용을 줄이려 했다.

| 구조 | 기본 / 480 | 추가 / 672 |
|---|---:|---:|
| 직접 작성 | 343 | 512 |
| 원본 보존, 자체 검토 | 338 | 476 |
| 원본 보존, A·B·C·D | 344 | 441 |

A·B·C·D는 B에서 이미 344·441이 됐고 C·D의 실제 반환은 바뀌지 않았다. B는 12개 모두 코드를 바꿨고 C는 1개, D는 0개를 바꿨지만 기능 변화는 B 이후 없었다. 예약 경과 시간에 반응하는 코드는 초안 0/12에서 10/12로 늘었으나 그 사실만으로 정책이 맞아진 것은 아니었다. D는 시드 131에서 24시간을 정정 유예로 쓰기도 했다. A가 정보가 없다고 인지해도 이후 작성자가 빈칸을 채워 버릴 수 있었다.

## 17. 시간 기준 최종 검토: 개선과 목표 이탈을 함께 확인하다

양쪽 5회 호출 구조 뒤에 공개된 시간 기준을 대조하는 마지막 검토를 추가했다. 단위를 통일하고 비교 방향을 확인하게 했다. 최종 검토 24건은 모두 시간 변환을 올바르게 기록했다. [S19]

| 구조 | 기본 / 480 | 추가 / 672 | 토큰 |
|---|---:|---:|---:|
| 직접 작성 | 343 | 512 | 7,136 |
| 자체 검토 5회 | 338 | 476 | 86,868 |
| A·B·C·D 5회 | 344 | 441 | 81,402 |
| 자체 검토 6회 | 409 | 572 | 102,065 |
| A·B·C·D 6회 | 411 | 583 | 97,561 |

기본 점수에서 A·B·C·D 6회는 직접 작성보다 +68이었다. 106개를 고치고 38개를 잃었다. 그러나 같은 6회 자체 검토와 비교하면 33개를 고치고 31개를 잃은 +2였다. 이전 6시드는 자체 검토 207, A·B·C·D 196으로 멀티가 11개 낮았고, 추가 6시드는 202 대 215로 13개 높았다. 기본 시드별 승무패는 4승 2무 6패, 추가 문항은 5승 2무 5패였다. 합계의 작은 차이만으로 안정적 우위를 말하기 어렵다.

검사 결과가 모델에 들어가지 않았는지 시간 경계도 확인했다. 원본 산출물 72개는 01:42:55에 봉인됐고, 최종 모델 응답은 01:45:31.586, 최종 산출물 60개 봉인은 01:45:31.587, 첫 채점은 01:45:31.909였다. 모델 서버를 중지한 뒤 평가했다는 실행 기록이 있다. 전체 기반 호출은 132건이다. 이는 앞의 후보 선택 실험보다 채점 분리가 명확한 결과다.

그럼에도 이 구조의 인간 개입은 0회였고, 반복 검토 사이클도 0회였다. 12개 시드는 서로 다른 실행이며 한 프로젝트를 12번 검토한 것이 아니다. 시드 131은 정정 기간을 5분, 353은 1시간으로 가정했고 다른 코드들은 10분을 가정했다. 사용자는 01시 54분경 ‘우리 목표는 그게 아니다’라고 바로잡았다. 핵심은 공개 정보의 수치 정규화만 잘하는 것이 아니라 모르는 정책을 사람에게 물어 더 적합한 코드를 만드는 것이다.

## 18. 인간 개입을 다시 중심에 놓은 실험

### 18.1 공동 답변에서 조건별 질문·답변으로

처음 복원한 인간 개입 비교는 동일한 답을 양쪽에 제공해 24 → 30 → 30을 얻었다. 그러나 한쪽이 잘 물은 결과를 다른 쪽에도 공유하면 질문 능력의 차이가 사라진다. 이후 각 조건이 실제로 물은 내용에만 답하고 상대 조건의 답을 공유하지 않는 방식으로 바꿨다. [S20]

담당자 역할은 사용자의 요청에 따라 자동 대리했다. 이미 정해진 정책 카드에서 질문 범위에 맞는 내용을 평소 말로 답했다. 실제 사람이 실험 중 직접 입력한 답과 같다고 표시하지 않는다. 이때 모델은 정책 카드 전체를 보지 않고 답변 원문만 받는다. 연구자 역할은 전체 정책을 가지고 사후 평가할 수 있다.

### 18.2 당시 비교 실행기의 정보 흐름

같은 첫 코드에서 출발하고 최대 6버전·24회 호출을 허용했다. 메인 예산은 2,200, 검토자는 850토큰이었다. 단일은 같은 메인의 세 관점을 순차로 점검하고, 멀티는 세 감시자가 독립적으로 점검했다. 이 예비 실험에서는 멀티의 메인도 질문할 수 있었다.

```text
공개 요구 + 공통 초안
  → 단일: 메인 자체 점검 3관점
  → 멀티: 감시자 3명의 독립 점검
  → 실제로 제출한 질문을 조건별로 모음
  → 담당자 대리: 질문한 정책만 자연어로 답함
  → 메인: 이전 계획·코드 + 자기 조건의 답 원문으로 수정
  → 새 버전을 다시 검토
  → 충분하면 제출, 한도에 닿으면 미완료 상태 기록
연구자 별도 경로: 버전·질문·답·코드를 보존하고 평가
```

검토자는 실제 코드와 계획, 받은 답을 본다. 메인은 검토자의 숨은 판단 근거나 채점 결과를 받지 않고, 본인의 이전 산출물과 담당자의 원문을 받도록 제한했다. 이 때문에 감시자가 오류를 알아도 질문·답변 경로로 필요한 정보가 전달되지 않으면 수정되지 않을 수 있다. 질문의 포착과 코드 반영을 따로 측정할 필요가 생겼다.

정책 결정은 일반 취소의 24시간 끝점, 정정 기간 길이, 정정 기간 끝점, 일반 마감 뒤 정정 허용 여부, 이용 시작 순간의 처리, 이용 시작 뒤 처리의 6개로 관리했다. 입력 범위나 함수 인터페이스 문의와 정책 문의를 구분했다.

### 18.3 자유 질문·고정 가이드·순서 있는 규칙표

| 방식 | 바꾼 부분 | 확인하려던 것 |
|---|---|---|
| 자유 질문 | 모델이 부족한 내용을 직접 찾음 | 실제 질문 발견 능력 |
| 가이드 검토 | 연구자가 공개 정보에서 만든 6개 질문 관점을 제공 | 질문 누락이 성능의 병목인지 |
| 코드 근거 검토 | 문제 지적에 코드 위치와 답의 근거를 연결 | 설명만 하고 구현을 놓치는지 |
| 순서 있는 규칙표 | 조건과 행동을 순서대로 적어 코드화 | 조건 충돌·우선순위·누락을 줄일 수 있는지 |

시드 131의 자유 질문과 가이드 결과는 양쪽 모두 정답 24, 오답 1, 미판정 15였다. 여기서 ‘25개 반환’은 정답 25개라는 뜻이 아니다. 순서 있는 규칙표에서는 두 조건 모두 14 → 20 → 29 → 35 → 35 → 35였다. 최종 35정답·5오답이며 전부 반환했다. 자유 질문 대비 11개 정답이 늘었지만 맞던 4개를 잃고 15개를 새로 맞혔다. 정정 10분을 10초로 옮긴 문제와 모순된 조건 결합을 고쳤으나 이용 시작 우선순위는 남았다.

시드 157의 초기 대리 답변 방식에서는 자유 질문 단일 20정답·5오답·15미판정, 멀티 20정답·0오답·20미판정이었다. 가이드는 양쪽 모두 25정답·0오답·15미판정이었다. 순서 있는 규칙표는 단일 20정답·1오답·19미판정, 멀티 14정답·1오답·25미판정이었다. 시드 131에서 유리했던 양식이 다른 시드에서는 같은 개선을 보장하지 않았다.

## 19. 담당자 대리의 과잉 답변을 바로잡다

### 19.1 질문에 언급됐다는 것과 물었다는 것은 다르다

질문의 배경 설명에 일반 마감과 정정 기간이 등장했지만 실제 의문문은 숫자 입력 범위만 묻는 경우가 있었다. 대리 답변기가 배경의 단어를 보고 ‘일반 마감 뒤에도 정정 가능’ 정책을 제공했다. 모델이 획득하지 않은 정보를 자동 제공한 셈이었다. 질문 능력을 비교하는 실험에서는 큰 교란이다. [S20]

의문문에 해당하는 부분을 우선 판독하고, 확인 요청을 정책 확정 근거로 다시 인용하지 않도록 고쳤다. 이전 답변은 덮어쓰지 않고 초기 프로토콜 결과로 남겼다. 이 정정 전후의 점수는 담당자 역할의 정보 제공량도 달라졌으므로 단순한 코드 개선량으로 비교하면 안 된다.

### 19.2 엄격한 답변 범위에서 확인한 감시자의 기여

| 시드 157, 엄격한 대리 답변 | 정답 | 오답 | 미판정 | 획득 정책 / 6 | 질문 수 | 답변 묶음 |
|---|---:|---:|---:|---:|---:|---:|
| 자유 질문 단일 | 15 | 0 | 25 | 1 | 11 | 1 |
| 자유 질문 멀티 | 20 | 0 | 20 | 3 | 15 | 4 |
| 순서 규칙표 단일 | 25 | 15 | 0 | 6 | 19 | 2 |
| 순서 규칙표 멀티 | 25 | 15 | 0 | 6 | 19 | 1 |

자유 질문 멀티에서는 감시자 1이 2번째 검토에서 정정 끝점을 묻고, 다음 검토에서 기간 길이를 물었다. 답변에서 10분을 받은 뒤 4번째 코드에 600초가 들어가 5개를 새로 맞혔고 기존 정답 손실은 없었다. 단일은 같은 정책을 얻지 못했다. 이 사례는 ‘독립 감시자의 질문 → 담당자 정보 → 코드 반영 → 정답 증가’ 경로를 실제 기록에서 연결할 수 있는 사례다.

다만 끝점을 포함한다는 답을 받았는데도 `<600`을 써 경계 반영은 실패했다. 규칙표 조건에서는 6개 정책을 모두 획득하고도 25정답·15오답이었다. 사람에게 답을 모두 들었다고 올바른 코드가 완성되는 것은 아니다. 누락 발견, 질문, 답 해석, 조건 변환, 우선순위 구현의 병목이 서로 다르다.

이 인간 개입 묶음에는 초기 6개와 엄격 답변 2개를 합친 8개 실행 폴더, 376개의 호출 기록, 41개 답변 묶음이 남았다. 16개 조건 모두 6버전 한도에서 공식 제출 없이 끝났다. 기록 수에는 재사용 자료가 들어갈 수 있어 이후 실험의 호출 수와 무조건 합산하지 않는다. 35점이나 25점은 이 미완료 버전의 연구자 측 측정값이다.

## 20. 시간 조건 개선: 자연어 답이 코드로 바뀌는 마지막 손실

### 20.1 기준선을 고정한 이유

다음 개선은 만점을 목표로 규칙을 정답에 맞춰 하드코딩하는 것이 아니라, 이미 확보한 자연어 정책이 코드에서 잘못 변환되는 원인을 줄이려는 것이었다. 기존 인간 개입 보고서와 비교 JSON의 SHA-256을 보존했다. 기존 자유 질문은 기본값으로 유지하고 새로운 모드는 실험 옵션으로 추가했다. [S21, S22]

`source_thresholds.py`는 공개 요구와 해당 조건이 실제로 받은 답에서 시간 표현을 수집한다. 같은 시간 기준인지 확인하고 분을 초로 바꾸며, 포함 여부는 원문 근거가 있을 때만 정한다. 값이 빠지거나 충돌하면 의존하는 경로를 보류한다. 숨은 채점기나 담당자 정책 카드에서 값을 가져오지 않는다. 원래 작성자가 정한 규칙 순서·행동·기본 반환은 별도 대상이다.

예를 들어 7분이라는 반사실 정책으로 419·420·421초를 점검했다. 끝점 포함·제외·미정, 상충 답변, 복합 표현, 소수·쉼표 숫자, 서로 다른 조건 간 정보 혼입도 점검했다. 이 검사는 특정한 10분 정답을 외워서 올리는 장치인지, 원문에 따라 다른 값도 처리하는지를 구분한다.

### 20.2 첫 시도: 원문 시간 양식을 작성자에게 요구

첫 변형은 작성자 출력 양식에 원문 시간 근거를 포함하게 했다. 같은 첫 질문과 답, 같은 수정 예산으로 비교했지만, 양식 변경이 규칙 전체 재작성을 유발했다.

| 조건 | 기존: 정답/오답/미판정 | 첫 변형: 정답/오답/미판정 |
|---|---|---|
| 157 단일 | 25 / 15 / 0 | 25 / 9 / 6 |
| 157 멀티 | 25 / 15 / 0 | 25 / 9 / 6 |
| 263 단일 | 24 / 16 / 0 | 20 / 5 / 15 |
| 263 멀티 | 25 / 15 / 0 | 16 / 24 / 0 |

157에서는 오답 5개를 고치면서 기존 정답 5개를 잃었고, 오답 6개가 미판정으로 바뀌었다. 263 단일은 기존 정답 4개를 오답으로 바꿨다. 263 멀티는 오답 11개를 고쳤지만 정답 20개를 잃었다. `until_start_seconds <= 86400`과 `age_seconds <= 600`을 합친 규칙이 이미 시작한 예약도 허용하는 식으로 변했다.

버전별 값도 안정적이지 않았다. 157은 15 → 11 → 25 → 25 → 25 → 25, 263 단일은 14 → 35 → 35 → 5 → 20 → 20, 멀티는 14 → 16 → 20 → 16 → 35 → 16이었다. 중간 35점 버전을 연구자가 골라 최종 성과로 삼으면 모델이 볼 수 없는 점수로 선택한 결과가 된다. 최종 버전과 전체 변동을 그대로 남겼다.

### 20.3 두 번째 진단: 기존 규칙표의 시간만 사후 대조

실패 원인이 시간 근거 장치 자체인지, 새로운 양식이 작성자의 규칙을 바꿔 버린 것인지 분리했다. 저장된 원래 규칙표를 고정하고 시간 부분만 원문에 연결하는 오프라인 재생을 했다. 새 모델이 답을 보고 다시 작성한 실험과 구분해야 한다.

| 고정된 원래 규칙표 | 기존 | 시간만 연결한 재생 |
|---|---|---|
| 157 단일 | 25 / 15 / 0 | 29 / 10 / 1 |
| 157 멀티 | 25 / 15 / 0 | 29 / 10 / 1 |
| 263 단일 | 24 / 16 / 0 | 24 / 15 / 1 |
| 263 멀티 | 25 / 15 / 0 | 29 / 10 / 1 |

기존 정답이 오답이 되는 경우는 없었다. 세 조건에서는 오답 5개가 정답이 되고 정답 1개가 미판정이 됐다. 시간 부분을 제한적으로 교정하면 도움이 되지만, 전체 규칙표를 다시 만들게 하면 더 큰 회귀를 유발할 수 있다는 가설을 얻었다.

### 20.4 세 번째 시도: 같은 양식을 유지한 실제 사이클

시드 263에서 작성자 프롬프트와 출력 형태를 그대로 유지하고, 원래 작성된 규칙표의 시간 항목에만 받은 원문을 연결했다. 첫 수정 요청과 응답이 기존 조건과 바이트 단위로 같은지 확인했다. 변환 후 코드를 검토자에게 보여 주고, 다음 메인도 그 코드를 받아 실제 검토 사이클을 진행했다. 따라서 앞의 사후 재생과 달리 교정된 코드가 다음 회차 상호작용에 들어갔다.

| 실제 사이클, 시드 263 | 기존 최종 | 개선 최종 | 버전별 정답 |
|---|---|---|---|
| 단일 | 24 / 16 / 0 | 24 / 15 / 1 | 14 → 24 → 24 → 24 → 24 → 24 |
| 멀티 | 25 / 15 / 0 | 29 / 10 / 1 | 14 → 29 → 29 → 29 → 29 → 29 |

멀티는 기존 오답 5개를 정답으로 바꾸고 정답 1개를 미판정으로 바꿨다. 기존 정답을 오답으로 만든 경우는 없었다. 단일과 멀티 모두 24회 호출이었다. 단일은 53,120토큰·질문 13개·답변 2묶음, 멀티는 42,327토큰·질문 17개·답변 1묶음이었다. 기존 단일 47,989토큰, 멀티 41,808토큰과도 함께 비교해야 한다.

```text
기존: 담당자 자연어 → 메인이 숫자·부등호·순서를 모두 작성 → 코드
첫 변형: 원문 시간 양식 추가 → 규칙표 전체가 달라짐 → 회귀 발생
개선: 기존 작성 양식·규칙 순서 유지
      → 받은 원문의 시간 값·단위·끝점만 연결
      → 변환된 코드로 검토 → 다음 수정에도 같은 코드 전달
연구자: 마지막 버전과 모든 중간 버전을 별도 평가, 모델에는 미전달
```

이 묶음의 고유 실행 폴더는 5개, 호출 기록 235개, 답변 묶음 16개였다. 검토 원문·코드·답변을 입력 스키마와 함께 재생해 정보 전달을 확인했다. 실제 인간 답변은 0개이며 정책 카드를 이용한 대리 답변이었다. 최종 검토자 세 명은 여전히 수정 필요로 판단했고 실행은 `incomplete_limit`, 버전 6이었다. 29/40은 최종 제출 완료 성적이 아니다.

확인된 한계는 분명하다. 시간 변환은 나아졌지만 시작 순간과 정정의 우선순위, 이미 시작한 경우, 복합 조건의 구조는 자동으로 해결하지 않았다. 시드 263 한 개의 실제 사이클 개선이므로 범용 멀티 구조의 우위로 발표할 수 없다. `--source-thresholds`와 `--bind-authored-times`는 실험 옵션이며 자유 질문의 기본 구조를 대체한 것으로 기록하지 않는다.

## 21. 현재 진행 중인 범용화와 최신 세 조건

### 21.1 예약 전용 틀을 벗어나려는 이유

사용자는 예약 문제에서만 통하는 개선을 목표로 하지 않는다고 다시 명시했다. 따라서 정정 기간 600초나 예약 변수 이름을 공통 감시 로직에 박아 넣는 대신, 일반적인 공개 요구와 텍스트 프로젝트 파일을 검토하는 방향으로 옮겼다. 최신 요청은 불충분 정보 단독, 자체 점검 후 인간 개입, 감시자 점검 후 인간 개입의 세 조건과 토큰 공개다. [S23, S24]

`backend/project_review.py`의 공통 입력은 공개 설명과 텍스트 파일이다. 검토 관점은 누락, 겹치는 규칙의 순서, 받은 답의 반영이다. 지적은 파일·위치·근거 출처와 연결하고 ASK 또는 FIX로 분류한다. 수정은 파일과 포함 범위의 시작·끝 행, 근거 ID, 교체 내용으로 표현한다. 겹치지 않는 수정을 원자적으로 적용하고 지정하지 않은 부분을 보존한다.

예약 취소 40문항 외에 분류 업무 16문항과 라벨 관련 업무 16문항을 준비했다. 시드는 263, 메인 2,200·검토자 850토큰, 최대 6버전이다. 사람 역할과 연구자 역할은 공통 검토 코드 밖에 두고 과제별 정책 카드와 평가기를 분리한다. 새 최초 질문을 생성하므로 앞의 29점과 질문·답이 정확히 같은 대조 실험은 아니다.

### 21.2 문법과 수정 적용 문제도 별도로 발견됨

초기 범용 실행에서는 분류 과제의 4번째 버전에서 들여쓰기 오류가 생겨 두 조건 모두 16문항에 반환을 내지 못했다. 라벨 과제에서는 질문이 인용문과 섞이는 문제가 있었다. 이후 Python·JSON·JavaScript 문법 검사를 추가하고, 문자 내용이 같고 들여쓰기만 다른 경우 복원하며, 새 수정이 문법을 깨면 이전 유효 파일을 유지하도록 했다. 이는 숨은 정책 점수와 별개인 산출물 유효성 검사다.

정확히 같은 모델·역할·전체 요청만 저장 응답을 재사용하고, 하나라도 다르면 새 호출한다. 담당자 답도 질문과 제안자가 일치할 때만 재사용한다. 중복된 선언형 문장을 질문에서 제거하더라도 자동으로 제출 준비 완료를 선언하지 않는다. 초기 질문 뒤에 추가한 과제당 세 개의 근거 탐침은 사후 보조 진단이며 사전에 정한 독립 평가라고 표현하지 않는다.

### 21.3 보고서 기준 시각의 실행 상태

| 과제 | 자체 점검 조건 | 감시자 조건 | 해석 |
|---|---|---|---|
| 예약 취소 | 버전 4, awaiting_human | 버전 4, awaiting_human | 답변 처리 대기. 완료나 실패로 단정하지 않음 |

이 표는 11월 26일 10시 43분까지 확인한 상태 스냅샷이다. 별도 대화가 계속 작업 중이므로 그 뒤 완료 여부는 이 보고서에 포함하지 않는다. 해당 폴더에서 세 과제의 완결된 종합 성적표는 확인하지 못했다. JavaScript 두 파일 예시도 있지만 완성된 성능 결과로 집계하지 않았다.

현재 공통 실행기의 일부 버전은 메인도 질문을 만들 수 있다. 사용자가 새로 정한 ③의 ‘감시자 질문’만으로 엄격하게 분리된 결과는 아직 없다. 출력 양식 문제가 지속되면 모델을 높이라는 요청도 있으나, 기준 시각에 더 높은 로컬 모델로 세 조건을 모두 완료한 기록은 없다. 이 두 항목은 앞으로 검증해야 할 작업이다.

## 22. 상호작용·사이클·인간 개입을 정확히 설명하는 모식도

### 22.1 목표로 확정한 정보 경계

```text
[모델이 볼 수 있는 영역]
공개 요구 + 현재 프로젝트 파일 + 해당 실행에서 받은 자연어 답
       ↓
① 메인 단독 작성 → 제출
② 메인 작성 → 자체 점검 → 질문 → 담당자 답 → 메인 수정 ↺
③ 메인 작성 → 감시자 A·B·C 점검 → 질문 → 담당자 답 → 메인 수정 ↺
       ↓
제출 또는 한도 도달 상태와 산출물을 고정

[모델과 분리한 연구자 영역]
전체 정책·평가기 → 저장 버전별 측정 → 질문/반영/회귀/비용 분석
       ↓
다음 실험의 공통 구조 개선 및 새로운 비교 실행
```

연구자가 중간 과정을 알아야 한다는 요구는 모델에게 중간 점수를 줘도 된다는 뜻이 아니다. 저장된 과정을 연구자가 평가하되, 그 정보가 진행 중인 모델의 프롬프트·자연어 답·후보 선택·종료 신호에 섞이지 않아야 한다. 다음 실험의 프롬프트를 개선하면 개발 데이터에 적응한 것이므로, 새 시드와 별도 과제를 남겨 검증해야 한다.

| 정보 | 메인 | 감시자 | 담당자 대리 | 연구자 |
|---|---|---|---|---|
| 공개 요구·현재 코드 | 허용 | 허용 | 질문 해석에 필요한 범위 | 허용 |
| 해당 조건의 실제 답변 | 허용 | 허용 | 자신이 낸 답 기록 | 허용 |
| 다른 비교 조건이 받은 답 | 기본 금지 | 기본 금지 | 조건별로 분리 | 비교 분석 가능 |
| 미질문 정책 카드 전체 | 금지 | 금지 | 답변 생성에 사용 | 허용 |
| 중간 점수·실패 문항·기대 출력 | 금지 | 금지 | 답변에 사용 금지 | 허용, 모델로 역류 금지 |
| 코드 문법·수정 범위 검사 | 프로토콜 범위 내 허용 | 프로토콜 범위 내 허용 | 불필요 | 기록 |

### 22.2 한 사이클에서 누가 무엇을 하는가

메인은 현재 알고 있는 요구와 답으로 작업물을 만든다. 확인되지 않은 업무 결정을 조용히 확정하지 않고 질문이나 미정 상태로 남긴다. 감시자는 같은 버전의 코드와 공개 요구·답을 보고, 빠진 정보·충돌·미반영을 찾는다. 최신 세 조건 비교에서는 ②는 메인, ③은 감시자가 부족한 정보를 검사하고 질문하는 주체가 된다.

질문이 발생하면 해당 정책에 의존하는 부분은 답을 받을 때까지 확정할 수 없다. 담당자는 질문에 필요한 범위의 자연어만 제공한다. 대리 답변을 쓰는 실험에서는 고정 정책 카드가 이 역할을 수행하며, 모르는 부분은 미정으로 남겨야 한다. ‘정확히 24시간 전도 가능한가’, ‘정정은 몇 분이며 마지막 순간도 포함하는가’, ‘정정 중이라도 이미 시작하면 금지인가’처럼 판단 경계가 질문 대상이다.

메인은 답을 받아 다음 버전을 만든다. 다음 검토는 말로 수정했다고 주장하는지보다 실제 코드에 어떤 조건이 들어갔는지 확인한다. 반복 중 더 필요한 정책이 발견되면 다시 질문할 수 있다. 다만 같은 답을 반복 요구하거나 같은 수정이 무한히 이어지지 않도록 질문·답·버전·근거를 기록한다.

‘계속 검토했다’는 표현만으로 사이클 횟수를 세지 않는다. 원본 초안 이후 실제로 새 코드가 생성되고 다시 검토됐는지 버전 기록으로 센다. 3사이클 실험은 실제 반복 3회였다. 공개 시간 최종 검토는 고정 6호출의 한 번짜리 흐름이었다. 인간 개입 실험은 최대 6버전까지 진행했으나 모두 완료 판정 없이 한도에 도달한 사례들이었다.

### 22.3 인간 개입 시점과 완료 판정

사람의 개입은 프로젝트 전체가 끝난 뒤의 평가가 아니라 계획 또는 코드 검토 중 정책을 확정해야 할 때 일어난다. 원래 웹 실행기는 계획·코드 점검과 질문 대기를 상태로 관리했다. 로컬 실행기는 버전별 질문과 답을 파일로 남겨 다시 이어 간다. 사용자가 답을 자동 대리하도록 허용한 실험에서도 인간 역할의 정보 통로는 유지되지만 실제 사람의 응답 부담은 측정하지 못한다.

완료는 ‘점수가 높다’와 같지 않다. 형식상 제출했는지, 실행 가능한지, 중요한 미정 정책이 남았는지, 검토가 수정을 요구하는지, 호출·버전 한도에 걸렸는지를 따로 기록해야 한다. 한도 도달 시 최종 코드를 사후 평가할 수는 있지만 ‘프로젝트를 완성했다’고 바꾸어 쓰지 않는다. 다음 세 조건 실험에서 이 종료 규칙을 공통으로 정하는 것이 필요하다.

가장 반복적으로 보인 원인은 ‘필요한 정보의 확보’와 ‘확보한 정보를 보존해 구현하기’가 분리돼 있다는 점이다. 독립 감시자는 일부 필요한 질문을 더 잘 찾았지만, 답을 모두 받은 조건도 틀렸다. 원문 시간 연결은 후자의 일부를 개선했지만 질문 능력 자체를 높인 것은 아니다. 이 두 장치를 한 숫자로만 평가하면 어느 부분이 기여했는지 사라진다.

또한 역할을 늘리는 것과 다양한 오류를 발견하는 것은 동일하지 않았다. 동일 모델이 동일 입력을 보고 비슷한 판단을 반복하면 호출 수만 늘었다. 뒤 역할이 앞 의견을 본 뒤 동조하거나, 수정본을 실제로 추적하지 못하면 통합 단계가 효과를 내지 못한다. 역할별 정보 차단, 관점, 출력 근거, 수정 범위가 각각 실험 변인이다.

## 24. 결과 해석과 학술제 발표에서 지켜야 할 구분

### 24.1 지금 말할 수 있는 것

첫째, 질문·답변·수정·재검토가 이어지는 실행 환경을 만들고 실제 API와 로컬 모델로 여러 버전을 기록했다. 둘째, 특정 시드에서 감시자가 추가 정책을 물어 코드의 정답을 늘리는 경로를 확인했다. 셋째, 작은 모델에서는 원문 답이 숫자·경계·우선순위로 바뀔 때 오류가 발생했고, 기존 구조를 보존한 제한적 시간 변환이 한 실제 사이클 비교에서 개선됐다. 넷째, 호출·토큰·완료 상태·정답 손실을 함께 기록해야 성능 상승을 올바르게 해석할 수 있음을 확인했다.

### 24.2 아직 말할 수 없는 것

멀티에이전트가 일반적으로 단일보다 우수하다고 결론 내릴 수 없다. 과제 하나 또는 시드 하나의 향상, 동일 모델의 추가 호출 효과, 규칙 변환기의 효과가 섞여 있다. 29점 결과는 범용 구조의 확정 성과도 공식 제출 만점도 아니다. 무질문 411/480의 큰 상승 대부분은 자체 검토 409/480에서도 나타났고, 중간 검사 기반 372/480은 현재 규정의 성과에서 제외해야 한다.

또한 자동 담당자 답변은 실제 인간과 다르다. 질문을 읽는 시간, 이해하기 어려운 표현, 답하기 피곤한 정도, 여러 사람이 다르게 답하는 변동을 측정하지 않았다. 대리 답변이 정책 카드에서 정답을 고르는 방식은 실제 업무의 미정·모순·변경 상황을 완전히 대표하지 않는다.

| 축 | 권장 기록 | 필요한 이유 |

## 25. 다음 개선을 설계할 때의 우선순위

이 절은 기존 기록에서 도출한 다음 실험안이며 이 보고서 작성 중 실행한 작업이 아니다. 최신 사용자 요청의 세 조건을 먼저 고정해야 한다. ①은 불충분한 공개 정보만 받고, ②는 메인이 검사·질문하며, ③은 감시자가 검사·질문하도록 한다. 같은 모델·과제·최초 정보·정책 카드·예산·종료 규칙을 사용하고 질문에 따라 받은 답의 차이는 효과의 일부로 기록한다.

그다음 질문 능력과 구현 능력을 나눠 비교하는 보조 실험을 둔다. 각 조건이 직접 획득한 답을 쓰는 본 실험은 전체 구조의 효과를 본다. 동일한 확인 답을 공통 제공하는 보조 실험은 답 이후 구현 능력을 본다. 두 결과를 섞지 않으면 독립 감시가 질문을 잘해서 좋아졌는지, 같은 정보를 더 잘 구현해서 좋아졌는지 해석할 수 있다.

범용 감시의 핵심 산출물은 과제 전용 정답표가 아니라 ‘아직 결정되지 않은 사항, 질문, 받은 원문, 관련 파일과 위치, 실제 반영 상태’의 연결이어야 한다. 숫자·시간 파서는 이 연결의 한 보조 기능으로 둔다. 모든 과제에 예약용 규칙표를 강제하지 않고, 원래 코드의 제한된 수정이 가능하도록 한다. 문법 검사와 패치 유효성 검사는 채점기와 명확히 분리한다.

추가 역할이나 사이클은 효과가 보일 때만 늘린다. 같은 코드·같은 질문·같은 반영 상태가 반복되면 왜 변화가 없는지 기록하고 미완료로 종료하는 규칙을 검토한다. 점수로 조기 종료하거나 최고 중간 점수 버전을 선택하지 않는다. 호출 수를 맞춘 자체 검토와 토큰·시간이 비슷한 자체 검토를 별도 비교하면 역할 분리의 효과를 더 명확히 볼 수 있다.

출력 양식 실패가 주요 병목으로 남으면 한 단계 높은 로컬 모델로 세 조건을 함께 다시 실행한다. 멀티만 강한 모델로 바꾸면 구조와 모델 능력이 섞인다. 예약 외 적어도 두 과제와 새로운 정책 변형을 남겨 개발에 쓰지 않은 조건에서 평가해야 한다. 새로운 결과가 나오기 전에는 기존 29점과 범용화 진행 상태를 그대로 기준선으로 보존한다.

시간 조건 실험의 당시 최종 보고는 전체 95개, 벤치 관련 8개, 웹 관련 12개 검증 통과를 기록했다. 범위가 겹칠 수 있으므로 115개의 서로 다른 검사를 의미한다고 단정하지 않는다. 이 보고서 작성 중 해당 성능 실험이나 전체 테스트를 새로 실행하지 않았다. 저장된 검증 결과와 소스·산출물을 읽었으며 PDF의 내용·레이아웃만 새로 검증했다.

공통 실행기의 완결성과 정책 정답률은 별개다. 단위 테스트가 통과해도 모델이 받은 답을 잘못 구현할 수 있다. 반대로 특정 벤치마크 점수가 높아도 질문 대기나 완료 처리에 결함이 있을 수 있다. 역사 기록에는 두 축을 함께 남겨야 한다.

## 27. 추가 확인: 학술제용 20문항·세 조건의 새 실행

이 절은 본문 상태표를 고정한 뒤 오전 11시 02분까지 새로 확인한 자료다. 별도 대화가 계속 작업 중이므로 이 시점의 고정된 초안 실험과 후속 개선 준비를 구분한다. 종합 README가 아직 존재하지 않아 `design.json`, 실행 상태, 호출 기록, 문항별 연구 결과를 직접 대조했다. 연구 결과의 코드 해시가 해당 최종 버전과 일치하는지 8개 조건 모두 확인했다. [S27]

### 27.1 모델과 세 조건을 실제로 다시 구성

새 설계의 모델 파일은 `Qwen3.5-4B-Q4_K_M.gguf`이고 시드는 263, 실행기는 llama.cpp b12706이다. 앞선 Qwen3-8B와 다른 모델이다. 이름의 세대와 파라미터 수가 함께 바뀌었으므로 이 기록만으로 ‘성능이 한 단계 높다’고 단정하지 않는다. 모델 파일 해시도 설계에 고정했다.

예약 취소 10문항과 문의 배정 10문항을 선택해 총 20문항으로 줄였다. 이전 40문항이나 16문항 전체 성적과 직접 비교하지 않는다. 주 비교는 마지막 고정 코드의 정답·오답·미판정이고, 중간 최고 점수를 고르지 않는다. 버전 상한은 이 설계에서 2이며 공통 코드의 기본값 3과 다르다. 메인 출력 예산 2,400, 검토자 950토큰, 한 질문 창의 질문 상한 3개다.

| 조건 | 질문 주체와 구조 | 과제당 호출 구조 |
|---|---|---|
| solo, ① | 메인 1회 작성, 추가 정책 질문 없음 | 작성 1회 |
| self, ② | 메인 자신의 검토 1회로 부족한 정책을 질문 | 버전마다 작성 1회 + 자체 검토 1회 |
| p2, ③의 기본형 | A·B·C가 누락·규칙 충돌·임의 가정을 독립 검토하고 질문 | 버전마다 작성 1회 + 감시 3회 |
| p3, ③의 근거형 | p2에 질문 상황과 가능한 결과 두 가지의 내부 기록 추가 | p2와 같은 호출 수, 더 긴 검토 출력 가능 |

메인 작성 응답은 파일과 완료 여부로 제한돼 질문은 검토자 응답에서 수집한다. p3의 두 결과가 같거나 상황이 비면 질문 근거가 부족한 것으로 기록한다. 담당자에게는 최종 질문만 전달하고 내부의 두 대안은 전달하지 않는다. 서로 다른 결과가 원문상 가능한지를 모델이 정확하게 판단했는지까지 형식 검사만으로 보증하지는 않는다.

자체 검토 1회와 감시 3회이므로 이 새 비교는 호출 수가 같은 구조 비교가 아니다. 사용자가 정한 실사용 세 조건의 비용과 성능을 함께 보는 설계다. 역할 분리만의 효과를 주장하려면 별도로 같은 예산의 자체 검토 대조가 필요하다.

### 27.3 후속 개선 파일에서 확인한 변경

이 보고서는 과거 자료를 복구·대조하고 같은 내용의 Markdown과 PDF로 묶는 작업이다. 원래 실험 코드, 실행 DB, 동기화된 `sources/` 자료를 수정하지 않았다. 과거 모델을 새로 호출하거나 진행 중인 다른 대화의 실험을 중단·재시작하지 않았다. 날짜가 같은 최신 결과 파일이 뒤에서 갱신되더라도 이 문서의 상태 표는 기준 시각의 기록이다.
