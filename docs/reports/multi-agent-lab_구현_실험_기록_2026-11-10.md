# Multi Agent Lab 구현 및 실험 기록 정리

작성일: 2026-11-10 (한국 시간)  
조사 방식: 로컬 소스·README·실행 DB·저장된 채점 결과·내려받은 실행 JSON·과거 개발 대화 확인. 이번 정리에서는 새 모델 호출이나 벤치마크 재실행을 하지 않았다.

## 1. 핵심 요약

Multi Agent Lab은 **메인 코드 작성 에이전트 1개와 서로 다른 관점의 감시자 3개가 공유 상태를 통해 협업하고, 필요한 정책을 인간에게 질문한 뒤 코드를 수정하는 로컬 실험 환경**이다. 초기에는 작업 A/B/C와 감시 분기를 보여주는 데모였고, 이후 실제 API 호출·인간 답변·격리 코드 실행·수동 채점을 연결했다.

현재 확인된 평가 과제는 예약 취소 100문항과 예약·대기열·자원 배정 150세트다. 바탕화면 실행 DB에는 실제 API 모드 실행 10건이 있으며, 완료 4건·중단 3건·실패 2건·일시 정지 1건이다. 저장된 호출 레코드는 218개, 질문 레코드는 50개, 인간 결정 레코드는 35개다. 호출 수는 성공한 API 응답만을 뜻하지 않으며 재시도·실패·중단도 포함한다.

채점 완료 기록은 예약 취소 **90/100, 100/100, 100/100**, 자원 배정 **150/150**이다. 이는 개발 중 파일럿 결과다. 모델·페르소나·인간 답변·프로그램 버전이 통제된 비교 실험으로 해석할 수는 없다.

## 2. 구현한 것

### 2.1 초기 화면과 독립 감시 분기 데모

- 작업 A/B/C와 감시자 3개를 표시하는 최소 웹 화면.
- 감시자마다 컨셉·모델·지침을 입력하고 분기별 질문·답변·상태·기록을 분리.
- 한 분기에 답하면 해당 분기만 진행하고 나머지는 계속 대기.
- 모든 분기가 끝나면 응답을 모으고 JSON 기록을 내려받음.
- 이 단계의 질문과 처리 지연은 고정 예시·타이머였다. 실제 모델 호출, 실제 작업 에이전트 실행, 코드 생성, 의미적 충돌 해결은 연결되지 않았다.

근거: `launcher_staging/archive/three-branch-demo/README.md`, `web/branch-runner.js`.

### 2.2 메인 1개 + 감시자 3개 구조

```text
메인: 계획·가정 제출 → 코드 작성·수정
                  ↓
실행 관리자: 코드 버전·검증 결과·질문·인간 결정 저장
                  ↓ 같은 회차의 상태 스냅샷
             감시 1 / 감시 2 / 감시 3
                  ↓
        계속 진행 / 추가 검증 / 인간 판단 요청
                  ↓
        인간 답변 → 공유 상태 → 다음 메인 수정
                  ↓
          프로젝트 완료 → 수동 벤치마크 채점
```

- 계획 제출 직후와 각 코드 버전 작성·검증 후 감시한다. 모델이 코드를 생성하는 도중의 내부 추론을 관찰하는 구조는 아니다.
- 메인은 계획·가정, 전체 소스 코드, 변경 요약, 완료 여부, 자체 검증 사례와 인간 결정 처리 ID를 반환한다.
- 감시자는 판단·근거·질문·우선순위·영향 작업·추가 검증 사례를 반환한다. 코드를 직접 수정하지 않는다.
- 감시 응답이 도착하면 다른 감시자를 기다리지 않고 질문을 등록한다. 동일한 질문 `key`를 기준으로 중복을 합친다.
- 같은 회차의 감시자는 동일 상태를 보지만, 후속 회차에는 이전 감시 결과가 공유된다. 모든 회차에서 완전히 독립적인 관찰자는 아니다.
- `affected_tasks`는 영향 범위 및 화면 상태에 사용한다. 작업별 별도 에이전트가 실행되는 일반적인 병렬 작업 스케줄러로 확대 해석하면 안 된다.

근거: `backend/live_workflow.py`, `backend/live_schemas.py`, `backend/engine.py`; 개발 대화 「멀티에이전트 인간 개입 설계」.

### 2.3 인간 개입·프롬프트·정책 분리

- 메인 프롬프트와 감시자 3개의 컨셉·지침을 각각 설정하고 원문을 API 입력으로 전달.
- 인간의 질문 답변과 추가 조언을 실행 결정으로 저장하고 후속 메인·감시 호출에 포함.
- 답변 수신과 코드 반영을 분리하며, `applied_decision_ids`와 `context_decision_ids`로 코드 반영 보고와 맥락 확인을 구별.
- 보고 누락·잘못된 ID·중복 분류에는 구체적 피드백을 주고 최대 2회 재요청.
- 운영 정책의 정답은 자동 전달하지 않도록 수정. 함수 계약·공통 실행 지침·현재 상태는 여전히 자동 제공된다.
- 진행자용 ‘규칙’ 버튼은 선택한 과제의 채점 정책을 보여주지만 모델 입력에 자동 포함하지 않는다.

따라서 ‘아무 정보도 미리 주지 않는 실험’은 아니다. 공개 과제와 실행 형식은 제공하고, 운영 정책은 사용자 프롬프트와 인간 답변으로 전달하는 설계다.

### 2.4 실행·저장·오류 복구

- 로컬 웹 서버와 실제 API 연결·해제, 메인·감시자별 모델 선택, 모델 목록 갱신.
- 지원 호환 목록과 계정 모델 목록을 대조하는 필터. 당시 목록 조회 성공이 실제 생성 권한을 보장하지는 않았음.
- 예약 취소용 모의 실행과 실제 API 실행을 구분. 자원 배정은 API 모드로 연결.
- SQLite에 상태·프롬프트·질문·답변·호출·응답·사용량을 기록하고 실행별 코드 버전과 채점 JSON 저장.
- 새 인간 답변 없이 자동 수정 6회 진행 시 일시 정지. 인간 답변 반영은 해당 제한과 구분하고 계속하기로 재개.
- 중단·서버 재시작·API 오류 뒤 기존 코드와 답변을 보존하는 복구 처리.
- 진행 중 / 답변 대기 / 일시 정지 / 완료 / 오류, 활성 메인·감시 호출 표시.
- 오류 에이전트·모델·단계·코드 버전·경과 시간·기대 조건과 실제 값·실패 응답·발생 위치를 남기는 상세 진단 추가.

### 2.5 검증과 평가 격리

- 함수 계약과 문법, 모델이 제시한 최대 10개의 자체 검증을 확인.
- 생성 코드 실행은 macOS `sandbox-exec` 기반으로 분리하고 파일·네트워크·자식 프로세스 접근을 제한. 격리 실패를 일반 실행으로 우회하지 않음.
- 숨겨진 정책·평가 입력·정답은 모델 입력에서 제외하고, 정답 비교는 신뢰하는 부모 프로세스에서 수행.
- 자체 검증과 최종 벤치마크를 구별하고 사용자가 ‘테스트하기’를 눌러 채점.
- API 키는 서버 메모리에 보관하고 기록·생성 코드·자식 환경에서 제외하며 진단 기록의 키 형태를 마스킹.

## 3. 만든 벤치마크

### 3.1 예약 취소 — 100문항

계약: `can_cancel(now, booked_at, starts_at) -> bool`.

정답 정책은 입력·시간 순서 검증 → 이미 시작했는지 → 예약 후 10분 유예 → 시작 24시간 전 마감 순서다. 마감이 금·토·일 또는 실험용 추가 휴일(2026-11-10, 2026-12-24)에 걸리면 앞선 영업일 18시로 조정한다. 시각은 한국 시간 기준이며 정확한 마감과 정확히 10분은 포함한다.

평일 마감, 마감 경계, 금·토·일 휴무, 추가 휴일, 연속 휴무, 유예 경계, 시작과 유예 우선순위, 잘못된 시간 순서의 **10유형 × 10문항**이다. 허용 45개·거부 55개이므로 무조건 거부하면 55점이다. 문항당 1점으로 채점하고 유형별·허용/거부별 성적을 남긴다.

정답 구현의 저장된 기준 결과는 100/100이다. 이 기준 결과는 모델 실험 성적과 별개다.

### 3.2 예약·대기열·자원 배정 — 150세트

계약: `simulate(initial_state, events)`.

동일한 이용 시간대의 좌석·노트북·프로젝터를 대상으로 예약, 취소, 변경, 자원 수량 변경을 순차 처리한다. **15유형 × 10변형, 총 1,690개 사건**이며 세트당 8~18개 사건이다.

| 유형 | 검증 내용 |
|---|---|
| 1~3 | 정원 경계·연속 해제, 동순위 선착순과 큰 그룹 건너뛰기, 우선순위 충돌 |
| 4~5 | 정원 초과 대기와 증설, 복수 자원의 원자적 확보 |
| 6~9 | 대기 취소·반복 취소, 확정 예약 비선점, 확정/대기 예약 변경 |
| 10~11 | 단계적 증설, 축소 거부와 자동 승격 |
| 12~14 | 사용자 중복·ID 재사용, 재전송·event_id 충돌, 잘못된 입력 |
| 15 | 취소·변경·증설의 복합 연쇄 |

사건 결과(`event_results`), 최종 상태(`final_state`), 알림(`notifications`)이 모두 일치해야 세트당 1점이다. 원점수는 150점 만점, 환산점수는 원점수/150×100이다. 객체 키 순서는 무시하지만 배열 순서·타입·값은 비교한다. 구성 요소별 성적도 별도 기록한다.

15개 시나리오 계열의 변형이지 150개의 독립적 문제 유형은 아니다. 내부의 모든 중간 상태 불변조건을 직접 추적하는 채점은 구현 범위에 포함되지 않는다. 정답 구현 150/150과 데이터 검증 완료는 과거 개발 대화에 보고되어 있다.

- 최종 상태는 완료지만 과거 감시 형식 오류도 남아 있다. 최종 성공이 전체 과정의 무오류를 뜻하지 않는다.

## 5. 실험한 감시 페르소나

| 묶음 | 관점 1 | 관점 2 | 관점 3 |
|---|---|---|---|
| 기본 관점 | 개입 판단의 태도: 위험·되돌릴 수 있는 범위·사용자 의도 | 집중하는 근거: 문서·테스트·목표·의존성 | 인간에게 필요한 기여: 현장 맥락·가치 우선순위·사용 경험 |
| 사용자 입력 관점 | 주장 감사관: 작업자의 주장과 기록된 증거·누락 비교 | 궤적 분석가: 현재 작업 방식이 좋은 결과로 이어지는지 검토 | 새벽 3시 온콜: 운영 문제를 빠르게 진단·중단할 수 있는지 검토 |

초기 논의에는 3컨셉 × 3개, 총 9개 페르소나 아이디어가 등장하지만 현재 실행 구조는 감시자 3개다. 9명의 감시자를 동시에 실행한 실험으로 기록하면 안 된다. 실제 저장 기록에는 위 두 묶음이 사용되며, 두 묶음을 동일 조건에서 반복 비교한 결과표는 확인되지 않았다.

## 6. 자동 테스트 및 개발 과정의 검증

소스에 있는 테스트는 다음 범위를 다룬다.

- 공유 상태·프롬프트 전달·질문 중복 통합, 느린 감시자와 독립 요청 처리.
- 인간 답변·반영 보고, 수동 채점 시점, 잘못된 인간 정책이 점수에 미치는 영향.
- HTTP API, 비공개 평가 파일의 웹 노출 차단, 연결 전 실행 거부.
- 실제 API 경로의 대체 응답 테스트, 키 비저장, 중단 응답성, 격리 환경 접근 제한.
- 자원 배정 계약·정답 비교, 알림 순서와 타입 오류, 과제별 선택·채점.
- 자동 수정 한도·재개, 서버 재시작, 이전 호출의 늦은 응답 처리.
- 생성 코드 오류 복구, API·감시 오류, 맥락 답변 분류와 보고 누락 재요청.
- 오류 상세 기록·실패 응답 보존·민감 정보 마스킹과 웹 상태 표시.

개발 대화에는 API 연결 단계 19개, 복구/규칙 화면 단계 27개, 공개 업로드 단계 35개, 후속 기능 단계 38~46개, 상세 진단 단계 **50개 통과** 등의 보고가 있다. 서로 다른 시점과 범위의 검증 횟수이므로 합산하지 않는다. 이번 조사에서는 테스트 파일의 존재와 과거 보고를 확인했으며, 50개를 새로 실행했다고 주장하지 않는다. 자동 테스트의 대체 API 응답 검증은 실제 모델 성능 실험과 별개다.

## 8. 현재 기록으로 말할 수 있는 결론과 한계

**확인된 성과:** 인간에게 정책을 질문하고 답변을 공유 상태에 넣어 메인 코드를 수정한 뒤, 두 종류의 고정 벤치마크로 평가하는 전체 실험 환경을 구현했다. 실제 실행에서 두 과제 모두 만점을 얻은 기록이 있으며, 정책 불일치·라이브러리 오류·접근 권한·응답 형식·답변 처리 검사 같은 실패도 관찰하고 복구 기능을 보강했다.

**아직 입증하지 않은 것:** 감시자 없는 조건 대비 개선량, 감시자 수의 효과, 페르소나별 우열, 모델별 우열, 비용·시간 대비 효과, 인간 개입 시점의 적절성에 대한 정량적 비교. 완료한 실행만 평균 내거나 접근 실패를 0점으로 넣으면 서로 다른 문제를 섞게 된다.

특히 질문 적절성, 인간 답변의 의미적 반영 여부, 여러 작업 사이 피드백 전파는 최종 함수 점수만으로 측정되지 않는다. 반영 ID는 모델의 보고이지 의미적 정확성의 증명은 아니다. 후속 비교 실험에는 고정된 인간 응답 프로토콜, 동일 과제·모델 조건, 반복 실행, 무감시/단일감시 대조군, 사전 정의한 질문 품질·시간·토큰 지표가 필요하다. 이는 후속 제안이며 이미 수행한 실험 목록에는 포함하지 않는다.
