# 감시자가 물은 것과 담당자가 답한 것을 코드에 보존하기

『감시자가 찾은 규칙은 코드에 남았나』 이후의 파이프라인 변경과 벤치마크 분석

와쿠쿠 5조 · 후속 연구 보고서 · 작성 2026년 11월 27일

**현재까지 확인한 성과는, 일부 답만 받은 상태를 보존하고 추가 답에 해당하는 동작만 바꾸는 작은 실행 체계를 구축했다는 것이다.** 혼합 감시 업로드의 원래 질문·초안을 고정한 실험에서, 상한 포함·제외 두 조건은 각각 20/20을 유지했다. 상한과 같을 때의 정책이 빠진 조건은 실제 회신 기준으로 12/20에서 20/20으로 개선됐다. 같은 첫 제출에 허용·거부 회신을 각각 주자 정확히 16바이트에서만 동작이 달라졌다. [S18]

| 이번 후속 연구의 주요 관찰 | 해석 |
| --- | --- |
| 최초 답 뒤집기 실험의 엄격한 성공 1/12쌍, 사후 검사 0/12쌍 | 답의 방향을 반영하는 일과 영향 밖의 동작을 보존하는 일을 함께 검증할 필요가 생겼다. |
| 업로드 값 예측 18/18, 코드 실행 13/18 | 구체적인 결과를 말하는 능력과 일반 조건문을 만드는 능력 사이의 차이를 관찰했다. |
| 작성기 개발 비교 13/18 → 17/18, 전체 10조건 재검증의 개선 0건 | 국소 개선이 전체 실행의 올바른 경로에 도달해야 한다. |
| 혼합 업로드 12/20 → 20/20 | 감시자의 지적과 충분한 회신을 편집기에 연결했을 때 기존 정답을 지키며 고칠 수 있었다. |
| 최신 업로드 5상태 모두 20/20, 환풍기 5상태 모두 4/4 | 열린 질문을 보존하고 답변에 해당하는 분기만 수정하는 동작을 두 과제에서 확인했다. |

후기 성공은 Qwen3.5-4B, 한 시드, 제한된 함수 형태의 개발 검증이다. 환풍기도 구현 수정 과정에 사용했다. 일반 프로젝트 전체나 다른 모델에서 같은 성과가 유지되는지는 아직 측정하지 않았다.

첨부한 종합보고서의 Markdown·PDF는 작업 폴더의 보관본과 각각 바이트 단위로 일치했다. 본문은 그 보고서 이후의 실행 기록, 후속 짝비교 보고서, 제출 코드와 호출 원문을 연결해 작성했다. 보고서 작성 과정에서 새 모델 벤치마크는 추가하지 않았다. [S01] [S02]

## 1. 이 후속 연구가 필요했던 이유

멘토링 피드백과 5조 2차 발표 이후 팀은 인간 개입이 있는 코딩 과정을 시연하는 데서 나아가, 감시자의 기여를 비교 가능한 조건으로 측정하기 시작했다. 원래 목표는 불충분한 요구사항을 AI가 임의로 채우는 일을 줄이고, 완성 전에 담당자에게 필요한 정보를 받아 더 적합한 코드를 만드는 것이었다. 이 목표는 후속 실험에서도 이어졌다. [S01]

세 비교 조건은 공개 정보만 받는 메인 단독, 메인이 스스로 검사하고 묻는 조건, 독립 감시자들이 검사하고 메인이 답을 반영하는 조건이었다. 초기 종합보고서에는 감시자들이 추가 정책을 찾아도 총점이 같거나 낮아지는 사례가 있었다. 여기서 “더 많이 찾았는가”와 “찾아서 받은 답이 프로그램의 판단을 바꿨는가”를 따로 확인할 필요가 생겼다.

| 종합보고서까지의 관찰 | 남은 질문 |
| --- | --- |
| 기본 예약에서 Qwen 단독과 혼합 감시의 코드가 같고 둘 다 15/50 | 확인한 정책이 이미 있던 행동을 정당화했는지, 실제 수정을 일으켰는지 |
| 자체 검토와 감시가 같은 65개 정답, 근거 충분 문항은 83 대 97 | 감시자가 추가로 확인한 14개 입력의 근거가 어디에 쓰였는지 |
| 인쇄에서 같은 문답으로 편집 문제를 고치자 14/20 → 20/20 | 편집 적용을 안정화하면 다른 과제에서도 받은 답을 보존하는지 |
| 모델별 감시 이득이 특정 과제에 집중 | 감시자 수나 모델 다양성의 이득이 과제 구성에 얼마나 의존하는지 |

후속 연구는 먼저 답 한 문장을 바꾸는 짝실험으로 정책의 효과를 추적했다. 이후 값 예측, 편집 방식, 경로 선택, 미응답 판정, 회신 문장 보존을 차례로 검사했다. 같은 총점의 원인을 좁혀 가는 과정이었다. [S02] [S03]

## 2. 실험이 이어진 순서와 변경의 당위성

실험 번호는 이 보고서의 읽기 순서다. 저장 폴더명은 원자료 식별자로 유지했다.

| 순서 | 다음 실험을 촉발한 관찰 | 시도한 변경 | 확인된 결과 |
| --- | --- | --- | --- |
| 1 | 코드가 같아도 확보한 근거 수가 달랐다. | 같은 상태에서 담당자의 답만 뒤집었다. | 목표와 대조를 모두 만족한 쌍은 사후 검사에서 0/12였다. |
| 2 | 코드를 보면 실패 위치는 보이지만 동작 해석 능력은 불명확했다. | 값 예측과 코드 수정을 독립 호출했다. | 18/18 대 13/18로 차이가 났다. |
| 3 | 양수 전체를 거부하는 등 수정의 적용 범위가 잘못됐다. | 동작 메모, 위치별 선택, 참·거짓 범위 조립을 비교했다. | 채택한 방식은 17/18까지 회복했다. |
| 4 | 개발 과제의 개선이 전체 비교에도 나타나는지 불명확했다. | 기존 10조건의 변경된 경로만 재실행했다. | 2,500개 문항·조건 쌍에서 개선 0건이었다. |
| 5 | 감시자의 지적이 있으면 새 편집 경로에서 배제됐다. | 혼합 업로드의 지적을 수정 위치에 연결했다. | 연구자 지정 범위에서 12/20 → 20/20이었다. |
| 6 | 충분한 답 한 종류만으로는 자동화와 보류를 검증할 수 없었다. | 포함·제외·미언급 세 회신으로 분기했다. | 명시된 답은 구현했지만 미언급을 잘못 판정했다. |
| 7 | 묶인 질문 중 무엇에 답했는지 사라졌다. | 질문 시점에 결정 항목과 공개 규칙을 저장했다. | 회신 추출기가 문장·숫자를 누락해 여전히 실패했다. |
| 8 | 올바른 질문 기록에도 답 원문이 제대로 도착하지 않았다. | 모든 회신 문장을 처리하고 숫자는 원문에서 취했다. | 업로드·표현 변경·환풍기의 지정된 목표를 충족했다. |

변경은 모두 알려진 실패를 참고한 개발 과정이다. 마지막 성과의 해석에는 반복 수정, 같은 과제 재사용, 단일 시드라는 조건이 함께 들어가야 한다. [S03] [S05] [S06] [S08] [S10] [S13] [S16] [S18]

## 3. 모델이 볼 수 있는 정보와 점수의 분모

실행 모델이 정책을 정할 때 사용할 외부 정보는 공개 명세와 실제로 받은 담당자의 자연어 답변이다. 감시자의 질문과 코드 지적은 어떤 문제를 살필지 알려 준다. 질문에 어떤 정책이 등장했다는 사실만으로 그 정책이 확정되지는 않는다.

연구자는 제출 뒤에 채점기·기대값·반례를 보고 다음 실험의 구조를 개선했다. 이러한 개발 피드백과 실행 중 모델에 가채점 결과를 주는 행위는 정보 전달 시점이 다르다. 이번 기록에서는 마지막 후보를 고정한 뒤 평가를 열었고, 새 작성 호출에는 가채점 결과를 넣지 않았다. 혼합 업로드의 초기 국소 실험은 1회차 제출을 고정해 평가한 뒤 개선·보존 조건을 만족할 때 후속 회차를 진행했다. 그 진행 여부는 연구자의 판단이었다. [S03] [S10] [S20]

| 지표 | 이 보고서에서 세는 대상 |
| --- | --- |
| 기존 공식 점수 | 원래 고정 정책의 기대값과 실행 반환값이 같은 입력 수 |
| 실제 회신 기준 점수 | 명세와 해당 시점에 받은 답으로 정해진 행동을 수행하고, 미정인 경우 보류하는 입력 수 |
| 목표 입력 양쪽 정답 | 답 A와 B에서 서로 다른 정답을 두 코드가 각각 따르는 입력 수 |
| 대조 입력 보존 | 답을 바꿔도 정답이 같은 입력에서 동작과 기존 정답이 유지되는지 |
| 정책 단위 반영 | 하나의 정책을 받아 의도한 범위 전체에서 작동했는지 |
| 사용 토큰 | 호출 범위와 재사용 계산 방법을 명시한 입력·출력 합계 |

업로드의 20문항 중 여러 입력은 같은 분기를 공유한다. 20/20과 독립적인 정책 결정 20건 성공은 의미가 다르다. 후기의 ‘5상태’도 같은 초안에서 만든 최초 세 회신과 두 후속 갈래다. 총 220회 평가를 합산할 수는 있지만, 이를 서로 다른 220문제에 대한 일반화 성능으로 읽으면 과장된다.

## 4. 추가 근거 14건과 모델별 이득의 재분석

기존 65점 동률 자료의 최종 반환값과 오류 상태를 100문항에서 짝지으면 모두 같았다. 감시자 쪽에서만 근거가 충분했던 14개 입력을 초안까지 거슬러 올라갔다. [S04]

| 추가 근거의 행방 | 입력 수 | 관찰 |
| --- | --- | --- |
| 처음부터 맞던 행동을 확인 | 1 | 숨김 파일 .local.txt에서 txt를 반환하는 행동이었다. |
| 초안 보류를 양쪽 모두 수정 | 1 | 상한 16을 둘 다 허용했지만 끝점 허용 답은 감시자만 받았다. |
| 답을 얻고도 잘못된 값 반환 | 8 | 확장자의 대소문자·여러 점·숨김 파일 정책이었다. |
| 답을 얻고도 잘못된 반환 형식 | 4 | 빈 문자열을 반환해야 할 곳에서 None이 나왔다. |
| 감시자 쪽만 행동 개선 | 0 | 추가 근거가 감시자만의 정답 증가로 연결된 입력은 없었다. |

기본 예약에서도 단독과 혼합은 같은 코드로 15/50을 받았다. 혼합은 45개 입력을 판단할 근거를 얻었고 이미 맞던 10개가 근거 있는 정답으로 바뀌었다. 단독의 근거 있는 정답은 0개였다. 요구사항 확인의 성과는 있었지만, 그 수치만으로 답에 따른 행동 변화가 입증되지는 않았다.

| 과제 구성 | Qwen 자체 / 동종 감시 | Gemma 자체 / 동종 감시 | Phi 자체 / 동종 감시 |
| --- | --- | --- | --- |
| 다섯 과제 전체 /100 | 57 / 65 | 45 / 54 | 31 / 21 |
| 업로드 제외 /80 | 45 / 45 | 26 / 35 | 27 / 13 |
| 제목 제외 /80 | 50 / 58 | 45 / 45 | 31 / 21 |

Qwen의 8점 이득은 업로드, Gemma의 9점 이득은 제목에서 발생했다. 이 결과는 감시자의 효과를 과제·정책 단위로 보여 줄 필요성을 뒷받침한다. 위 모델 비교와 앞의 65점 동률 자료는 답변 운영이 다른 실행이므로 별도로 읽어야 한다. [S02] [S04]

## 5. 담당자의 답 한 문장을 뒤집은 최초 짝실험

예약·업로드·문의 배정·센서의 네 과제에서 세 시드 273·419·887을 사용했다. 쌍 안에서는 명세·초안·질문·작성 모델·편집기·시드를 고정하고 정책 한 문장만 바꿨다. 12쌍, 제출 24개를 평가했다. [S03]

| 과제 | A와 B가 달라지는 정책 | 실제 실패 |
| --- | --- | --- |
| 예약 | 정정 기간의 정확히 600초 포함 / 제외 | 일부 제안은 올바른 방향의 비교식을 썼지만 편집 위치와 출력 문제로 여섯 제출 모두 초안이 남았다. |
| 업로드 | 정확히 16바이트 허용 / 거부 | 제외 정책에서 양수 전체 거부, 초과값 허용, 반환 누락이 발생했다. |
| 문의 배정 | 두 팀의 우선순위 순서 교환 | 팀 이름 순서를 바꿔도 입력 태그를 먼저 만난 순서대로 반환했다. |
| 센서 | 중복 ID의 첫 값 / 마지막 값 보존 | 첫 값 보존에서 중복 하나를 건너뛸 자리에 함수 전체 종료가 들어갔다. |

사전에 정한 52개 입력을 세 시드에서 사용했다. 목표 입력 양쪽 정답은 7/39, 대조 입력 양쪽 정답은 75/117이었다. 목표 전부를 맞힌 쌍은 3/12였고, 대조 행동 보존까지 만족한 쌍은 1/12였다. 24개 중 16개 제출에서 편집이 적용됐으므로 편집 수락만으로 정책 반영을 판단할 수 없었다.

코드를 확인한 뒤 예약 56·업로드 36·문의 85·센서 341개, 합계 518개 입력으로 범위를 넓혔다. 유일하게 통과했던 센서 쌍에서도 뒤에 등장한 다른 센서가 사라지는 반례가 발견돼 엄격한 성공은 0/12가 됐다.

이 0/12는 그 네 과제·세 시드·편집 방식에서 확인된 반례의 결과다. 518개 범위는 코드 검토 후 정한 사후 검사다. 새로운 과제에서의 성공률이나 감시자의 질문 능력을 추정하는 수치로 확대할 수 없다. [S02] [S03]

## 6. 감시자 수·독립성·정보 충분성의 별도 대조

Qwen 한 명이 앞선 질문을 읽고 세 관점을 순차 검토하는 조건과, 서로의 의견을 가린 Qwen 세 호출이 한 관점씩 검토하는 조건을 비교했다. 같은 초안·모델·세 번의 호출·시드 593을 사용했고, 담당자는 각 팀의 첫 두 정책 항목까지만 답했다. [S04]

업로드 독립 검토는 상한값도 발견했지만 답변 항목 제한 때문에 실제 회신에는 그 값이 없었다. 작성기는 1,000,000을 임의로 넣었다. 따라서 13점이라는 결과에는 근거 없는 추정이 포함됐다. 인쇄에서는 독립 검토의 편집이 겹치는 위치 때문에 거절됐고, 순차 검토는 일부를 고치면서 기존 정답 다섯 개를 잃었다.

완전 명세와 정책 하나가 빠진 명세를 두 과제·두 시드에서 비교했을 때, 완전 조건 4/4회에서도 재질문했다. 누락 조건에서도 4/4회 질문했으나 실제 빠진 정책을 요청한 것은 0/4였다. 독립성의 이득은 발견·전달·답변·반영의 각 단계에서 확인해야 하며, 최종 구조에는 불필요한 질문을 줄이는 능력도 필요하다.

## 7. 근거 충분성의 AI 재판정이 남긴 한계

사람 평가를 대리해 Gemma 3 4B와 Phi-4-mini가 12개 상황을 독립 판정했다. 조건명·최종 코드·정답·종전 충분성 표시를 가리고, 공개 명세·실제 문답·평가 입력을 제공했다. 상황 순서는 평가자마다 달랐다. [S02] [S04]

| 지표 | 첫 양식 | 발화자·반환 형식 보완 후 |
| --- | --- | --- |
| 판단 가능 / 불가의 일치 | 8/12, 카파 0.33 | 11/12, 유효한 11쌍 모두 가능 |
| 반환값까지 일치하거나 모두 보류 | 6/12, 모두 보류 사례 | 2/12 |
| 종전 충분성 판정과 일치 | Gemma 4/12, Phi 4/12 | Gemma 7/12, Phi 8/12 |
| 가능 판정 뒤 값까지 정답 | Gemma 0/6, Phi 0/2 | Gemma 5/11, Phi 3/12 |

‘10분’이라고만 한 예약 회신을 보고 두 평가자는 정확히 600초를 모두 거부했다. 두 모델의 일치가 같은 가정에서 생길 수 있음을 보여 준다. 두 번째 양식은 판정이 한 범주에 몰려 카파를 계산할 수 없었고, Gemma의 무효 응답 한 건도 분모에 남겼다.

대리 담당자가 질문받지 않은 정책을 알려 줬는지도 재검토했다. 확장자가 없는 이름을 묻는 넓은 질문이 마지막 글자가 점인 경우까지 포함하는지는 해석이 갈릴 수 있었다. 모델의 범위 초과 판정만으로 이를 확정하지 않았다.

이 작업은 논쟁적인 표현을 담은 작은 AI 평가 실험이다. 사람 평가자 간 재현성, 실제 담당자의 부담, 사람이 작성한 답의 다양성에 대한 증거는 추가로 필요하다. 후속 보고서의 ‘실제 회신 기준’ 역시 정책 문구와 평가 규칙을 공개해 검토할 수 있어야 한다.

## 8. 값은 맞히는데 코드는 틀리는가

업로드에 대해 동일 자료를 받은 두 역할을 독립 실행했다. 작성기는 기존처럼 일반 코드를 수정했고, 별도의 예측 역할에는 15·16·17바이트의 결과를 물었다. 예측값을 작성기에 전달하지 않았다. 세 시드와 포함·제외 두 정책의 18개 실행 결과를 비교했다. [S05]

| --- | --- | --- | --- |

이 결과는 구체적인 입력의 결과를 선택할 수 있어도 그 범위를 일반 조건문으로 옮기면서 실패할 수 있음을 보여 준다. 예측 역할에는 세 검사 입력을 명시했으므로 두 지시의 차이를 포함한 결과다. 코드를 쓰던 순간의 내부 추론을 직접 관찰한 것으로 해석할 수는 없다.

이 실험을 바탕으로 입력별 올바른 동작을 보존하면서 실행문으로 변환하는 작성기를 비교했다. 값 예측은 3,996토큰, 코드 수정은 4,537토큰이었다.

## 9. 작성 방식을 바꾼 개발 비교

첫 시도는 동작 메모를 작성한 뒤 일반 편집기에 전달하는 것이었다. 이후 미구현 위치별 동작 선택, 전체 참·거짓 범위 조립, 명시된 값의 예측으로 메모 대체, 동등 비교 표기 보정을 비교했다. [S06] [S07]

| 작성 방식 | 경계 /18 | 업로드 /216 | 센서 /682 | 계측 /38 | 업로드 토큰 |
| --- | --- | --- | --- | --- | --- |
| 기존 직접 편집 | 13 | 153 | 618 | 38 | 4,537 |
| 동작 메모 후 일반 편집 | 3 | 50 | 446 | — | 13,946 |

| 명시된 값 예측으로 메모 대체 | 15 | 182 | 618 | 29 | 5,126 |
| 범위 조립과 동등 비교 표기 보정 | **17** | **215** | **618** | **38** | **6,943** |

216은 업로드 정수 36개를 정책 2개·시드 3개에 반복한 수다. 센서는 두 정책에 순서 341개씩, 계측은 두 정책에 정수 19개씩 적용했다. 대시는 해당 조합의 미측정이다.

채택한 버전은 모든 정수를 참·거짓 범위가 겹치거나 빠짐없이 나누는지 검사한 뒤 미구현 위치에 반환문을 조립했다. 시드 419의 제외 정책이 수학식 등호 ‘=’를 사용한 것을 ‘==’로 받아들이자 같은 모델 응답으로 한 제출이 회복됐다. 마지막 단계는 새 모델 호출 없이 원응답을 재생했다.

기존 업로드 정답 153개 중 152개를 지키고 오답 63개를 고쳤다. 남은 한 건은 포함 정책 시드 887의 16바이트였다. 참·거짓이 전체 범위를 완전히 나눠도 정책 방향을 틀릴 수 있었다. 센서의 오답 64건은 그대로 남았고 계측은 정답 변화 없이 비용이 늘었다. 알려진 실패를 보며 선택한 개발 결과로 읽어야 한다.

## 11. 혼합 업로드 한 회차를 고쳐 경로의 병목을 확인했다

같은 초안·질문 3개·회신 1건·코드 지적 2건·시드 273을 고정했다. 기존 편집기와 지적을 전달한 조건식 편집기를 비교하자 첫 회차가 12/20에서 20/20으로 바뀌었다. 기존 정답 12개를 모두 지키고 반환값이 없던 8개를 고쳤다. [S10] [S11]

| 시점 | 기존 편집 | 지적을 받은 조건식 편집 |
| --- | --- | --- |
| 1회차 직후 | 12/20 | 20/20 |
| 2회차 직후 | 12/20 | 20/20 |
| 3회차 최종 | 12/20 | 20/20 |

기존 코드는 크기가 16을 초과하는 분기에서 False를 반환한 뒤에 True 반환을 들여썼다. 1·2·4·8·12·14·15·16은 반환문 없이 함수 끝에 도달했다. 새 작성기는 ‘양수이며 16 미만 또는 정확히 16’이라는 참 범위를 표현했다.

이 실험에서 **연구자가 두 지적의 수정 위치와 근거를 확인해 적용 경로를 열었다.** 위치 대응표 자체는 모델에 보내지 않았지만 경로 허용에 사람 판단이 들어갔다. 따라서 자동으로 모든 지적을 적절한 편집기에 배정했다고 주장할 수 없다.

후속 두 회차에서는 감시와 편집을 실제 실행했다. 수정 제안 네 건이 모두 위치·범위·구문 검사에서 거절돼 1회차 정답 코드가 유지됐다. 이는 정답 보존의 관찰이며 후속 편집 능력이 향상됐다는 근거로 쓰기 어렵다.

편집만 보면 1회차 1,845 → 1,662토큰이었다. 공통 초안과 감시까지 포함한 세 회차는 14,109 → 13,023토큰이었다. 이 비용 이득은 해당 한 과제·시드에서 확인한 값이다.

## 12. 포함·제외·미언급 세 회신이 드러낸 새 실패

다음에는 연구자가 경로를 지정하지 않아도 되는지, 답이 빠지면 그 부분만 보류하는지를 물었다. 원래 혼합 업로드 문답에서 회신만 세 종류로 바꿨다. 지적은 모델이 미구현 위치에 연결했다. [S12] [S13]

문장별 근거를 고르고 별도 호출이 그 근거를 재심사한 첫 방식은 이미 명시된 답까지 거절했다. 포함·제외 모두 4/20, 미언급은 보류를 인정하는 기준에서 5/20이었다. 후속 답을 받아도 초안이 유지됐다. 근거 검사 호출을 늘리는 것만으로 전달 문제가 해결되지 않았다.

| 기존 작성기를 유지한 방식 | 15 / 16 / 17바이트 | 실제 회신 기준 | 기존 공식 점수 |
| --- | --- | --- | --- |
| 포함 | 허용 / 허용 / 거부 | 20/20 | 20/20 |
| 제외 | 허용 / 거부 / 거부 | 20/20 | 19/20 |
| 미언급 최초 | 보류 / 허용 / 거부 | 12/20 | 13/20 |
| 잘못된 재질문에 답한 뒤 | 허용 / 허용 / 거부 | 19/20 | 20/20 |

미언급의 동작 메모에는 1~15 허용이 이미 있었다. 다음 미응답 판정 호출이 그 범위를 미정으로 바꾸고, 답받지 못한 16은 허용으로 남겼다. 재질문은 “0바이트보다 크고 16바이트보다 작은 파일은 허용하시겠습니까?”였다. Codex 대리 담당자는 물은 부분만 허용한다고 답했다.

16에 대한 제외 회신은 실제로 전달되지 않았다. 이 조건의 올바른 최종 행동은 여전히 16 보류였다. 기존 results.json의 계획된 제외 정책 평가와 실제 전달된 답 기준 재집계를 구분하기 위해 received-policy-results.json을 사용했다. 공식 만점과 담당자 회신 충실도가 어긋나는 사례다.

## 13. 질문 시점의 결정 기록이 필요한 이유

이번 병목은 감시자가 이미 물은 정책이 회신 처리 과정에서 사라졌다는 점이었다. 감시자는 상한값과 상한 일치 처리 모두 물었다. 담당자는 그중 값만 답할 수 있다. 답을 읽은 뒤 함수 전체를 다시 해석하면 모델이 두 결정을 한꺼번에 닫거나 공개 규칙을 다시 미정으로 만들 수 있었다.

이에 질문을 보낼 때 독립적으로 답할 수 있는 결정 항목을 만들고, 공개 규칙과 연결해 저장했다. 이후 회신은 이 기록에서 열린 항목의 값만 채운다. [S15] [S21]

| 업로드의 항목 | 질문 시점에 저장하는 내용 | 상한값·빈 파일 답만 받은 뒤 |
| --- | --- | --- |
| 상한값 | 담당자가 채울 수치 변수 | 16으로 확정 |
| 빈 파일 처리 | 크기 0에 적용할 행동 변수 | 거부로 확정 |
| 상한 일치 처리 | 크기와 상한이 같을 때 적용할 행동 변수 | 열린 상태 유지 |
| 상한 미만 양수 | 공개 명세의 허용 규칙 | 상한에 16을 대입해 허용 |
| 상한 초과 | 공개 명세의 거부 규칙 | 상한에 16을 대입해 거부 |

작성기와 질문 단계가 같은 기록을 읽는다. 닫힌 항목의 답을 다음 회차에 다시 생성하지 않고, 열린 항목만 원래 저장한 단일 질문으로 제시한다. 처음의 묶인 원문은 보존하며, 재질문 문장은 항목화 시점에 모델이 미리 나눠 쓴 문장이다.

이 설계는 질문 발견 이후의 기억과 전달을 개선한다. 감시자가 질문 자체를 빠뜨리거나 항목화가 잘못되면 그 오류도 기록에 남을 수 있다. 기록을 만드는 단계의 정확성은 여전히 별도로 검증해야 한다.

## 14. 결정 기록을 만들고도 실패한 중간 실행

개발 중 최초 자유형 규칙 계획은 행동 변수를 수치 조건 안에 섞어 구조 검사를 통과하지 못했다. 회신을 보내기 전에 실패를 보존하고, 공개 인수·수치·기호 변수에서 만든 입력 조건 후보를 선택하게 바꿨다. 환풍기에서는 일반적인 구현 고려사항 질문을 수치 결정으로 분류해 한 번 더 막혔다. 모델이 일반 의견인지 재판정하게 하고 해당 기록을 보관했다. [S16]

질문 기록이 고정된 뒤에도 첫 회신 추출기는 문장을 빠뜨렸다. “상한은 16바이트입니다. 정확히 상한이면 허용합니다. 0바이트 빈 파일은 거부합니다.”에서 상한 일치 문장 전체가 추출 결과에서 사라졌다. 수치 16을 다시 쓰는 응답에는 닫는 중괄호가 들어가 값 확정이 거절됐다.

| 중간 실행 | 포함 | 제외 | 미언급 | 후속 허용 / 거부 |
| --- | --- | --- | --- | --- |
| 업로드 /20 | 5 | 5 | 6 | 목표 질문만 남지 않아 실행 안 함 |
| 표현 변경 업로드 /20 | 5 | 5 | 6 | 상한값 질문만 남아 실행 안 함 |
| 환풍기 /4 | 4 | 4 | 4 | 3 / 4 |

표현 변경에서는 “용량 제한은 16바이트예요”를 행동 선언으로 읽고 상한 일치 허용에 연결하기도 했다. 환풍기는 한 항목만 열린 상태를 만들었지만 “네, 켜 주세요”의 긍정 답을 처리하지 못해 그 갈래에서 보류가 남았다.

이 결과는 결정 항목을 저장하는 것과 회신 원문을 항목에 정확히 연결하는 것이 각각 필요함을 보여 준다. 구조 수정은 회신 전 준비 실패를 보고 이루어졌고, 다음 문장 처리 수정은 실제 호출 원문을 보고 이루어졌다. 실패 제출은 보존했으며 마지막 제출까지 고정한 뒤 두 방식을 채점했다.

## 15. 최종 파이프라인과 인간 개입 시점

다음 도식은 최신 실행의 실제 역할을 나타낸다. 감시자는 Qwen·Gemma·Phi 세 모델이고, 결정 기록 작성과 회신 연결은 Qwen 메인이 맡는다. 추가 모델 호출에는 상태를 정리하는 역할이 있지만, 독립 감시자 인원을 늘리지는 않았다. [S19] [S21] [S22]

~~~mermaid
flowchart TB
    A["공개 명세 → 메인 초안"]
    B["감시자 A·B·C → 원래 질문·코드 지적"]
    C["메인 → 결정 항목·공개 규칙·적용 범위 저장"]
    D["담당자 → 자연어 회신"]
    E["회신 원문 → 답한 항목만 확정"]
    F["확정값 대입 → 해당 분기만 코드로 조립"]
    G["열린 항목이 있으면 저장한 질문 재사용"]
    H["담당자 추가 답 → 열린 분기만 갱신"]
    I["제출 고정 → 연구자 평가"]
    A --> B --> C --> D --> E --> F
    F -->|"열린 항목 있음"| G
    G --> H --> E
    F -->|"제출 평가 시점"| I
~~~

초기 인간 개입은 감시자의 질문과 결정 기록이 준비된 뒤다. 회신에서 일부 항목만 답했으면 첫 코드는 확정된 부분을 구현하고 나머지를 보류한다. 다음 인간 개입은 그 열린 항목의 재질문에 답하는 시점이다. 마지막 검증에서는 Codex가 사전 정책에 따라 자연어로 대리 답했다.

업로드는 원래 감시 기록을 재사용했다. 환풍기는 새 초안과 기존 세 감시자의 질문을 한 번 생성했다. 이후 같은 최초 미언급 제출을 복제해 허용·거부 답을 각각 전달했다. 두 반대 답을 같은 대화에 순서대로 넣은 실험은 아니다.

이 마지막 단계는 감시자를 매 회차 다시 돌리는 완전한 3회차 비교가 아니다. 이미 발견한 질문에서 빠진 답을 보완하는 최초 회신과 추가 회신을 검증했다. 후속 감시 호출 없이 열린 질문을 재사용한 효과가 포함된다.

## 16. 원문 보존과 국소 수정이 구현된 방식

최종 회신 처리기는 문장 경계로 원문 전체를 순회한다. 복합 문장은 필요할 때 절로 나누되 추출에서 빠진 나머지 문구도 보존한다. 각각이 현재 열린 어떤 질문에 직접 답하는지는 모델이 선택한다. [S21] [S22]

| 구성 요소 | 수행하는 일 | 오류를 줄이는 이유 |
| --- | --- | --- |
| 결정 항목 기록 | 수치와 행동을 별개 항목으로 저장 | 상한값만 답한 회신으로 등호 정책을 닫기 어렵게 한다. |
| 공개 규칙 보존 | 답변 전에 입력 조건과 반환 방향 저장 | 이미 정해진 상한 미만 허용을 재질문 단계가 다시 바꾸는 일을 줄인다. |
| 문장 전체 순회 | 모델 요약에서 누락될 수 있는 문장도 처리 | 끝점 정책 한 문장이 통째로 사라지는 경로를 줄인다. |
| 원문 수치 추출 | 수치 선언의 단일 정수를 직접 취함 | 모델이 16을 다시 쓰다가 다른 토큰을 내는 문제를 피한다. |
| 열린 항목 제한 | 회신을 현재 티켓의 항목에 연결 | 다음 회차가 기존 확정값을 임의로 뒤집는 범위를 제한한다. |
| 국소 코드 조립 | 미확정 문장만 확정 행동으로 교체 | 나머지 분기를 재작성하면서 발생하는 퇴행을 줄인다. |

수치 선언은 한국어 종결 표현과 일부 영어 표현을 포함한 패턴으로 판별한다. 따라서 범용적인 자연어 이해가 완성된 것은 아니다. 소수·한글 수사·복잡한 단위 변환·인용 속 숫자·조건부 회신은 추가 검증이 필요하다.

환풍기 초안에는 담당자 정책을 이미 단정한 반환문이 있었다. 불리언 입력 조합을 대조해, 질문의 결정 하나에만 속하는 반환문을 보류문으로 다시 열었다. 공개 동작을 함께 처리하는 반환문은 자동으로 열지 않는다. 업로드는 원래 존재한 미구현 위치를 편집했다.

관찰된 후속 수정은 보류문 한 줄의 True 또는 False 교체였다. 이는 해당 구조와 입력 범위에서의 보존 근거다. 임의의 프로그램 전체에서 모든 국소 수정이 안전하다는 보장은 아니다.

## 17. 업로드의 변경 전후와 반대 답 검증

현재 회신 처리기는 기존 작성기의 미언급 최초 12/20을 20/20으로 개선했다. 아래 ‘회신 기준’은 명세와 실제 받은 답에 맞는 보류까지 성공으로 센다. 기존 공식 정책은 정확히 상한을 허용한다. [S13] [S18]

| 현재 상태 | 15 | 16 | 17 | 회신 기준 /20 | 공식 /20 | 추가 질문 |
| --- | --- | --- | --- | --- | --- | --- |
| 포함 답 최초 | 허용 | 허용 | 거부 | 20 | 20 | 0 |
| 제외 답 최초 | 허용 | 거부 | 거부 | 20 | 19 | 0 |
| 미언급 최초 | 허용 | 보류 | 거부 | 20 | 19 | 1 |
| 미언급 뒤 허용 회신 | 허용 | 허용 | 거부 | 20 | 20 | 0 |
| 미언급 뒤 거부 회신 | 허용 | 거부 | 거부 | 20 | 19 | 0 |

재사용한 질문은 “정확히 상한 크기에 해당하는 파일을 허용하는지 확인해주세요.”였다. 같은 최초 코드에 “네, 허용합니다.”와 “아니요, 거부합니다.”를 각각 주었다. 최초부터 포함·제외를 받은 코드와 후속 갈래는 각각 같은 동작을 보였다.

업로드 -2~33과 ±1,000,000의 38개 대조 입력도 다섯 상태 모두 통과했다. 실제 제출의 조건문이 정수 상수 비교만 사용하는지 확인한 뒤, 경계와 경계 사이의 대표 입력을 검사했다. 이 제한된 언어에서 비교식의 진릿값은 같은 구간 안에서 변하지 않으므로 정수 전체에 대한 동작 차이를 확인할 수 있었다. 두 갈래가 달라지는 입력은 정확히 16이었다.

기존 미언급 후속 코드는 1~15만 고치고 답받지 않은 16을 허용해 공식 20/20, 회신 기준 19/20이었다. 최신 미언급 첫 코드는 공식 19/20이지만 회신 기준 20/20이다. 발표에서는 정책 확정 여부를 점수와 함께 보여 줘야 한다.

## 18. 표현을 바꾼 회신과 새 환풍기 과제

표현 변경에서는 상한·빈 파일 답을 “빈 파일은 받지 않습니다. 용량 제한은 16바이트예요.”로 바꿨다. 포함에는 “한도와 딱 같은 크기도 올릴 수 있어요”, 제외에는 “한도와 딱 같은 크기는 올릴 수 없어요”를 덧붙였다. 업로드 원래 표현과 같은 항목 기록을 사용했다. 다섯 상태 모두 회신 기준 20/20, 대조 38/38이었다. [S17] [S18]

새 과제는 공부방 환풍기였다. 높은 이산화탄소 신호만 있으면 켜고, 정숙 신호만 있으면 끈다는 것은 공개 명세에 있었다. 두 신호가 동시에 있을 때와 모두 없을 때는 담당자 결정이었다. 최초 회신에서는 모두 없을 때 끈다는 정책을 공통 제공하고 동시 발생 정책을 켜기·끄기·미언급으로 바꿨다.

| 두 신호의 조합 | 공개 규칙·공통 회신 | 동시 정책 미언급 | 켜기 회신 후 | 끄기 회신 후 |
| --- | --- | --- | --- | --- |
| 높음 없음·정숙 없음 | 담당자가 끄기로 확정 | 끔 | 끔 | 끔 |
| 높음 없음·정숙 있음 | 공개 명세에서 끔 | 끔 | 끔 | 끔 |
| 높음 있음·정숙 없음 | 공개 명세에서 켬 | 켬 | 켬 | 켬 |
| 높음 있음·정숙 있음 | 동시 정책의 답 필요 | 보류 | 켬 | 끔 |

직접 켜기·끄기 답까지 포함한 다섯 상태 모두 네 조합을 맞혔다. 후속 질문은 동시 발생 시 우선순위를 어떻게 설정하는지였으며 “네, 켜 주세요”와 “아니요, 꺼 주세요”를 각각 받았다. 이 답은 행동을 명시하므로 열린 질문을 닫을 수 있었다.

불리언 두 입력의 네 조합은 이 과제의 전체 입력 공간이다. 다만 함수가 작고 결정 항목도 두 개다. 환풍기 초기 질문의 일반 의견 분류와 초안의 단정 반환 처리 때문에 파이프라인을 수정했으므로 최종 설계에 쓰지 않은 독립 시험으로 제시할 수 없다.

## 19. 비용은 무엇까지 포함했는가

최신 회신 처리 실행의 서로 다른 요청은 15회였고 입력 2,950·출력 214, 합계 3,164토큰이었다. 같은 요청이 여러 갈래에서 재사용되므로 조건별 사용량의 합과 다르다. 결정 항목·공개 규칙 준비, 최초 초안·감시 비용은 이 3,164에 들어 있지 않다. [S18] [S19]

| 기록 범위 | 서로 다른 호출 | 합계 토큰 | 포함 범위 |
| --- | --- | --- | --- |
| 문장별 근거 재심사 방식 | 52 | 26,517 | 세 최초 회신과 각각의 후속 편집 |
| 기존 작성기·미응답 재판정 방식 | 14 | 9,354 | 포함·제외·미언급과 한 후속 회신 |

첫 개발 묶음 13,310은 환풍기 초안·감시 2,985, 새 결정 기록 관련 호출 9,569, 이전 동일 요청 재사용 756으로 구성된다. 이미 실패한 준비 호출도 이 묶음에 포함한다. 최신 회신 처리의 3,164와 합치면 연결된 두 개발 폴더의 고유 기록 비용은 16,474다. 이는 완성 파이프라인 한 번의 운영 비용과 다르다.

조건별 실행 비용을 계산하려면 공유된 준비도 각 조건에 한 번 포함해야 한다. 저장된 업로드 준비는 4호출·2,586토큰, 환풍기 준비는 3호출·1,380토큰이었다. 다음 장은 이 준비를 포함하고 초안·최초 감시를 제외한, 회신 이후 비교 비용이다.

비용 범위가 다른 실험끼리 총 토큰만으로 절감률을 계산하면 잘못된 결론이 생긴다. 후기의 성공은 제한된 표현·편집 절차와 재사용을 포함한 전체 시스템의 효과이며, 토큰을 동일하게 맞춘 최종 대조 실험은 아직 없다.

양쪽 최초 비용에는 각 방식의 위치 판단·준비·회신 처리·필요한 질문 단계가 포함된다. 초안과 최초 감시 호출은 제외했다. 이전 미언급 후속은 1~15만 물었으므로 최신의 16 허용·거부 갈래와 동일 문답 대조가 아니다. 이전 후속까지의 합은 5,125토큰이었다. [S13] [S15] [S19]

표현 변경 업로드는 준비 포함 최초 포함·제외 각각 3,187, 미언급 2,976, 후속 허용 3,163·거부 3,165토큰이었다. 환풍기는 최초 켜기 1,870·끄기 1,869·미언급 1,623, 후속 두 갈래 각각 1,829토큰이었다. 환풍기의 초안·최초 감시 2,985토큰을 포함한 전체 비용은 별도로 더해야 한다.

다른 단계의 비용 변화도 일관된 방향은 아니었다. 최초 업로드 작성기 개선은 4,537 → 6,943토큰으로 늘었고, 혼합 업로드의 수동 범위 연결은 첫 편집 1,845 → 1,662로 줄었다. 전체 10조건 재검증에서는 Qwen 동종 감시 전이 비용이 84,630 → 85,629로 늘면서 점수는 같았다. [S06] [S08] [S10]

이 연구가 뒷받침하는 것은 비용을 줄이는 유일한 구조가 아니라, 어느 단계의 추가 비용이 어떤 오류 감소와 연결됐는지 추적할 수 있는 방식이다.

## 21. 결과의 의의와 감시자의 역할

**답변의 효과를 동작 차이로 보여 줬다.** 같은 미언급 상태에서 반대 답을 받았을 때 두 코드가 목표 입력에서만 다르다는 검증은, 고정 정책에서의 만점보다 사용자 선택을 따르는 능력을 직접 설명한다. 공개 규칙과 영향 밖의 동작까지 함께 검사했다.

**질문의 발견에서 코드 반영까지 병목을 나눴다.** 예약은 편집 적용, 업로드는 적용 범위와 미응답 판정, 문의는 실제 반복 순서, 센서는 종료 범위에서 실패했다. 이후 전체 비교에서는 새 편집 경로 선택 자체가 막혔다. 같은 오답에 같은 처방을 적용하기 어려운 이유가 드러났다.

**감시자가 추가로 찾은 내용이 유효한 자산이 되려면 전달 구조가 필요하다.** 이번 업로드에서 원래 혼합 감시가 이미 끝점을 물었다는 사실은 중요하다. 질문을 추가하지 않고 회신 이후를 바꿔 성과를 얻었으므로 이 사례의 실패를 감시자 발견 부족으로 설명하기 어렵다.

한편 최신 결과는 감시자 세 명이 자체 검토보다 우수하다는 새로운 대조 결과를 제공하지 않는다. 업로드는 기존 혼합 질문을 고정했고 환풍기는 혼합 팀만 생성했다. 최신 기록·회신 처리기를 자체 검토에도 같은 조건으로 붙여야 감시 구조의 순효과를 비교할 수 있다.

| 발표에서 제시할 수 있는 주장 | 함께 밝혀야 할 범위 |
| --- | --- |
| 이미 확보한 질문과 자연어 답을 더 정확히 구현하도록 개선했다. | 두 과제·한 시드·제한된 함수 편집기 |
| 정보가 빠진 부분만 보류하고 추가 답으로 그 부분을 바꿨다. | 업로드 16, 환풍기 동시 신호의 작은 짝실험 |
| 감시 의견의 가치가 전달·구현 병목 때문에 총점에 나타나지 않을 수 있다. | 해당 실행에서 확인한 구체적 경로 |
| 기록 기반 처리가 다른 정책에도 확장될 가능성이 있다. | 표현 확장과 독립 과제 검증이 필요한 연구 가설 |

## 22. 현재 구현과 연구 설계의 한계

현재 코드 편집기는 정수 인수 하나 또는 불리언 인수 최대 여섯 개를 받는 제한된 결정 함수를 지원한다. 숫자·비교·논리식과 단순 분기를 다룬다. 시간 문자열 여러 개, 상태 변화, 반복 컬렉션, 예외 우선순위가 있는 큰 함수로의 확장은 아직 확인하지 않았다. 예약·문의·센서 전체를 최신 방식으로 다시 검증한 결과도 없다. [S21] [S22]

| 남은 위험 | 현재 코드·실험에서의 의미 |
| --- | --- |
| 질문을 잘못 나누거나 적용 범위를 잘못 연결 | 잘못된 구조가 이후 회차에도 보존될 수 있다. |
| 확정 정책의 변경·철회 | 현재 수신기는 열린 항목을 중심으로 답을 받아, 이미 닫힌 정책을 사용자가 뒤집는 운영 흐름은 별도로 필요하다. |
| 복합 문장·다양한 수치 표현 | 일부 종결 패턴과 정수 추출에 의존한다. 조건부 답·부정 중첩·단위 변환은 미검증이다. |
| True의 의미 | 실행·허용·켜기 중심 해석을 쓴다. 위험 여부처럼 True가 부정적 의미인 함수는 추가 검증이 필요하다. |
| 규칙 간 충돌 | 같은 회신의 상반된 값은 확정하지 않지만, 복잡한 정책 충돌의 해결 절차는 충분하지 않다. |
| 코드 밖의 설명 | 국소 수정은 기존 주석·문서·예시를 갱신하지 않을 수 있다. 환풍기 원래 설명에는 추정 정책이 남아 있다. |

원문 구절을 저장한다고 그 문장과 적용 항목의 의미 연결까지 자동으로 옳아지는 것은 아니다. 새 입력에서 해당 의미를 잘못 연결하면 구조 검사를 통과할 수 있다.

후기 데이터는 재사용한 개발 과제와 한 시드에 집중됐다. 샘플 입력이 많아도 하나의 정책 분기를 공유하므로 독립 시행 수를 늘려 해석하면 안 된다. Codex가 담당자 역할을 대신했고 사람 두 명의 독립 재판정도 확보하지 않았다. 현재 운영 성공과 일반화 가능성을 함께 발표하되 그 차이를 분명히 해야 한다.

## 23. 다음 검증을 설계한다면

이 보고서에서는 추가 실행을 하지 않았다. 후속 연구의 우선순위는 최신 구조를 고정한 뒤 개발에 쓰지 않은 요구사항과 회신에서 같은 목표를 검증하는 것이다.

| 우선순위 | 검증 질문 | 통제와 관찰 지표 |
| --- | --- | --- |
| 1 | 새 정책·표현에서도 열린 항목을 정확히 보존하는가 | 구조 고정 후 새 과제·여러 시드·조건부 답·미정 답·복합 답을 사용한다. 잘못 닫힌 항목과 불필요하게 열린 항목을 모두 센다. |
| 2 | 같은 작성기를 쓰면 감시자가 자체 검토보다 더 필요한 정책을 찾는가 | 단독·자체 검토·동종 감시·혼합 감시에 동일 기록·수정 절차를 적용한다. 질문 가능 횟수와 답변 정책 범위를 맞춘다. |
| 3 | 성과 중 어느 부분이 코드의 제한된 표현 덕분인가 | 같은 문답에서 기존 편집, 결정 기록만, 원문 보존만, 둘 모두를 비교한다. 토큰 상한 대조도 별도로 둔다. |
| 4 | 담당자가 기존 답을 바꾸거나 모순된 답을 주면 어떻게 되는가 | 정책 개정과 충돌 상태를 기록한다. 변경된 정책의 영향 범위와 기존 정답 보존을 검사한다. |
| 5 | 실제 인간에게도 질문과 답변이 효율적인가 | 묶인 질문과 단일 질문의 응답 시간·누락·재질문·이해도·최종 반영을 비교한다. |

학술제 발표에서는 다음 인과관계를 실제 문답·코드와 함께 제시할 수 있다. 감시자는 상한값과 끝점을 모두 물었다. 담당자는 값만 답했다. 이전 작성기는 끝점을 임의로 허용하고 이미 아는 범위를 재질문했다. 새 기록은 답받은 항목만 닫고 끝점을 보류했다. 끝점에 답하자 그 한 분기만 바뀌었다.

이는 멀티 에이전트의 메리트를 찾는 연구와 연결된다. 감시자의 추가 발견이 코드까지 살아남을 기반을 먼저 갖추면, 이후에는 질문 발견의 이득과 작성기의 이득을 같은 조건에서 비교할 수 있다.
