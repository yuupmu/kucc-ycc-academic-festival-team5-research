## 01. Multi Agent Lab: 연구 배경과 실험 경과

### 이 슬라이드가 필요한 이유

발표 초반에 시스템의 목적과 연구의 진행 단계를 알려주기 위한 슬라이드입니다. 청중이 “이미 우수성이 입증된 모델을 소개하는 발표”로 오해하지 않도록 범위를 설정합니다.

### 슬라이드 본문 — 현재 PPT 기준

> 어떤 연구인가
>
> 코드를 작성하는 AI 옆에 검토용 AI를 두고,
>
> 사람에게 확인해야 할 사항을 찾아 질문하게 하는 연구입니다.
>
> 무엇을 발표하는가
>
> 이 구조를 어떻게 구현했고 어떤 문제로 시험했는지 설명합니다.
>
> 이어서 현재 비교 방식의 한계와 다음 실험 계획을 제시합니다.
>
> 현재 연구 단계
>
> 실제로 작동하는 환경과 예비 실험 결과를 확보했습니다.
>
> 단일 AI보다 더 정확하거나 효율적인지는 아직 비교 검증이 필요합니다.
>
> 핵심 질문: 여러 AI가 검토하는 방식은 같은 결과를 더 적은 비용으로 만들 수 있을까?

### 발표할 때 풀어서 설명하기

이 프로젝트는 새로운 언어모델을 학습한 연구가 아닙니다. 기존 AI 모델을 작업 담당과 검토 담당으로 나누고, 필요한 순간에 사람에게 질문하게 하는 실행 방식을 만들었습니다. 예를 들어 예약 프로그램을 만들 때 취소 마감이나 휴무일이 요구사항에 없다면 AI가 임의로 결정할 수 있습니다. 우리는 검토 담당 AI가 이런 빈칸을 찾아내고, 사람의 답을 받은 뒤 작업 담당 AI가 코드를 고치도록 연결했습니다. 오늘은 이 환경의 구현과 예비 실험, 그리고 앞으로 어떤 비교를 해야 연구적 의미가 있는지를 설명하겠습니다.

### 해석할 때 주의할 점

이 발표에서 “제안 구조”는 학습한 새 모델이 아니라 여러 모델 호출을 연결한 작업 방식입니다. 예비 실험은 본격 비교 전에 동작과 문제점을 확인하는 단계입니다.

### 다음 슬라이드 연결

먼저 코드가 실행된다는 것과 사용자가 원하는 프로그램을 만들었다는 것이 왜 다른지 보겠습니다.

## 02. 왜 사람에게 질문하는 AI가 필요한가?

### 이 슬라이드가 필요한 이유

인간 개입이 왜 필요한지 설명합니다. 단순히 에이전트 수를 늘리는 데 목적이 있는 것이 아니라, 자동 검증만으로 해결할 수 없는 요구사항의 빈칸을 다루려는 것입니다.

### 슬라이드 본문 — 현재 PPT 기준

> 실행되는 코드도 요구와 다를 수 있습니다
>
> “예약 취소 프로그램을 만들어라”라는 요청만으로는
>
> 취소 마감, 휴무일, 예외를 알 수 없습니다. AI가 임의로 정할 수 있습니다.
>
> 계산 오류와 결정이 필요한 문제를 구분해야 합니다
>
> 날짜 계산 오류는 AI가 테스트로 확인할 수 있습니다.
>
> “휴무일에는 취소를 허용할까?”는 운영자가 정해야 하는 규칙입니다.
>
> 연구 목적
>
> 검토용 AI가 빠진 규칙을 찾아 질문하고,
>
> 사람의 답변을 코드 수정으로 연결할 수 있는지 확인하려고 했습니다.
>
> 질문을 많이 하는 것보다, 실제로 필요한 질문을 하고 답을 반영하는 것이 중요합니다.

### 발표할 때 풀어서 설명하기

예약 취소가 언제나 가능한 프로그램도 문법 오류 없이 실행됩니다. 그러나 운영자가 하루 전까지만 취소를 허용하려 했다면 그 프로그램은 잘못된 결과입니다. 이런 차이는 모델이 계산을 잘하는 것만으로 해결되지 않습니다. 아직 전달받지 않은 운영 규칙을 알아야 하기 때문입니다. 반대로 날짜 형식이 잘못됐거나 자원이 음수가 되는 문제는 가능한 한 시스템 안에서 먼저 검증해야 합니다. 따라서 이 연구의 관심은 사람에게 모든 것을 묻는 것이 아니라, AI가 확인할 수 있는 문제와 사람이 결정해야 하는 문제를 구분하는 데 있습니다.

### 해석할 때 주의할 점

단일 에이전트도 질문할 수 있습니다. 별도의 검토자를 두는 것이 추가로 도움이 되는지는 후속 비교에서 확인해야 합니다.

### 다음 슬라이드 연결

이 목적을 구현하기 위해 작업 담당과 검토 담당을 어떻게 나눴는지 설명하겠습니다.

## 03. 무엇을 구현했는가?

### 이 슬라이드가 필요한 이유

아이디어 제안과 실제 구현을 구분합니다. 청중이 화면만 만든 것인지, 실제 AI가 실행되고 평가까지 이어지는지 이해하도록 합니다.

### 슬라이드 본문 — 현재 PPT 기준

> 작업 담당 1개
>
> 메인 AI가 계획을 세우고
>
> 코드를 작성·수정합니다.
>
> 검토 담당 3개
>
> 감시자마다 모델과 관점을
>
> 직접 설정할 수 있습니다.
>
> 실행과 기록
>
> 질문·답변, 코드 버전,
>
> 검사와 최종 점수를 저장합니다.
>
> 실제 개발 화면: 메인 모델과 감시자별 역할 설정

### 발표할 때 풀어서 설명하기

메인 에이전트는 코드를 만드는 담당자입니다. 감시자라는 이름의 세 에이전트는 그 코드를 직접 바꾸지 않고 검토합니다. 실행 관리 프로그램이 각자에게 자료를 전달하고, 질문과 답변을 기록하며, 생성한 코드를 검사합니다. 이 일반 프로그램까지 포함한 전체 환경이 Multi Agent Lab입니다. 초기에는 고정된 질문을 보여주는 화면 데모였지만, 이후 실제 API를 연결해 모델이 계획과 코드와 질문을 생성하도록 바꿨습니다. 코드 버전과 실패 기록을 저장했기 때문에 최종 점수뿐 아니라 도중에 무슨 일이 있었는지도 확인할 수 있습니다.

### 해석할 때 주의할 점

실제 구현은 메인 1개와 감시자 3개입니다. 여러 작업 담당 AI가 각각 다른 프로그램을 병렬 개발하는 범용 시스템은 아닙니다.

### 다음 슬라이드 연결

실행 버튼을 누른 뒤 어떤 순서로 일이 진행되는지 한 회차를 따라가 보겠습니다.


### 추가한 화면 자료

#### 설정 화면

개발 당시 저장한 메인 모델·감시자 설정 화면을 오른쪽에 제시합니다. 메인 모델 선택과 세 감시자 역할 입력란을 가리키며 설명합니다.

## 04. 실제 실행 파이프라인

### 이 슬라이드가 필요한 이유

앞 장에서 소개한 구성 요소들이 실제로 어떤 순서로 연결되는지 보여줍니다. 특히 검토자가 코드를 직접 수정하는 것이 아니라, 문제를 찾고 필요한 질문을 제안하며 메인이 수정한다는 역할 분담을 설명합니다.

### 슬라이드 본문 — 현재 PPT 기준

> 과제와 모델을 설정하면, 메인이 작성하고 세 검토자가 확인하며 사람의 답을 반영합니다.
>
> ① 메인 AI
>
> 계획을 세우고
>
> 코드를 작성·수정
>
> ② 검사와 상태 공유
>
> 문법·공개 검사를 실행하고
>
> 계획·코드·검사 결과를 기록
>
> ③ 검토자 3명이 병렬 검토
>
> 같은 시점의 정보를 읽고
>
> 추가 검사·질문의 필요성을 판단
>
> ④ 사람에게 질문
>
> 웹 화면에서 부족한 조건에 답변
>
> ⑤ 답변 기록·반영
>
> 답변을 공유 상태에 기록
>
> 확인이 필요할 때
>
> 수정 후 다시 검사·검토
>
> 검토자는 코드를 직접 고치지 않습니다. 답변이 오면 세 검토자의 종료를 모두 기다리지 않고 반영합니다.
>
> 완료와 채점
>
> 현재 코드 검토 완료 + 미답변 질문 없음 + 검사 통과 + 메인의 완료 판단
>
> → 프로젝트 완료 → 사용자가 ‘테스트하기’를 눌러 숨겨진 평가 문항으로 별도 채점

### 발표할 때 풀어서 설명하기

이 슬라이드는 실제 구현의 핵심 실행 흐름을 요약합니다. 먼저 과제, 메인 모델, 검토자 모델과 프롬프트를 설정합니다. 메인은 계획을 세우고 코드를 작성합니다. 계획 단계부터 검토 요청을 시작할 수 있으므로 모든 작업이 한 줄로 직렬 실행되는 것은 아닙니다.

각 코드 버전에는 문법 검사와 공개 검사가 적용됩니다. 세 검토자는 같은 시점의 계획, 코드, 검사 결과와 인간 답변을 복사한 정보를 각각 받아 병렬 검토합니다. 검토자는 코드를 직접 수정하지 않고 추가 검사나 인간 질문을 제안합니다. 질문은 웹사이트의 답변 입력창으로 연결되고, 입력된 답변은 다음 메인 호출에 포함됩니다. 답변이 먼저 들어오면 다른 검토자의 응답을 모두 기다리지 않고 수정에 반영합니다.

인간 답변이 필요하지 않아도 검사 실패나 미완료 판단이 있으면 수정 주기를 다시 진행할 수 있습니다. 자동 수정에는 한도가 있으며, 오류나 한도 도달 시 일시정지 후 이어갈 수 있습니다.

완료는 최신 코드에 대한 세 검토자의 검토, 미답변 질문 없음, 검사 통과, 메인의 완료 판단을 함께 확인합니다. 이 단계의 공개 검증은 최종 벤치마크 점수와 다릅니다. 완료 후 사용자가 테스트하기를 누를 때 숨겨진 평가 문항으로 별도 채점합니다.

### 흐름도를 가리키며 설명하기

1. **상단 왼쪽 — 메인 AI:** 과제를 받고 계획과 코드 초안을 만듭니다. 사람에게 물을 필요가 없는 오류는 검사 결과를 보고 다시 고칠 수 있습니다.
2. **상단 가운데 — 검사와 상태 공유:** 현재 계획, 코드 버전, 검사 결과를 기록합니다. ‘공유 상태’는 AI들이 확인할 수 있도록 저장한 작업 기록을 뜻합니다.
3. **상단 오른쪽 — 세 검토자:** 같은 시점의 자료를 각각 받아 살펴봅니다. ‘병렬’은 한 검토자가 끝나야 다음 검토자가 시작하는 방식이 아니라, 여러 검토를 동시에 진행한다는 뜻입니다.
4. **하단 오른쪽 — 인간 답변:** 누락된 운영 규칙처럼 사람이 정해야 하는 문제가 발견되면 웹 화면에 질문을 표시합니다.
5. **하단 가운데와 되돌아가는 화살표 — 답변 반영:** 답을 기록하고 메인에게 전달합니다. 메인은 다음 코드를 작성하고 검사·검토를 다시 진행합니다.
6. **맨 아래 — 완료와 채점:** 완료 조건을 충족한 뒤 사용자가 ‘테스트하기’를 누릅니다. 실행 중 검사와 숨겨진 평가 문항을 통한 최종 채점은 서로 다릅니다.

### 해석할 때 주의할 점

화살표는 핵심 데이터 흐름을 단순화한 그림입니다. 계획 단계에서도 검토가 시작될 수 있고, 질문이 없어도 검사 실패나 미완료 판단에 따라 수정이 반복될 수 있습니다. 모델의 내부 생각을 실시간으로 읽는 구조는 아닙니다. 검토자는 계획·코드처럼 제출된 결과를 확인합니다.

### 다음 슬라이드 연결

이 그림에서 사람이 답하는 부분이 실제 웹 화면에서는 어떻게 구현되어 있는지 보겠습니다.

앞 장의 파이프라인 중 ‘사람에게 질문하고 답을 반영하는 부분’을 실제 웹 화면으로 확인합니다. 청중이 추상적인 구조와 사용자가 하는 행동을 연결해서 이해하도록 합니다.

### 슬라이드 본문 — 현재 PPT 기준

### 발표할 때 풀어서 설명하기

흐름은 작성, 검토, 질문, 답변, 수정의 반복입니다. 메인이 처음부터 코드를 모두 완성해야만 감시가 시작되는 것은 아닙니다. 계획이 나왔을 때도 검토하고, 코드가 한 버전 나올 때마다 다시 검토합니다. 검토자 중 한 명이 질문을 제출하면 다른 검토자가 끝날 때까지 기다리지 않고 사람에게 보여줄 수 있습니다. 답변은 기록에 저장되어 다음 메인 호출과 검토 호출에 전달됩니다. 마지막에는 모델이 만든 자체 검사와 별도로 준비한 정답 세트로 평가합니다. 이렇게 해야 모델이 스스로 정한 검사만 통과한 결과를 최종 성공으로 오해하지 않을 수 있습니다.

### 해석할 때 주의할 점

모델이 “답변을 반영했다”고 보고한 사실과 실제로 올바르게 반영한 사실은 다릅니다. 현재 구조는 보고와 검사 결과를 기록하며, 의미적으로 완벽한 반영을 보장하지 않습니다.

### 다음 슬라이드 연결

이 흐름이 제대로 작동하는지 보기 위해 처음에는 단순한 문제를 쓰고, 이후 여러 사건이 연결되는 문제로 확장했습니다.

## 06. 왜 100문항에서 150세트로 확장했는가?

### 이 슬라이드가 필요한 이유

“왜 문제 체급을 높였는가”에 답합니다. 100에서 150으로 숫자만 늘린 것이 아니라, 정책 하나가 여러 후속 결과에 영향을 주도록 문제의 구조를 바꿨다는 점이 중요합니다.

### 슬라이드 본문 — 현재 PPT 기준

> 처음: 예약 취소 100문항
>
> 취소 가능 여부만 판단하는 문제라 규칙을 모두 알려주면
>
> 풀이가 짧아지고, 점수 차이를 보기 어렵다는 우려가 생겼습니다.
>
> 확장: 여러 사건이 연결되는 150세트
>
> 예약·취소·변경 후 대기자와 남은 자원까지 달라지게 했습니다.
>
> 한 세트에 8~18개 사건을 넣어 처리 결과와 알림까지 확인합니다.
>
> 사이트에서 두 과제를 선택할 수 있습니다
>
> 기존 100문항을 유지한 채 새 과제를 추가했습니다.
>
> 하지만 확장 과제에서도 150/150이 나와 효율 비교가 필요해졌습니다.
>
> 현재 로컬 사이트 캡처
>
> 150세트 과제 선택
>
> 문항 수만 늘린 것이 아니라, 한 결정이 후속 결과에 미치는 영향을 복잡하게 만들었습니다.

### 발표할 때 풀어서 설명하기

예약 취소 문제는 조건을 확인한 뒤 참 또는 거짓 하나를 반환합니다. 필요한 규칙을 모두 알게 되면 구현이 비교적 짧고, 좋은 모델에서는 만점이 쉽게 나와 구조의 효과를 구별하기 어려울 수 있습니다. 그래서 더 복잡한 작업에서도 검토와 인간 답변이 도움이 되는지 볼 과제가 필요했습니다. 새 문제에서는 좌석과 장비를 동시에 배정하고, 자원이 없으면 대기시키며, 취소 후에는 다음 사람을 자동으로 올려야 합니다. 예를 들어 대기 순서가 앞선 큰 그룹을 기다릴지 뒤의 작은 그룹을 먼저 받을지에 대한 인간의 답이 여러 결과를 바꿉니다. 총 150세트는 15개 유형을 10개씩 변형한 것이고, 전체 사건 수는 1,690개입니다. 그러나 이 확장 문제에서도 만점이 나와 최종 점수만으로 비교하기 어려운 문제는 남았습니다.

### 해석할 때 주의할 점

“만점이 너무 쉽게 나와 과제를 어렵게 했다”는 연구 동기를 설명하되, 단일 모델과의 통제 비교로 난이도 효과를 입증했다는 뜻은 아닙니다. 기록상 과제 확장 당시의 명시적 문제의식은 기존 과제가 너무 단순하다는 것이었습니다.

### 다음 슬라이드 연결

그렇다면 실제 실행 기록에서 어느 정도 결과가 나왔는지 보겠습니다.


### 추가한 화면 자료

#### 과제 선택 화면

2026-11-10 현재 로컬 사이트에서 150세트 과제를 선택한 화면입니다. 기존 100문항 과제를 지우지 않고 선택 항목을 추가했다는 점을 설명합니다. 새 성능 실험을 돌린 화면은 아닙니다.

## 07. 실제로 실행했을 때 어떤 결과가 나왔는가?

### 이 슬라이드가 필요한 이유

실제 수치와 그 수치로 말할 수 있는 범위를 함께 제시합니다. 완료된 실행만 보여주면 전체 실험이 모두 성공한 것처럼 보일 수 있어 미완료 상태도 설명합니다.

### 슬라이드 본문 — 현재 PPT 기준

> 총 10건 중 4건에서 최종 채점까지 완료
>
> 나머지는 중단 3건, 실패 2건, 일시 정지 1건이었습니다. (모델을 낮게 설정한 경우라서, 출력물의 요구 형식을 지키지 못함)
>
> 채점하지 못한 실행을 0점으로 계산하지는 않았습니다.
>
> 채점 결과
>
> 예약 취소 과제는 90/100, 100/100, 100/100이었습니다. (90점은 의도적 거짓 답변을 사용)
>
> 더 복잡한 자원 배정 과제도 한 실행에서 150/150을 기록했습니다.
>
> 이 결과가 보여주는 것
>
> 질문과 인간 답변, 코드 수정, 채점까지 실제로 연결됐습니다.
>
> 다만 모델·답변·프로그램 버전이 달라 이 결과만으로 모델 간 우열은 알 수 없습니다.
>
> 현재 결과는 작동과 문제점을 확인한 예비 실험이며, 공정한 조건의 비교 실험은 아닙니다.

### 발표할 때 풀어서 설명하기

로컬 DB에서 확인한 실행은 10건입니다. 이 중 네 건이 최종 채점까지 이어졌고, 취소 문제 세 건과 자원 배정 문제 한 건입니다. 이 네 건의 점수는 각각 90점, 100점, 100점, 그리고 150점 만점에 150점이었습니다. 취소 90점과 100점은 같은 실행에서 점수가 오른 것이 아니라 서로 다른 실행입니다. 인간 답변의 내용과 횟수도 달랐습니다. 따라서 감시자가 몇 점을 올렸다고 계산하거나 어떤 모델이 더 낫다고 말하기에는 조건이 맞지 않습니다. 지금 확인한 것은 만들어 둔 실험 절차가 실제로 작동했고, 몇몇 조건에서 정답에 도달했다는 것입니다.

현재 PPT에 추가한 실험 맥락도 함께 설명해야 합니다. 90/100 실행에는 의도적으로 거짓인 인간 답변을 사용했습니다. 따라서 이 점수를 정상적인 정책 정보를 제공한 실행과 같은 조건의 모델 성능으로 비교해서는 안 됩니다. 잘못 전달된 정보가 결과에 영향을 줄 수 있다는 사례로 설명하는 것이 적절합니다.

또한 낮은 모델 설정에서 요구한 출력 형식을 지키지 못한 경우가 있었다는 설명을 반영합니다. 여기서 출력 형식 오류는 코드의 정답률이 낮다는 것과 다릅니다. 프로그램이 다음 단계에서 읽을 수 있는 약속된 형태로 응답하지 못해 실행이 진행되지 않는 문제입니다. 다만 중단·실패·일시 정지는 서로 다른 상태이므로, 미채점 여섯 건 전체가 같은 원인이라고 묶어 말하지 않습니다. 이 원인 설명과 거짓 답변 사용 여부는 최종 PPT에 사용자가 보완한 실험 맥락입니다.

### 해석할 때 주의할 점

추적용 실행: b4825f61 취소 90/100, ed547e89 취소 100/100, 96e7426a 자원 150/150, 158f8385 취소 100/100. 앞의 세 실행은 gpt-6.1-sol 메인·감시 구성, 마지막은 gpt-5 메인과 gpt-5.5 감시 구성입니다.

## 08. 한계 1. 모두 만점이면 차이를 보기 어렵다

### 이 슬라이드가 필요한 이유

정확도 중심의 평가를 시간·비용 평가로 넓혀야 하는 이유를 설명합니다. 과제를 어렵게 만들었는데도 여전히 연구적 차이를 보기 어렵다는 사용자의 문제의식을 반영합니다.

### 슬라이드 본문 — 현재 PPT 기준

> 문제를 복잡하게 해도 만점이 나왔습니다
>
> 자원 배정은 여러 사건의 영향을 추적해야 하는 과제였지만 150/150을 기록했습니다.
>
> 충분한 모델 능력과 규칙 정보가 있으면 이런 문제도 해결할 수 있습니다.
>
> 같은 점수라도 그 과정의 부담은 다를 수 있습니다
>
> 한 방식은 여러 번 고치고 많은 토큰을 쓴 끝에, 다른 방식은 더 적은 수정으로
>
> 같은 점수에 도달할 수 있습니다. 현재 점수만으로는 이 차이를 알 수 없습니다.
>
> 정확도와 함께 효율을 확인할 필요가 있습니다
>
> 목표 점수까지 걸린 시간, 전체 모델 사용량, 사람에게 한 질문을 측정해야 합니다.
>
> 점수가 상한에 몰려 차이가 잘 안 보이는 현상을 “천장효과”라고 부릅니다.
>
> 더 어려운 과제를 추가하는 것과 함께, 같은 품질을 얻는 데 필요한 자원을 비교해야 합니다.

### 발표할 때 풀어서 설명하기

시험이 너무 쉬워 학생들이 모두 100점을 받으면 어떤 공부 방법이 더 좋은지 점수만으로 구별하기 어렵습니다. 현재 상황에도 이와 비슷한 문제가 있습니다. 더 복잡한 문제를 만들었지만 만점이 나왔습니다. 그렇다고 다중 감시가 필요 없다는 결론도 바로 낼 수 없습니다. 만점까지 도달하는 데 든 시간이 다를 수 있고, 반대로 감시자 때문에 토큰과 시간이 더 들었을 수도 있습니다. 따라서 다음 실험에서는 같은 결과를 얻기까지의 과정을 함께 봐야 합니다. 문제를 계속 어렵게 만드는 것만이 해결책은 아니며, 과제의 종류를 넓히는 방법과 효율 측정을 병행할 수 있습니다.

### 해석할 때 주의할 점

단일 에이전트도 실제로 같은 과제에서 만점을 받았다는 비교 기록은 아직 없습니다. 여기서는 비교 평가가 만점 부근에서 구별하기 어려울 가능성을 지적하는 것입니다.

### 다음 슬라이드 연결

또 하나의 고민은 검토자의 성격을 바꾸는 실험만으로 충분한 연구 질문이 되는가입니다.

## 09. 한계 2. 검토자의 성격만 바꿔 비교하기 어렵다

### 이 슬라이드가 필요한 이유

사용자가 말한 “우리 틀에만 해당하는 조작변인”을 쉽게 설명합니다. 조작변인은 실험자가 의도적으로 바꾸는 조건이며, 여기서는 역할 지침의 변화가 넓게 적용되는 연구 결과로 이어지는지 고민하는 것입니다.

### 슬라이드 본문 — 현재 PPT 기준

> “페르소나”는 검토자에게 부여한 관점입니다
>
> 예를 들어 근거를 따지는 검토자, 작업 방향을 보는 검토자,
>
> 운영 중 오류를 걱정하는 검토자처럼 지침을 다르게 주는 방식입니다.
>
> 성격의 효과와 모델 능력의 효과가 섞일 수 있습니다
>
> 모델도 함께 바꾸면 결과가 좋아진 이유를 구분하기 어렵습니다.
>
> 강한 모델의 영향이 더 클 것이라는 우려도 있지만 아직 따로 검증하지 않았습니다.
>
> 다른 연구에서도 반복할 수 있는 비교가 필요합니다
>
> 직접 만든 역할 이름은 이 과제에만 잘 맞을 수 있습니다. 모델을 고정하고
>
> 검토자 수나 검토 시점을 바꾸면 무엇을 비교하는지 더 명확해집니다.
>
> 페르소나 비교는 가능하지만, 먼저 구조 자체의 효과를 분리해서 확인하려고 합니다.

### 발표할 때 풀어서 설명하기

검토자에게 역할을 주는 방법 자체는 구현하기 쉽습니다. 주장 감사관은 작업자의 보고가 근거와 맞는지 보고, 궤적 분석가는 작업 방향을 살피고, 온콜 담당은 운영 중 문제가 나면 원인을 찾을 수 있을지 봅니다. 그러나 이 이름과 지침은 우리가 직접 만든 것입니다. 좋은 결과가 나와도 어떤 문구가 효과가 있었는지, 다른 과제에서도 같은 효과가 있는지 설명하기 어렵습니다. 모델까지 바꾸면 문제가 더 복잡해집니다. 그래서 우선 같은 모델에서 검토자 유무나 검토 횟수처럼 명확한 조건을 비교한 뒤, 페르소나의 추가 효과를 후속 질문으로 두는 것이 낫다고 봤습니다.

### 해석할 때 주의할 점

페르소나가 중요하지 않다고 확정한 것은 아닙니다. 모델 성능이 더 중요하다는 생각 역시 검증할 가설이며 현재 데이터로 효과의 크기를 비교할 수 없습니다.

### 다음 슬라이드 연결

그렇다면 검토자가 없는 단일 AI와 비교하면 해결될까요? 여기에도 정보 제공의 공정성 문제가 있습니다.

## 10. 한계 3. 한쪽만 질문할 수 있으면 공정하지 않다

### 이 슬라이드가 필요한 이유

정보를 의도적으로 적게 주는 실험의 목적과, 그 설정이 잘못된 대조군을 만나면 왜 편향을 만들 수 있는지 설명합니다. 대조군은 제안 방식과 비교하기 위한 기준 방식입니다.

### 슬라이드 본문 — 현재 PPT 기준

> 현재 과제는 일부 규칙을 처음부터 알려주지 않습니다
>
> 이는 검토자가 누락된 정보를 찾아 사람에게 질문하는지 보기 위한 설정입니다.
>
> 예를 들어 취소 마감이나 대기 순서의 기준을 비워두는 방식입니다.
>
> 제안 구조만 답을 받으면 처음부터 유리해질 수 있습니다
>
> 단일 AI에는 짧은 요청만 주고, 제안 구조에는 인간 답변을 추가로 주면
>
> 점수 차이가 여러 AI의 협력 때문인지 정보가 더 많아서인지 알 수 없습니다.
>
> 비교 대상에도 같은 정보와 질문 기회를 줘야 합니다
>
> 두 방식 모두 사람에게 질문할 수 있게 하고 같은 규칙으로 답변합니다.
>
> 처음부터 전체 정책을 알려주는 조건도 따로 두어 구조의 차이를 확인합니다.
>
> 비교 대상인 단일 AI가 불리하도록 실험을 설계하지 않는 것이 핵심입니다.

### 발표할 때 풀어서 설명하기

원래의 관심은 빠진 정보를 발견하는 능력입니다. 그래서 처음 요청에 모든 정답 정책을 넣지 않았습니다. 하지만 이 상태에서 단일 AI는 질문하지 못하게 하고 우리 구조만 사람에게 묻게 하면 공정하지 않습니다. 추가 정보를 받은 쪽이 유리할 수 있기 때문입니다. 그 결과로 점수가 높아졌다고 해서 감시자 세 명이 필요하다는 결론을 내릴 수는 없습니다. 두 방식 모두 질문할 수 있어야 하고, 질문에 대한 답도 같은 정책에서 나와야 합니다. 전체 규칙을 처음부터 주는 조건을 추가하면 정보 획득의 차이를 줄인 상태에서 검토 방식의 기여를 살펴볼 수 있습니다.

### 해석할 때 주의할 점

불공정한 조건에서 제안 구조가 반드시 더 높은 점수를 얻는다고 단정하지 않습니다. 더 높은 점수가 나오더라도 구조적 우월성을 설명하는 근거로 쓰기 어렵다는 뜻입니다.

### 다음 슬라이드 연결

그래서 다음 연구의 중심은 같은 정보와 기회를 준 상태에서 어느 방식이 더 효율적인지 비교하는 것입니다.

## 11. 다음 질문: 같은 결과를 어느 방식이 더 효율적으로 얻나?

### 이 슬라이드가 필요한 이유

단일 에이전트에 충분히 다시 생각하고 고칠 기회를 주는 대조군을 제안합니다. 우리 구조의 1회 실행과 단일 모델의 1회 호출을 단순 비교하지 않도록 비용의 경계를 분명히 합니다.

### 슬라이드 본문 — 현재 PPT 기준

> 비교 A: 단일 AI가 여러 번 작업합니다
>
> 한 AI가 코드를 만들고 스스로 검토한 뒤 다시 고칩니다.
>
> 이전 코드와 검사 결과, 사람의 답변을 유지하며 순차적으로 개선합니다.
>
> 비교 B: 메인과 검토자들이 한 작업을 함께 수행합니다
>
> 메인 1개가 코드를 작성하고 검토자 3개가 확인하는 현재 구조를 실행합니다.
>
> 그 안에서 일어나는 모든 작성·검토·재시도 비용을 합산합니다.
>
> 확인하려는 내용
>
> 목표 품질까지 걸린 시간과 모델 사용량, 사람의 응답 부담을 비교합니다.
>
> 협력으로 수정을 줄이는 이득이 검토자를 추가한 비용보다 큰지 살펴봅니다.
>
> “제안 구조를 한 번 실행”해도 내부에서 모델은 여러 번 호출됩니다.

### 발표할 때 풀어서 설명하기

하나의 강한 모델을 여러 번 돌려도 좋은 결과를 얻을 수 있습니다. 그렇다면 감시자를 붙이는 대신 같은 모델에게 반복해서 검토와 수정을 맡기는 방법과 비교해야 합니다. 이 발표에서 단일 AI의 반복은 매번 처음부터 새로 만드는 것이 아니라 이전 결과를 유지하며 순차 개선하는 방식입니다. 제안 구조의 한 번 실행도 내부에는 많은 호출이 있습니다. 실제 자원 배정 실행에는 44개 호출 레코드가 남았습니다. 따라서 1회 대 여러 회라는 표현만으로 효율을 판단하면 안 됩니다. 질문은 같은 품질을 얻는 데 어느 쪽의 총부담이 더 작은가입니다.

### 해석할 때 주의할 점

독립적인 답을 여러 개 만든 뒤 가장 좋은 것을 고르는 best-of-k 방식은 별도 실험입니다. 그 경우 좋은 답을 선택하는 절차와 비용도 포함해야 합니다.

### 다음 슬라이드 연결

이 비교를 공정하게 하려면 무엇을 같게 두고 무엇만 바꿀지 미리 정해야 합니다.

## 12. 어떻게 조건을 맞춰 비교할 것인가?

### 이 슬라이드가 필요한 이유

“통제된 비교”가 실제로 무엇을 뜻하는지 풀어 설명합니다. 구조 두 가지와 정보 조건 두 가지를 조합하면 네 조건이 되며, 정보 획득과 검토 구조의 효과를 구분할 출발점이 됩니다.

### 슬라이드 본문 — 현재 PPT 기준

> 모델과 작업 조건은 같게 둡니다
>
> 같은 모델, 같은 문제, 같은 코드 검사 도구를 사용합니다.
>
> 모델이 생각하는 정도와 전체 토큰·시간 한도도 조건별로 동일하게 맞춥니다.
>
> 정보 제공 조건을 두 가지로 나눕니다
>
> ① 모든 규칙을 처음부터 제공합니다. ② 일부 규칙을 빼되 두 방식 모두 질문하게 합니다.
>
> 각 조건에서 단일 AI의 반복과 메인·검토자 구조를 각각 실행합니다.
>
> 사람의 답변도 일정한 기준을 따릅니다
>
> 미리 준비한 정책 문서에서 질문받은 내용만 답하는 등 응답 규칙을 고정합니다.
>
> 그때그때 한쪽에만 더 자세한 설명이나 구현 힌트를 주지 않도록 합니다.
>
> 바꾸는 것은 작업 방식과 정보 조건이며, 모델·문제·답변 기준은 맞춰 둡니다.

### 발표할 때 풀어서 설명하기

먼저 모델이 다르면 결과가 달라진 원인을 구조에서 찾기 어렵기 때문에 같은 모델을 사용합니다. 과제와 검사 도구도 같게 둡니다. 다음으로 정보 조건을 두 가지로 나눕니다. 전체 정책을 주는 조건에서는 이미 아는 규칙을 얼마나 잘 구현하고 검토하는지 볼 수 있습니다. 일부 정책을 빼는 조건에서는 두 방식에 똑같이 질문할 기회를 주고, 누락 정보를 얼마나 효과적으로 해결하는지 볼 수 있습니다. 질문 기회가 같다고 실제 질문 수가 같아야 하는 것은 아닙니다. 질문 수는 측정할 결과입니다. 단, 답변하는 사람이 한쪽에만 더 많은 힌트를 주면 안 되므로 답변 문서와 규칙이 필요합니다.

### 해석할 때 주의할 점

동일한 총예산을 준다고 각 호출의 개수가 반드시 같아야 하는 것은 아닙니다. 모든 에이전트의 사용량을 합친 예산을 비교하고, 실행 순서와 서버 혼잡 등도 가능한 한 균형 있게 배치합니다.

### 다음 슬라이드 연결

이 네 조건에서 결과 점수뿐 아니라 어떤 부담을 기록할지 구체적으로 정하겠습니다.

## 13. 무엇을 측정하고 어떻게 해석할 것인가?

### 이 슬라이드가 필요한 이유

“효율적”이라는 표현을 실제 숫자로 바꾸는 슬라이드입니다. 정확도와 비용을 함께 보아야 빠르지만 틀린 방식이나, 정확하지만 지나치게 비싼 방식도 구분할 수 있습니다.

### 슬라이드 본문 — 현재 PPT 기준

> 완성도와 시간
>
> 최종 점수와 목표 점수에 도달한 비율을 기록합니다.
>
> 처음부터 끝까지 걸린 시간과 사람이 답하는 대기 시간을 분리해서 봅니다.
>
> 모델 사용량과 사람의 부담
>
> 모든 AI의 입력·출력 토큰과 재시도 횟수를 합산합니다.
>
> 토큰은 모델이 읽고 쓰는 텍스트 단위입니다. 질문 수와 사람의 응답 시간도 기록합니다.
>
> 두 방향으로 결과를 비교합니다
>
> 같은 시간·토큰 한도에서 누가 더 잘 푸는지, 같은 점수까지 누가 덜 쓰는지 봅니다.
>
> 여러 번 반복하고 실패한 실행도 포함하여, 한 번의 좋은 결과에만 의존하지 않습니다.
>
> 정답은 작업 중 알려주지 않고 사후 채점합니다. 목표 미달과 실행 오류도 구분해 보고합니다.

### 발표할 때 풀어서 설명하기

효율 비교에는 두 시각이 있습니다. 첫째는 예산이 같을 때 어느 방식이 더 높은 품질을 얻는가입니다. 둘째는 같은 품질을 얻기 위해 얼마나 많은 자원이 필요한가입니다. 시간을 잴 때 검토자들이 동시에 동작한 시간을 단순 합산하면 실제 사용자의 대기 시간과 달라집니다. 실제 경과 시간을 재고 인간 응답 대기는 따로 기록해야 합니다. 토큰은 메인뿐 아니라 세 검토자와 재시도까지 모두 합쳐야 합니다. 캐시 사용량도 구분해 남길 수 있습니다. 각 코드 버전을 사후 채점하면 언제 목표 품질에 도달했는지 확인할 수 있지만, 그 정답을 작업 중 모델에게 돌려주면 평가 문제가 학습 힌트가 되므로 분리해야 합니다.

### 해석할 때 주의할 점

목표 점수, 예산, 중단 기준, 반복 횟수는 비교 전에 정해야 합니다. 목표에 못 도달한 실행을 빼고 성공한 실행의 비용만 평균 내면 결과가 유리하게 왜곡될 수 있습니다. 모델 접근 오류 같은 운영 실패는 품질 미달과 별도로 분류합니다.

### 다음 슬라이드 연결

마지막으로 이번에 확보한 것과 앞으로 입증해야 할 것을 구분해 정리하겠습니다.

## 14. 현재 성과와 앞으로 확인할 것

### 이 슬라이드가 필요한 이유

구현 성과를 인정하면서도 검증되지 않은 우위를 과장하지 않고 마무리합니다. 청중에게 다음 실험이 지금의 문제의식과 어떻게 연결되는지 남깁니다.

### 슬라이드 본문 — 현재 PPT 기준

> 현재 확보한 것
>
> 작업 AI, 검토 AI, 인간 답변을 연결하는 실험 환경을 만들었습니다.
>
> 두 종류의 평가 과제와 실제 실행 기록을 통해 동작과 실패 원인을 확인했습니다.
>
> 아직 답하지 못한 것
>
> 좋은 점수가 검토자 덕분인지, 모델 능력이나 추가 정보 덕분인지 분리하지 못했습니다.
>
> 단일 AI를 반복해서 쓰는 방식보다 실제로 이득이 있는지도 아직 모릅니다.
>
> 다음 연구의 목표
>
> 같은 모델과 정보 조건에서 두 작업 방식을 반복 비교하려고 합니다.
>
> 동일 품질까지 필요한 시간·토큰·인간 부담을 측정해 구조의 가치를 확인하겠습니다.
>
> 연구의 다음 목표는 “만점을 받았다”를 넘어, 어떤 조건에서 왜 도움이 되는지 설명하는 것입니다.

### 발표할 때 풀어서 설명하기

지금까지는 인간 개입을 포함한 다중 감시 구조를 실제로 실행하고 평가할 수 있는 기반을 만들었습니다. 단순한 취소 문제에서 여러 사건이 연결되는 자원 배정 문제로 확장했고, 만점뿐 아니라 인간 답변의 불일치와 실행 오류도 확인했습니다. 그러나 높은 점수만으로 이 구조가 필요하다고 말하기는 어렵습니다. 모델이 강해서일 수도 있고, 사람에게 받은 정보가 충분해서일 수도 있습니다. 따라서 다음 단계에서는 단일 AI도 반복해서 고치고 질문할 수 있게 해 공정하게 비교하려 합니다. 다중 검토가 더 빨라지는 조건, 토큰이 더 많이 드는 조건, 사람의 부담을 줄이는 조건을 구별하는 것이 연구의 다음 목표입니다.

### 해석할 때 주의할 점

효율 우위는 결론이 아니라 앞으로 검증할 질문입니다. 일부 조건에서 손해가 나더라도 그 조건을 설명하는 것은 의미 있는 결과가 될 수 있습니다.

### 다음 슬라이드 연결

질의응답에서는 정보 누락 과제의 타당성, 인간 응답 통제 방법, 목표 품질과 예산 설정을 중심으로 논의할 수 있습니다.

## 근거와 읽는 기준

- 최종 PPT의 슬라이드 본문과 기존 슬라이드별 발표 해설을 대조하여 통합했습니다. 새 파이프라인은 4장에, 기존 질문·답변 화면은 5장에 배치했습니다. 최종 PPT에서 삭제된 실행 복구 슬라이드의 독립 해설은 제외했습니다.
- [로컬 구현·실험 기록](<../reports/multi-agent-lab_구현_실험_기록_2026-11-10.md>): 구현 경과, 과제 구성, 실행 상태와 점수의 근거입니다.
- [실행 파이프라인 구현](<../../backend/live_workflow.py>): `_work_live`, `_live_observe`, `_live_monitor`를 기준으로 4장의 데이터 흐름을 설명했습니다.
- 7장의 거짓 답변 사용과 낮은 모델 설정의 출력 형식 오류는 사용자가 최종 PPT에 보완한 실험 맥락을 반영했습니다. 개별 실행 원인을 확인하지 않고 모든 미완료 실행에 확대 적용하지 않습니다.
- 11~13장의 단일 AI 반복과 다중 검토 구조의 효율 비교는 후속 연구 설계입니다. 현재 데이터로 효율 우위가 입증되었다는 뜻은 아닙니다.
