# 와쿠쿠 발표 대본

최종 자료 「5조_2차 미팅」 기준 · 13장 · 약 6분 30초


## 1. 표지 (20초)

안녕하세요. 저희 팀은 AI가 코드를 작성하는 과정에 검토자를 두고, 필요한 경우 사람에게 질문하도록 하는 실행 환경을 만들고 있습니다.

오늘은 현재 구현한 구조와 예비 실험 결과, 그리고 다음 비교 실험에서 맞춰야 할 조건을 말씀드리겠습니다.

## 2. 프로젝트 개요 (25초)

하나의 AI가 코드를 작성하다 보면, 요구사항에 빠진 부분을 스스로 정해서 진행할 수 있습니다. 저희 팀은 별도의 검토자가 이런 부분을 찾아 사람에게 확인하도록 구성했습니다.

현재는 질문을 만들고, 답변을 받아 다음 수정으로 넘기고, 결과를 채점하는 흐름까지 작동합니다. 단일 AI보다 정확하거나 효율적인지는 아직 확인하지 못했습니다.

## 3. 왜 사람에게 질문해야 할까? (40초)

예를 들어 예약 취소 프로그램을 만든다고 해보겠습니다. 취소 마감이나 휴무일 처리 기준이 빠져 있어도, AI는 나름대로 규칙을 정해서 실행되는 코드를 만들 수 있습니다. 다만 그 규칙이 사용자의 의도와 맞는지는 알 수 없습니다.

날짜 계산 오류는 검사해서 고칠 수 있지만, 휴무일에도 취소를 허용할지는 사용자에게 확인할 필요가 있습니다. 운영하는 곳마다 기준이 다를 수 있기 때문입니다.

그렇다고 모호한 부분을 전부 물어보면 작업이 자주 끊길 수 있습니다. 반대로 그냥 넘어가면 잘못된 가정으로 코드를 작성할 수 있고요. 그래서 어떤 내용을 언제 물어보는 게 좋을지도 함께 살펴보려고 합니다.

## 4. 메인 1개, 검토자 3개의 실행 구조 (30초)

현재 구조에는 코드를 작성하는 메인 AI 하나와 검토자 세 개가 있습니다.

메인이 계획과 코드를 제출하면, 검토자들은 공유된 기록을 보고 확인합니다. 여기에는 코드 버전과 검사 결과, 질문과 답변이 포함됩니다. 메인 AI의 내부 사고 과정을 보는 건 아닙니다.

검토자는 문제를 지적하거나 질문을 제안하고, 실제 코드 수정은 메인이 담당합니다.

## 5. 메인 모델과 검토자 설정 (15초)

이 화면에서 메인 모델을 선택하고, 검토자 세 개가 각각 어떤 관점으로 확인할지 설정할 수 있습니다.

화면에 나온 모델은 개발 당시의 설정 예시입니다. 어떤 모델이나 검토자 조합이 가장 좋은지는 아직 비교하지 않았습니다.

## 6. 질문, 응답, 수정의 반복 (35초)

메인이 계획과 코드를 작성하면 문법 검사와 공개 검사를 진행하고, 검토자 세 개도 병렬로 검토합니다.

사람의 판단이 필요한 부분이 나오면 질문을 제안합니다. 답변이 도착하면 기록해서 다음 코드 수정에 전달합니다.

최신 코드의 검토가 끝나고, 남은 질문 없이 검사를 통과하면 메인의 완료 판단까지 확인한 뒤 실행을 마칩니다.

실행 중에 보는 공개 검사와, 완료 후에 하는 숨겨진 최종 채점은 별도입니다.

## 7. 질문을 고르고 답변을 남기는 화면 (20초)

사람은 이 화면에서 질문을 선택하고 답변을 입력합니다. 제출한 답변은 기록되고 다음 수정 단계로 전달됩니다.

이 캡처는 입력 동작을 확인할 때 찍은 화면이라, 내용 자체는 실제 정책 답변이 아닙니다. 다만 답변을 전달했더라도 코드에서 다르게 해석했을 수 있어서, 실제 수정 내용까지 확인할 필요가 있습니다.

## 8. 평가 과제의 확장 (35초)

처음에는 예약 취소 가능 여부를 판단하는 100문항을 사용했습니다. 그런데 규칙을 알고 나면 풀이가 짧아져서, 작업 방식에 따른 차이가 잘 드러나지 않을 수 있었습니다.

그래서 예약과 취소, 대기자 승급이 이어지는 자원 배정 과제를 추가했습니다. 15개 유형을 각각 10개씩 변형한 150세트이고, 세트마다 8개에서 18개의 사건이 있어 총 1,690개입니다.

앞에서 정책을 어떻게 해석했는지가 이후 결과에도 영향을 줍니다. 두 과제는 채점 단위가 달라 점수를 직접 비교할 수는 없습니다.

## 9. 예비 실행 10건의 결과 (35초)

현재 예비 실행은 총 10건이고, 최종 채점까지 마친 건 4건입니다.

예약 취소 과제에서는 90점 한 건과 100점 두 건이 나왔고, 자원 배정에서는 150점 만점 한 건이 나왔습니다. 90점 실행에는 의도적으로 잘못된 사람의 답변을 넣었습니다.

나머지는 중단 3건, 실패 2건, 일시정지 1건이며, 미채점을 0점으로 처리하지 않았습니다.

실행마다 모델과 답변, 프로그램 버전이 달라서 이 결과로 성능 우위를 판단할 수는 없습니다. 현재는 전체 실행 흐름을 확인한 예비 결과로 보고 있습니다.

## 10. 높은 점수만으로 설명하기 어려운 것 (35초)

예비 실험에서는 점수가 만점에 몰리는 천장효과가 나타났습니다. 정확도만으로는 구조 간 차이를 보기 어려워서, 후속 실험에서는 실행시간과 토큰 사용량도 함께 비교할 계획을 세웠습니다.

또 사용한 6.1 sol의 모델 성능과 검토자의 관점이 결과에 각각 얼마나 기여했는지는 구분하지 못했습니다. 실행마다 모델 설정이 달랐기 때문입니다. 사람의 답변 조건도 달라서, 추가 정보의 효과가 교란 요인으로 남았습니다.

답변을 기록해서 다음 수정에 전달하는 흐름까지는 구현했습니다. 다만 전달 여부는 확인했어도, 답변과 코드 사이의 의미적 정합성까지 검증한 것은 아니었습니다. 그래서 답변이 코드에 의도대로 반영됐는지는 후속 검증 항목으로 남겨뒀습니다.

## 11. 단일 반복과 다중 검토 비교 (35초)

다음에는 스스로 초안을 검토하고 수정하는 단일 AI와, 메인에 검토자 세 개를 붙인 구조를 비교하려고 합니다.

양쪽에 반복 수정과 질문 기회를 주고, 모델과 추론 설정, 검사 도구를 맞출 계획입니다. 전체 시간과 토큰 한도도 같게 두려고 합니다.

정보 조건은 처음부터 전체 정책을 주는 경우와, 일부를 빼고 질문으로 확인하게 하는 경우로 나눕니다. 두 작업 구조에 두 정보 조건을 적용한 네 조건을 반복 실행해서, 구조와 정보 제공의 영향을 살펴보려 합니다.

## 12. 비교에서 함께 볼 것 (30초)

최종 점수와 목표 점수 도달률을 보고, 실제 경과시간도 기록하려고 합니다. 작업한 시간과 사람의 답변을 기다린 시간은 구분합니다.

모델 사용량은 메인뿐 아니라 검토자와 재시도까지 모두 합산합니다. 사람에게 한 질문 수와 응답시간도 함께 보고요.

같은 예산에서 어느 정도 품질을 얻는지, 같은 품질에 도달하려면 얼마나 드는지를 비교할 계획입니다. 목표와 중단 기준을 미리 정하고, 실패한 실행도 포함하겠습니다.

## 13. 다음 실험에서 정할 기준 (35초)

다음 실험에서는 어떤 과제를 쓰고, 목표 점수를 어느 정도로 잡을지부터 정하려고 합니다. 너무 쉽게 만점이 나오면 두 방식의 차이를 보기 어렵기 때문입니다.

사람의 답변은 고정된 정책 문서를 기준으로 맞추려고 합니다. 질문에 어디까지 답해줄지도 미리 정해두고요.

검토자를 붙였을 때 시간과 토큰이 얼마나 더 드는지, 사람이 질문을 이해하고 답하는 데 얼마나 걸리는지도 보려고 합니다. 점수가 같더라도 불필요한 질문에 계속 답해야 한다면 사용하기 번거로울 수 있기 때문입니다.

이 기준들을 어떻게 잡으면 좋을지 의견을 듣고 싶습니다. 감사합니다.
