# 감시자가 찾은 규칙은 코드에 남았나

불충분한 요구를 받은 코딩 AI가 언제 사람에게 묻고, 그 답을 얼마나 정확히 실행하는가

와쿠쿠 5조  ·  2026년 10월~11월 26일  ·  Codex 로컬 실험 종합

연구의 전환점은 멘토링 피드백과 5조 2차 발표였다. 두 자료를 바탕으로 질문·답변이 작동하는 시스템 시연에서, 같은 기회를 준 메인과 독립 감시자가 무엇을 더 확인하고 얼마나 정확히 구현하는지 비교하는 연구로 방향을 바꿨다.

### 발표에서 답할 세 가지 질문

| 발표 질문 | 실험에서 관찰한 답 |
| --- | --- |
| 세 명이면 한 명이 놓친 정보를 찾는가? | 다섯 과제의 첫 회차에서 혼합 감시자 한 역할의 질문은 최대 12/17개 주제를 다뤘고, 세 역할을 합치면 17/17개였다. 한 역할만 남기는 사후 집계다. |
| 메인이 스스로 물을 때보다 코드가 좋아지는가? | 다섯 과제 21조건 실험에서는 자체 검토 68점, 감시자 81점이었다. 예약·문의 26조건의 실제 3회차에서는 같은 순서로 73점, 62점이었다. |
| 추가 토큰은 어디에서 가치를 잃는가? | 기본 예약 50문항에서 Qwen과 혼합 감시자는 45문항을 판정할 근거를 얻고도 15점이었다. 46,585토큰을 사용한 뒤 제출한 코드가 1,054토큰짜리 단독 초안과 같았다. |

> 감시자가 찾아낸 정보의 가치와 그 정보를 코드에 옮긴 결과를 따로 측정해야 한다. 두 값이 어디서 갈라졌는지가 이 연구의 주된 발견이다.

본문은 연구 설계, 초기 프로토타입, 통제 실험, 세 모델 비교, 발표 결론 순서로 구성했다. 부록에는 조건별 전체 수치, Codex 작업 계보와 원자료 색인이 있다.

## 세 조건에서 사람은 언제 개입하는가

**연구 설계 · PDF 3쪽**

모델이 모르는 사실은 운영자의 선택이다. 접수한 시각은 계산할 수 있어도, 정확히 마감 시각에 접수한 고객을 받을지는 운영자에게 물어야 한다.

| 비교 조건 | 같이 주는 정보 | 추가로 일어나는 일 |
| --- | --- | --- |
| ① 메인 단독 | 공개 명세와 시작 파일 | 메인이 한 번 작성하고 제출한다. 정책 질문 기회가 없다. |
| ② 메인 자체 검토 | 같은 메인의 같은 초안 | 메인이 직접 빠진 기준을 찾는다. 최근 비교에서는 한 회차에 질문을 최대 세 개 보낸다. |
| ③ 독립 감시자 | ②와 같은 초안·담당자 정책 | 감시자 A·B·C가 같은 코드를 각자 읽고 한 질문씩 제안한다. 실제 코드 수정은 메인이 맡는다. |

~~~mermaid
flowchart LR
    N0["검토<br/>현재 코드·공개 명세·이전 문답을 읽는다."]
    N1["질문<br/>결과가 갈리는 상황을 묶어 담당자에게 보낸다."]
    N2["인간 답변<br/>질문받은 범위에 한해 자연어로 한 번 답한다."]
    N3["수정<br/>메인이 근거 구절과 변경할 위치를 연결한다."]
    N0 --> N1 --> N2 --> N3
    N3 -. "1·2회차 수정본" .-> N0
    N3 --> F["3회차 뒤 제출 고정·연구자 채점"]
~~~

최근 3회차 실험에서는 수정본을 다음 회차에 넘겼다. 질문이 없는 회차에는 답변을 추가하지 않았다. 감시자들은 같은 회차의 동료 출력을 읽지 않았다. 사람이 경계를 정하고, 코드를 고칠지와 어떻게 고칠지는 메인의 몫이었다.

후기 통제 실험에서 ‘인간 답변’은 사용자의 위임을 받은 Codex가 담당자 역할로 제공했다. 미리 정한 정책 카드에서 실제로 질문받은 부분만 자연어로 답했다. 이 방식은 팀마다 같은 기준을 적용하지만, 실제 사용자의 답변 속도와 부담은 측정할 수 없다.

연구자는 모든 조건의 최종 제출을 고정한 뒤 저장해 둔 회차별 코드도 채점했다. 모델이 수정 도중 받은 형식 피드백은 들여쓰기·인용 위치 같은 편집 정보다. 초기 공개 검사 피드백 실험의 성과는 별도로 표시했다.

## ‘100문항’의 분모를 먼저 맞춘다

**연구 설계 · PDF 4쪽**

한 함수를 100가지 입력으로 실행한 것과, 서로 다른 개발 과제 100개를 수행한 것은 증거의 범위가 다르다.

| 묶음 | 무엇이 한 점인가 | 어디에 쓰였나 |
| --- | --- | --- |
| 예약 기본 40 | 일반 마감·경계·정정·시작 우선순위 각 10건 | 모델·시드 교정과 초기 A·B·C·D. 추가 56개 입력은 같은 정책의 별도 검사. |
| 핵심 20 | 예약 10 + 문의 태그 배정 10 | 질문 생성과 코드 작성 방법을 바꿔 빠르게 원인을 찾음. |
| 예약·문의 100 | 예약 50 + 문의 50, 두 함수 | 기존 20을 포함한 18유형. 26조건과 과거 제출을 비교. |
| 전이 100 | 제목·확장자·식별코드·업로드·인쇄 각 20 | 같은 다섯 과제를 21조건, 국소 수정기, 모델 10조건에서 각각 평가. |
| 모델별 예약 50 / 100 | 기본 50은 앞의 예약 50. 휴무 포함 100은 시각 문자열 3개를 받는 별도 계약 | 세 모델 10조건에서 두 정책을 각각 독립 실행. 점수와 비용을 따로 셈. |
| 자원 배정 150 | 15유형 × 10시나리오. 각 시나리오의 사건 결과·최종 상태·알림 모두 일치 | 초기 웹 파일럿, 완전정보 단독, 이후 일정·배정 수정 경로를 서로 구분. |

정답, 오답, 판단 보류, 실행·형식 오류를 구분했다. ‘근거 충분’은 공개 명세와 실제로 받은 답을 합쳐 그 입력의 반환을 정할 수 있다는 뜻이다. ‘근거 있는 정답’은 그중 코드도 맞힌 수다. 근거가 부족한 정답은 추측과 일치할 수 있어 모델의 이해를 입증하지 않는다.

조건별 토큰은 입력과 출력의 합이며, 같은 초안·요청을 재사용해도 각 구조를 독립 운영할 때의 비용을 계산했다. 모델마다 토큰화가 다르다. 시드·질문 수·검토 수가 달랐던 실험의 점수와 토큰은 합산하지 않았다.

## 왜 작업자와 검토자를 나눴나

**개발 계보 · PDF 5쪽**

10월 초 Codex에서 논의한 문제는 ‘피드백이 여럿일 때 누가 사람에게 판단을 요청하는가’였다. 성능을 재기 전에, 판단이 어디에 남고 누가 다시 일을 시작하는지 구현해야 했다.

### 10월 10~16일 · 규칙 기반 OxyGent

디자인 피드백의 충돌을 어떻게 점수화할지 논의하다가, 정답을 재현할 수 있는 예약 취소를 첫 과제로 택했다. 작업자 1개와 요구사항 분석·기능 검증·변경 영향 검토 3개가 같은 상태 사본을 읽었다. 누락이면 사람에게 묻고, 문서에 기준이 있으면 질문을 생략하고, 코드만 틀리면 자동 수정하는 세 경로를 실행했다.

이 프로토타입의 판단과 수정은 Python 규칙이었다. 실행 JSON과 테스트 9건은 분기와 기록의 작동을 확인한다. LLM이 언제 질문해야 할지 스스로 판단한다는 증거는 여기서 얻을 수 없었다.

### 10월 28일~11월 초 · 웹에서 실제 모델과 사람 연결

별도 로컬 웹 작업에서는 세 작업을 나눠 수행하던 데모를 보관하고, 한 메인의 전체 프로젝트를 세 검토자가 감시하도록 바꿨다. 계획, 코드 버전, 검토 의견, 질문, 인간 결정, 검사·완료 상태를 저장했다. 중단 뒤에도 받은 답을 잃지 않고 재개하도록 보강했다.

~~~mermaid
flowchart LR
    N0["프로토타입<br/>정책 누락·기재·코드 오류를 규칙으로 분기"]
    N1["웹 실행기<br/>실제 모델이 제안한 질문을 사람이 선택·응답"]
    N2["채점 과제<br/>같은 예약·배정 입력에서 최종 코드 검증"]
    N0 --> N1 --> N2
~~~

> 재현 가능한 과제로 옮긴 이유는 ‘좋은 질문’의 기준을 만들기 위해서였다. 답이 다르면 같은 입력의 허용·거부가 바뀌는 상황을 명시할 수 있어야 한다.

## 휴무 세트의 55점은 세 가지 결과를 숨긴다

**세 모델 비교 · PDF 25쪽**

정답이 허용 45개·거부 55개여서, 어떤 입력에도 ‘거부’라고 답하는 코드가 55점이다. 점수와 함께 실제 반환을 읽으면 모델별로 다른 문제가 드러난다.

| --- | --- | --- | --- | --- |
| Qwen 동종 3명 | 0 | 55 | 0 | 100건 모두 거부 |
| Gemma 동종 3명 | 45 | 10 | 0 | 입력 문자열 now < starts_at이면 허용 |
| Phi 동종 3명 | 0 | 55 | 0 | 100건 모두 거부 |

| Qwen 자체 / Phi 자체 | 0 / 0 | 0 / 0 | 각 100 보류 | 필요한 정책을 구현하지 않은 경로에서 중단 |

Gemma 동종은 허용 45건을 모두 맞혔지만 거부 45건을 잘못 허용했다. Qwen·Phi 동종은 허용 45건을 전부 놓쳤다. 어느 조건도 일괄 거부의 55점을 넘지 못했다. 실제 운영에서 잘못 허용하는 비용과 잘못 거부하는 비용이 다르면 같은 55점도 다른 선택이다.
