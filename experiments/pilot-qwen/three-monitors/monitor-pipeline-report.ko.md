# 감시자 3명은 예약 취소 코드의 정확도를 높였는가?

**독립 감시자 3명을 붙였을 때 Qwen2.5-Coder-14B는 57.5%에서 61.7%로 올랐다. 7B와 Qwen3-8B의 정확도는 그대로였다.** 실패는 두 단계에서 관찰됐다. 7B 감시자들은 안내문에 있는 일반 취소 규칙의 누락을 놓쳤다. Qwen3 감시자는 중요한 예외를 찾아 담당자에게 물었지만, 메인은 명시적인 답을 받고도 시작 정각의 오류를 고치지 못했다. 웹 실행기에서도 검사 0건인 코드를 완료로 처리하는 경로를 재현했다.

과제는 예약한 지 몇 초가 지났는지와 이용 시작까지 몇 초가 남았는지를 받아 취소 허용 여부를 반환하는 함수였다. 안내문에는 일반 마감과 정정 시간의 존재가 적혀 있다. 운영자 역할의 실험자는 모델이 실제로 물어본 정책만 고정 문구로 답했다. 시드 17·29·43에서 만든 각 초안에 같은 40문항을 적용했다. 분모 120은 한 과제의 반복 측정이다. 목표 점수에 맞춰 문항을 빼거나 시드를 선별하지 않았다. [기존 메인 단독 실험](../README.md) · [시드·조건별 집계](paired-results.json)

독립 감시 조건에서는 같은 모델의 감시자 셋이 서로의 의견을 보지 않고 초안을 검토했다. 자체 검토에서는 메인이 같은 세 관점을 차례로 검토했다. 두 조건 모두 검토 3회와 메인 수정 1회를 썼다. ‘감시자가 만든 사례’ 조건에서는 감시자에게 최대 두 개의 입력과 기대값을 받아 초안을 실행했다. ‘확정된 규칙의 사례’ 조건에서는 일반 독립 감시에서 나온 **초안, 세 의견, 담당자 답, 모델, 시드, 생성 설정을 고정**하고, 마지막 수정 요청에 이미 공개된 규칙으로 사람이 작성한 기대값과 초안 실행 결과를 덧붙였다. 이 마지막 조건은 실패 원인을 좁히기 위한 사후 실험이다. ## 2. 감시와 수정은 각각 어디서 실패했나

**7B에서는 일반 규칙 자체가 빠졌다.** 시드 43의 초안은 예약한 지 10분이 넘으면 이용 시작이 이틀 뒤여도 취소를 거부했다. 감시자 셋은 이 분기를 찾아내지 못했다. 7B와 14B의 일반 감시에서는 모델별 9개 의견 모두 담당자에게 제출할 질문 칸이 비었다. 14B는 일부 의견에 “확인이 필요하다”고 썼다. 이 문장은 메인에게 전달됐지만 담당자에게 보낼 질문으로 등록되지 않았다. [7B 실행 기록](7b-seconds-monitors-43.json) · [14B 실행 기록](14b-seconds-monitors-43.json)

**14B의 순증 5문항에는 회귀가 숨어 있었다.** 시드 43에서 일반 마감 후에도 예약 생성 직후에는 취소할 수 있다는 감시 의견을 메인이 반영했다. 초안의 오답 10개가 정답이 됐다. 동시에 이용 시작 여부를 검사하기 전에 정정 요청을 허용하면서 기존 정답 5개가 오답이 됐다. 이 시드가 20/40에서 25/40으로 올랐고, 나머지 두 시드의 점수는 같았다. [수정 코드와 문항별 결과](14b-seconds-monitors-43.json)

**Qwen3는 올바른 질문과 답이 모두 있었는데도 한 문항을 놓쳤다.** 시드 43에서 두 번째 감시자는 정정 시간이 이용 중에도 적용되는지 물었다. 담당자는 시작 시각과 같거나 이후면 정정 시간이 남아 있어도 거부한다고 답했다. 메인의 마지막 입력에 이 답이 있었지만, 코드는 남은 시간이 0보다 작을 때만 거부했다. 예약 생성 후 300초인 경우를 실제 실행하면 다음과 같다. [질문·답변·최종 코드](qwen3-8b-off-monitors-43.json) · [실행 결과를 추가한 재실험](qwen3-8b-off-contract-43.json)

| 이용 시작까지 남은 시간 | 담당자 답에 따른 기대 | 일반 감시 후 | 기대값과 초안 실행 결과까지 본 뒤 |
|---|---|---|---|
| 1초 | 허용 | 허용 | 허용 |

## 3. 테스트를 붙이면 무엇을 알 수 있나

감시자가 제안한 52개 사례 중 입력 계약을 만족하고 허용·거부를 명시한 것은 43개였다. 완전한 운영 정책으로 사후 대조하니 **16개는 감시자가 기대값을 잘못 붙였다.** 초안이 실제로 틀렸고 감시자 기대값이 맞았던 제안은 3개였다. 모두 14B 시드 43에서 나왔고 같은 입력을 중복 제안한 두 건을 포함한다. 14B 시드 29의 한 검토 응답은 320토큰 한도에서 잘려 구조화된 사례를 얻지 못했다. [사례별 집계](paired-results.json) · [14B가 실제 오류를 찾은 기록](14b-seconds-probes-43.json)

| 모델 | 제안 수 | 유효 입력·기대값 명시 | 잘못된 기대값 | 실제 오류를 짚은 제안 |
|---|---:|---:|---:|---:|
| 7B | 18 | 12 | 5 | 0 |
| 14B | 16 | 13 | 3 | 3 |
| Qwen3-8B | 18 | 18 | 8 | 0 |

사람이 이미 확정된 규칙으로 사례를 만든 조건에서는 **수정 후 9개 제출 중 7개에서 공개 검사 실패가 남았다.** 7B는 세 제출 모두, 14B와 Qwen3는 세 제출 중 두 개씩 실패했다. 14B는 일반 감시보다 순증 5문항, 7B는 순감 9문항, Qwen3는 동일했다. 공개 검사를 모두 통과한 두 제출도 전체 평가에서는 각각 29/40과 39/40이었다. 공개 사례는 구체적인 실패를 드러낼 수 있지만, 통과만으로 다른 규칙까지 충족했음을 보장하기는 어렵다. [검사 전후와 전체 평가](paired-results.json)

공개 사례와 평가 문항의 중복도 확인했다. 사후 대조에서 사람이 작성한 사례는 3문항, 감시자 사례는 다른 1문항과 두 입력이 정확히 일치했다. 이 4문항을 모든 조건에서 뺀 결과도 방향은 같았다. 메인 단독 → 독립 감시 → 확정 규칙 사례 순으로 7B는 70 → 70 → 62, 14B는 62 → 66 → 72, Qwen3는 90 → 90 → 90이었다. 각각 108회 판정 기준이다. 위의 시작 정각 재현 사례도 겹친 문항 중 하나다.

## 4. 웹 파이프라인 검토

로컬 모델 실험과 별도로, 실제 웹 백엔드에 **고정된 메인·감시자 응답**을 넣어 완료 경로를 검사했다. 메인은 항상 취소를 거부하는 함수와 빈 검사 목록을 냈다. 감시자 셋은 모두 추가 검사 없이 계속 진행을 선택했다. 실행기는 **0/0을 검증 통과로 기록하고 프로젝트를 완료**했다. 이후 별도 채점 결과는 20/40이었다. 이 재현은 잘못된 완료가 가능한 조건을 보여 준다. 실제 웹 모델에서 그 경로가 발생하는 빈도는 이번에 측정하지 않았다. [웹 실행기 재현 기록](web-completion-diagnostic.json) · [공개 검사 처리](../../../backend/isolated.py) · [완료 판정](../../../backend/live_workflow.py)

웹 실행기는 메인이 담당자 답변의 식별자를 빠짐없이 처리했다고 보고했는지 검사한다. 특정 답변을 반영했다고 보고해도, 그 답변에 해당하는 행동을 검증할 사례가 하나도 없으면 코드 동작까지 확인할 수 없다. 반면 로컬 실험은 초안에 감시자를 한 차례 붙이고 메인이 한 번 수정하는 구조다. 웹의 상시 감시·반복 수정과 로컬의 한 차례 검토 결과는 구분해서 해석해야 한다. [답변 반영 보고와 실행 상태 처리](../../../backend/live_workflow.py)

## 5. 다음 비교에서 우선 바꿀 점

1. **완료 기준을 바꾼다.** 검사 0건은 ‘미검증’으로 표시한다. 행동을 바꾸는 담당자 답변에는 그 답에 근거한 허용·거부 사례를 연결한다. 수정 후 실패하면 기대값과 실제값을 돌려주고, 정해진 수정 횟수가 끝나면 남은 실패를 표시한다. 이전에 통과한 사례도 다시 실행해 14B에서 본 회귀를 잡는다.
2. **감시자의 기여를 단계별로 센다.** 이미 확정된 규칙에는 반례를, 아직 정하지 않은 정책에는 답에 따라 결과가 달라지는 입력과 담당자 질문을 내게 한다. 유효한 오류 발견 수, 실제로 접수된 질문 수, 답변 후 수정 성공 수, 새로 틀린 문항 수를 함께 기록하면 감시가 기여한 단계가 드러난다.
3. **새 과제에서 같은 비용의 대조군을 둔다.** 정책과 평가 사례를 먼저 고정하고, 일반 규칙 하나·예외 하나·두 규칙이 충돌하는 상황이 있는 새 과제를 사용한다. 메인 자체 검토와 독립 감시 조건 양쪽에 동일한 검사 도구와 수정 횟수를 제공한다. 그래야 실행 검증 자체의 이득과 독립 감시자의 기여를 분리할 수 있다.
