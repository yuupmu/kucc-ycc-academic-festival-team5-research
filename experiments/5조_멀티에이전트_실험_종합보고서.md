## 1. 프로젝트의 출발점과 멘토 피드백

팀은 메인 AI가 코드를 작성하고 감시자가 요구사항의 빈틈을 찾아 필요하면 사람에게 묻는 웹 실행 환경을 구축했다. 감시자는 코드 버전, 질문·답변, 공개 검사 등 공유 기록을 읽는다. 코드를 직접 수정하는 역할은 메인이다. 예컨대 날짜 계산은 코드를 실행해 검증할 수 있지만, 휴무일에 취소를 허용할지는 운영자가 정해야 한다.

이전 2차 미팅의 예비 실행 10건 중 최종 채점까지 간 것은 4건이었다. 예약 취소에서 90/100, 100/100, 100/100점, 자원 배정에서 150/150점이었다. 90점 실행에는 의도적으로 잘못된 사람 답변을 넣었다. 나머지 6건은 중단 3건, 실패 2건, 일시정지 1건으로 미채점이었다. 사용 모델·답변·프로그램 버전이 서로 달랐고, 완료된 실행은 만점 부근에 몰렸다.

멘토는 메인 혼자서도 가끔 실패하는 과제, 같은 호출 수를 쓰는 간단한 대조군, 사람 답변의 일관성, 실행 간 변동, 감시 비용을 강조했다. 이에 따라 연구 질문을 **“어떤 조건에서 감시자가 누락이나 코드 오류를 찾아 실제 수정으로 이어지게 하며, 거기에 얼마의 비용이 드는가?”**로 좁혔다. 60%는 초기에 상정한 대략적인 난도였다. 이후 해석에는 고정 문항에서 실제 얻은 점수를 사용했다. ## 2. 무엇을 평가했나

주 과제는 작은 연습실의 취소 함수 `allow_cancel(age_seconds, until_start_seconds)`다. 첫 입력은 예약 생성 후 경과한 초, 두 번째는 이용 시작까지 남은 초다. 두 번째가 0이면 시작 정각, 음수이면 이미 시작한 상태다. 공통 어댑터가 날짜를 초로 바꾸고 모델은 허용·거부 규칙을 구현한다.

| 정책 | 실제 채점 기준 | 오류를 구분하는 사례 |
| --- | --- | --- |
| 일반 취소 마감 | 이용까지 24시간 이상 남으면 허용한다. | 오래된 예약에서 정확히 24시간 전과 그보다 1초 늦은 시점을 비교한다. |
| 방금 만든 예약의 정정 | 일반 마감 후에도 예약 생성 후 10분까지 허용한다. 10분 정각을 포함한다. | 이용 시작 전, 예약 후 600초와 601초를 비교한다. |
| 이용 시작의 우선순위 | 시작 정각과 그 이후에는 정정 유예가 남아도 거부한다. | 예약 후 5분인 고객이 이용 시작 1초 전과 시작 정각에 요청한다. |

부분정보 안내문에는 일반 마감과 별도 정정 시간의 존재가 나온다. 구체적인 유예 시간·경계·우선순위는 완전정보 조건이나 해당 사항에 대한 담당자 답변에서 제공한다. 일반 마감, 마감 경계, 예약 직후 유예, 시작과 유예의 우선순위에 각 10문항씩 총 40문항이다. 허용과 거부가 20건씩이라 일괄 거부만 해도 20/40점이다. ## 4. 독립 감시와 같은 횟수의 자체 검토

세 모델 각각에서 시드별로 질문과 초안을 한 번만 만들었다. 조건 A는 공통 초안을 제출했다. B에서는 메인이 세 관점을 차례로 검토하고 한 번 수정했다. C에서는 감시자 셋이 같은 초안을 서로 독립적으로 읽고 메인이 한 번 수정했다. B·C의 추가 호출은 모두 4회였다. 이 절의 A·B·C는 **실험 조건 이름**이며, 뒤의 검토 주기에서 쓰는 **감시자 세 명의 이름**과 구분한다.

| 모델 | A 단독 | B 자체 검토 | C 독립 감시 | B / C 시드당 평균 총 토큰 | B / C 평균 모델 시간 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 7B | 79/120 | 79/120 | 79/120 | 5,224 / 4,279 | 19.06 / 14.90초 |
| 14B | 69/120 | 69/120 | 74/120 | 6,013 / 4,938 | 61.40 / 50.57초 |
| Qwen3-8B | 98/120 | 98/120 | 98/120 | 6,746 / 6,116 | 39.12 / 41.75초 |
| 합계 | 246/360 | 246/360 | 251/360 | | |

### 전달과 완료 처리 수정

- **답이 도달해도 코드가 따르지 않은 사례.** Qwen3 감시자가 이용 시작 순간에 관해 물었고 담당자는 시작 순간부터 거부한다고 답했다. 메인의 입력에 답변이 있었지만 코드는 남은 시간이 음수일 때만 거부했다. 정각인 0초는 허용했다.
- **웹 실행기의 완료 오류.** 고정된 응답으로 재현하니 메인이 검사를 하나도 내지 않고 감시자 셋이 계속 진행을 선택하면 0/0을 통과로 기록하고 완료했다. 수정 후 같은 경로에서 빈 검사가 반복되면 ‘미검증’으로 멈췄다. 이는 재현한 실행 경로이며 실제 사용에서의 발생률은 측정하지 않았다.
- **어떻게 전달하는지가 달랐던 단건.** 같은 39/40 제출에서 실패 사례를 나열한 일반 재수정은 5회 뒤에도 39점이었다. 담당자 답 옆에 실패한 호출·기대값·실제값을 붙인 조건은 추가 호출 1회 만에 40점이 됐다. 별도의 3모델 비교에서 실패 사례를 제공한 조건과 일반 재검토의 최종 점수는 각각 7B 74 대 70, 14B 74 대 74, Qwen3 99 대 98이었다(각 120점 만점). ## 8. 결론과 다음 검증

1. **정확도 상승은 시드별로 다르다.** 같은 호출 수의 독립 감시가 자체 검토를 앞선 사례와, 추가 수정이 기존 정답을 잃게 한 사례가 함께 있었다. 총점에 더해 새로 고친 문항과 새로 틀린 문항을 기록해야 이 차이가 보인다.
2. **발견·전달·구현은 각각 확인할 수 있다.** 예외를 언급한 피드백, 메인이 실제로 받은 원문, 수정 후 어떤 입력의 반환값이 바뀌었는지는 서로 다른 증거다. 웹의 빈 검사 완료 오류는 고쳤고, 최근 실험에서는 원문을 보존해도 코드 판독 오류가 남았다.
3. **현재 확인한 병목은 D의 코드 판독이다.** 공개 자료만으로 확인 가능한 실행 경로조차 잘못 읽었다. 반면 유예가 정확히 몇 분인지는 부분정보만으로 특정하기 어렵다. 두 상황을 같은 종류의 실패로 집계하지 않는다.
4. **다음 실험은 메인의 반영 능력을 분리한다.** 같은 현재 코드와 메인 지시에서 기존 전달문만 주는 조건과, 공개 코드로 검증한 진단 한 문장을 덧붙이는 조건을 비교할 수 있다. 예를 들면 ‘25시간 조건에 걸리는 고객은 앞선 24시간 조건에서 이미 허용된다’이다. 담당자 답변·중간 채점 없이 최종 오답 복구, 새 오답, 비용을 비교한다. 이 비교와 D의 후속 질문 경로는 아직 실험하지 않았다.

후속 결과를 새로운 과제에 일반화하려면 정책·채점 사례·중단 기준을 먼저 고정하고, 기존 실패를 보고 선택하지 않은 과제와 코드로 반복해야 한다. 현재 자료는 어느 단계에서 오류가 났는지를 보여 주며, 감시자 수나 페르소나의 일반적인 우위는 추정하지 않는다.
