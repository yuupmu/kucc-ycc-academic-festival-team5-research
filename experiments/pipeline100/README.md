# 100문항 멀티에이전트 비교

예약 취소 50문항과 문의 배정 50문항에 로컬 Qwen3.5-4B의 26가지 구조를 적용했다. 가장 최근의 실제 3회차 운영에서는 메인 단독 66/100, 자체 질문 73/100, 독립 감시자 A·B·C 질문 62/100이었다. 공개 명세 또는 담당자 회신으로 근거를 확보하고 맞힌 문항은 각각 18개, 43개, 60개였다.

## 이번 비교에서 고정한 것

- 난수 시드는 263이며 같은 프로젝트의 모든 조건은 같은 초안에서 시작했다. 메인과 감시자는 같은 모델을 사용했다.
- 100문항은 두 함수의 서로 다른 입력 100개다. 기존 20개에 80개를 더해 18개 유형의 경계를 구현하는 방식을 살폈다. 처음 채점하기 전, 예약 생성 시각이 이용 시작보다 앞서도록 추가 입력 4개를 교체했다. [문항과 기대 반환](sample.json) · [기준](protocol.json) · [입력 교체 전후](sample-correction.json)
- 실제 3회차 운영에서는 직전 코드와 누적 회신으로 다음 질문을 생성했다. 고정 대화에서는 기존 3회차 질문·회신을 그대로 써 작성기 변경의 영향을 측정했다. 동일한 모델 요청이 앞선 실행에 있으면 당시 원 응답을 재사용했다. [모델 실행과 대리 회신 기록](runs)
- 담당자는 Codex가 대리했다. 질문에 해당하는 기존 정책 문장만 골라 자연어로 전달했고, 이미 답한 동일 질문 묶음에는 같은 답을 재생했다. 중간 점수는 모델에 전달하지 않았다. 모든 새 제출을 고정한 뒤에만 연구자 쪽에서 각 버전을 채점했다. [최종 후보 파일 식별값](submission-manifest.json)

## 문항 하나를 추적하는 방법

1. 엑셀의 **문항 100개**에서 입력, 기준값, 충분한 답변을 확인한다. 예약의 두 숫자는 예약 후 경과 초와 이용 시작까지 남은 초다.
2. **질문과 답변**에서 구조와 과제를 선택한다. 회차, 제안자, 질문 원문, 대리 담당자의 답, 같은 회차에서 관련 문항의 성패가 바뀐 내역이 나온다. 처음 받은 문구의 주제에는 재확인이나 구체화 요청도 들어간다. 같은 회차에서 겹치는 개선 건수는 여러 질문에 중복 표시될 수 있다.
3. **문항별 실행**에서 문항 번호와 조건을 골라 최종 반환, 판단 보류나 오류, 마지막 실행 줄을 확인한다. **회차와 비용**은 회신 묶음과 정확한 제출 파일을 연결한다. **전달 안 된 질문**에서 감시자가 제안한 뒤 탈락한 원문을 확인한다.

예를 들어 R28은 예약 생성 후 정확히 600초, 이용 시작까지 3,600초 남은 입력이다. 감시자 조건의 담당자는 끝점을 포함한다고 답했다. 실제 운영 코드는 1회차에 허용했지만 2·3회차에는 37번째 줄에서 거부했다. 반대로 T09에서는 문의의 담당 태그가 account와 billing일 때 우선순위를 답한 뒤 최종 코드가 billing을 선택했다.

## 재현과 기록 범위

연구 기록 검산은 실험실 루트에서 다음 명령으로 실행한다.

~~~sh
python3 -B -m experiments.pipeline100.verify
~~~

세부 실행 절차는 문항 등록(design), 생성·회신(collect), 잠긴 제출에 대한 사후 채점(grade), 결과 대조(verify)로 나뉜다. 사후 채점을 다시 실행할 때는 아래 명령을 사용한다. 원래 제출의 파일 식별값을 먼저 검사한다.

~~~sh
python3 -B -m experiments.pipeline100.grade
~~~

최종 판정은 2,600건, 회차별 코드를 포함하면 3,800건이다. 이전 방식들은 원 과제의 같은 50문항에서 다시 비교했다. 301행은 조건·시드·프로젝트·단계의 조합이며 중복된 코드도 있다. 기록이 회신 묶음 단위로만 남은 사례는 엑셀에서 표시했다. 2차 미팅 자료에 나온 자원 배정 150세트는 다른 과제다.
