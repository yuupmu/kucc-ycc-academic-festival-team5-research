# 감시자가 지적한 코드만 수정하는 작성기

새로 시작하는 3회차 실행은 감시자의 수정 지적, 해당 시점의 코드, 실제로 받은 자연어 답을 함께 메인에 전달한다. 작성기는 공개 명세와 회신에서 입력 조건과 반환값을 연결할 수 있는 범위를 찾아 그 분기만 바꾼다. 해당 분기가 이미 맞으면 그대로 유지하고, 기존 함수에 분기가 없으면 그 입력에만 적용되는 조건을 추가한다. 시간 구간의 끝점을 포함한다는 말은 기간에 속한다는 뜻으로 처리하고, 실제 허용·거부는 기간 안의 동작을 확정한 별도 회신과 연결한다.

기존 실행 명령으로 새 폴더에 시작하면 이 방식이 기본이다. 이전 버전으로 시작한 실행은 저장된 버전으로 재개된다. 사람에게는 한 회차의 질문을 묶어서 제시한다. 마지막 코드 검토에서 새 지적이 나오면 그때까지 받은 답변으로 한 번 더 수정하고, 코드가 달라지면 다시 검토한다. 담당자도 아직 정하지 않았거나 근거 있는 수정 범위를 특정할 수 없으면 미해결 상태를 기록한다.

~~~sh
python3 -B -m experiments.repeated_intervention 새실험폴더 --project 공개명세.json --role multi --cycles 3
python3 -B -m experiments.repeated_intervention 새실험폴더 --reply-to 1 --answer-file 담당자답변.txt
~~~

## 비교 방법

| 시점 | 기존 방식 | 수정 후 |
|---|---|---|
| 감시자가 오류를 발견한 뒤 | 검토 결과에 지적을 남겨도 작성기가 다음 수정의 입력으로 받지 못했다. | 직전 코드와 지적 원문을 함께 전달한다. 다음 회차에 감시자가 다시 언급하지 않아도 미해결 지적을 이어받는다. |
| 담당자가 답한 뒤 | 메인이 여러 입력 구간의 반환값을 다시 선택해 앞선 회차에서 맞힌 값도 바뀔 수 있었다. | 지적 또는 답한 질문에 해당하는 입력을 찾고, 누적 회신과 공개 명세로 결과를 확정할 수 있는 분기만 편집한다. |
| 3회차 최종 검토 | 마지막에 새 지적이 생기면 수정 기회 없이 종료할 수 있었다. | 이미 받은 답으로 한 번 더 수정한다. 코드가 바뀌면 감시자가 다시 읽고, 남은 지적을 기록한다. |

일반 실행에서는 회차마다 `감시자 A·B·C → 질문 묶음 → 담당자의 자연어 답변 → 메인의 분기 수정 → 감시자 코드 재검토` 순서로 진행한다. 접수한 질문이 있으면 답변이 도착할 때까지 멈춘다. 자체 검토 조건에서는 메인이 감시자 역할도 맡는다.

- 기존 100문항 조사에서 실제 후속 질문을 한 조건의 초안·질문·대리 담당자 답변·모델·시드를 그대로 사용한다. 질문을 고정한 이번 비교의 새 검토에는 각 조건이 만든 실제 코드가 들어간다.
- 예약에서 이미 거부 코드를 만들었던 2회차 제출도 별도로 사용한다. 그 당시 감시자 A·C의 지적과 당시까지의 회신만으로 고친다. 새 수정에 사용한 정보에 채점기나 예제의 기대 결과는 없다.
- 새 제출을 모두 고정한 후 연구자만 기존 핵심 20문항을 채점한다. 고장 난 예약 코드를 직접 고치는 비교는 기존 예약 50개로 나머지 분기의 동작까지 확인한다.
- 자연어를 표현할 수 있는 모든 프로그램에 대한 보장은 아니다. 확인 가능한 입력·출력 규칙을 가진 Python 결정 함수를 대상으로 한다. 모호한 문장, 서로 충돌하는 규칙, 복수 함수에서 위치를 특정할 수 없는 지적, 부작용을 보존할 수 없는 편집은 미해결로 남긴다.

## 첫 수정 결과

기존 핵심 20문항에서 감시자 3회차는 **13개에서 15개**, 메인 자체 검토 3회차는 **13개에서 13개**였다. 이전 값은 수정된 코드를 보고 실제 후속 질문을 한 기존 실행의 마지막 제출에서 가져왔다. 첫 수정(v2)에는 그 실행의 초안·질문·자연어 회신을 그대로 주었다. 두 프로젝트를 각각 세 번 검토했고, 코드를 바꾼 뒤의 검토 의견은 새로 받았다.

| 조건 | 예약 정답 /10 | 문의 정답 /10 | 합계 /20 | 새 정답 / 잃은 정답 | 누적 토큰 |
|---|---:|---:|---:|---:|---:|
| 메인 단독 · 공통 초안 | 6 | 4 | 10 | — | 1,625 |
| 메인 자체 검토 · 기존 → 첫 수정 | 5 → 6 | 8 → 7 | 13 → 13 | 1 / 1 | 24,801 → 16,823 |
| 감시자 A·B·C · 기존 → 첫 수정 | 5 → 7 | 8 → 8 | 13 → 15 | 5 / 3 | 54,221 → 53,179 |

토큰은 각 조건을 독립 실행할 때의 두 과제 입력·출력 합계다. 첫 수정에서 자체 검토는 입력 13,322·출력 3,501토큰, 감시자는 입력 39,971·출력 13,208토큰을 사용했다.

**감시자가 지적한 600초 분기.** 기존 예약 2회차의 거부 코드에 당시 A·C의 지적과 그때까지의 답만 다시 적용했다. 코드에서 바뀐 줄은 ‘예약 후 정확히 600초, 이용 시작까지 0초 초과 24시간 미만’의 반환값 한 줄이었다. 이 분기를 지나는 **R28·R29·R30·R31·R32 다섯 입력이 모두 거부에서 허용으로** 바뀌었다. 예약 50문항의 정답은 **19 → 24개**, 나머지 **45개는 반환값과 판정이 모두 같았다**. 이는 이미 거부한 프로그램을 직접 고친 별도 실험이다.

**3회차 전체에서 남은 결함.** 감시자 방식은 R01·R07·R28·R29·R43을 새로 맞혔지만, 이전 제출에서 맞았던 **R12·R13·R14**를 잃었다. 세 문항은 일반 취소 마감과 정정 기간이 모두 지난 경우다. 담당자가 두 조건이 모두 성립하면 거부한다고 명시했어도 첫 수정의 최종 코드는 세 입력을 모두 허용했다. 자체 검토는 R43을 새로 맞혔고, 미등록 태그와 두 담당 팀이 섞인 T31에서 기존의 privacy 대신 account를 반환해 한 문항을 잃었다.

이 비교는 Qwen3.5-4B의 시드 263 하나와 기존 두 과제의 고정 대화에서 얻은 결과다. 새 파이프라인이 후속 질문까지 다시 생성할 때의 점수는 별도 검증이 필요하다. 재생 중 여러 구간의 근거를 집합 순서로 처리하면서 기록·코드 순서가 달라지는 문제도 확인했다. 첫 수정의 최종본은 확정된 구간을 작성 요청의 입력 목록 순서대로 기록하도록 고쳐 고정했다.
